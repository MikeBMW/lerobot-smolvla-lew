## 一、⚠️ 更正 SKILL.md ⑦: 训练用的 state 是 env 原生 obs, 不是 visual39

SKILL.md ⑦ 原本写"引擎内已备同源通道 `_l3_forward(visual39)`, 外部脚本必须喂 visual39"。
**这是错的, 且曾直接导致接管卡死。** 实证链条:

```
① tools/collect_simreal_vla_data.py 落盘: {"observation.state": np.asarray(o[:39], dtype=np.float32)}
② 该 o 来自引擎回调 _frame_sink(self, act, o)
③ 引擎里 o = np.asarray(env._get_obs(), ...).ravel()
④ 数据集 parquet 实测 (131383, 39):  前几维 [0:3]=手xyz, [3]=gripper, [4:7]=peg, [7]=0.1034
   → 与 env 原生布局一致; 而引擎自构造 visual39 的 [4:7] 是**速度** v
```

**结论**: 训练与推理都该用 **env 原生 obs**; `visual39` 是给 L2 六层控制器用的中间量,
不是模型输入。

**实测效果**:
| 传给 `_l3_forward` 的东西 | 结果 |
|---|---|
| `visual39` (引擎自构造) | 接管卡死"转移"段 2318 帧, 2500 步不完成 |
| `o` (env 原生) | 接管正常完成 |

**方法论教训(比结论更重要)**:
- 口径要以**采集脚本实际落盘的字段**为准去核对, 不要按"哪个看起来更像训练用的"推断。
- 不要凭注释/变量名猜 —— ⑦ 当初就是靠推断写错的, 然后被后续会话当权威照抄。
- 反面参考: policy config 里的 `resize_images_to=[64,64]` 也属"看起来像但实际不是"的坑
  (推理端实测正确值是 **128**, 见 ⑧/⑩)。

## 二、运行时可归因性: "评估的模型" 必须 = "产品默认跑的模型"

**触发**: 用户追问"现在这个模型, 是真正的运行时跑的模型么?"
**实锤**: 引擎默认 `SS_L3_CK` 指向 `.../smolvla_lew_v8/checkpoints/030000/...`(旧模型),
而"跑通全链"的是 `.../smolvla_lew_v10_1h/checkpoints/004000/...` →
**GUI 里开 SS_L3 跑的是旧模型, 与验证对象不是同一个** → 成绩无法归因。

**规则(每次交付都适用)**:
1. 任何"跑通/达标"结论必须给出**三要素**: 哪个 ckpt 路径 · 哪条代码路径(哪个开关) · 哪份日志/视频。
2. 引擎/产品侧**启动必须打印实际加载的模型路径**, 并存成可读字段(如 `self._l3_ck_used`),
   让"验证对象"与"运行时对象"当场可核。
3. 切换默认模型 = **一次正式操作**:
   训练完成 → 多 seed 验证 → 通过 → 才改默认 ckpt → 启动日志确认一致 → 出视频存证。
4. **同物两处默认值**(引擎默认 vs 评估脚本默认)必须同时对齐, 改一处必查另一处。

## 三、跨会话/跨路径结论核验: 不要未复现就否定他人结果

**实锤(我自己判断错了)**: 另一会话报"模型闭环 5/6", 我在引擎里测接管卡死 →
我一度判定"不采信 / 虚报"。
**真相**: 它的 rollout 脚本直接 `env.render()`, **绕过了我引擎里的黑帧 bug**(见 SKILL.md ⑭)
→ 两条路径一个有一个没有 → 成绩天然不同。**不是虚报, 是路径差异。**

**正确流程**:
1. 先做**逐项输入对比**(state / image / 动作语义)找出路径差异, 再下任何结论。
2. 只有在**同一 ckpt + 同一脚本 + 同一环境变量**下复现失败, 才可以质疑数字。
3. 质疑要发"可复现三要素请求"(要对方给 ckpt / 脚本 / 环境变量), 而不是直接下"虚报"结论。

**反向教训**: 未复现就否定他人结果, 与虚报同样有害 —— 它会掩盖真正的 bug(本例就是)。

## 四、接入审计法: "存在" ≠ "被调用" (定义≠接入)

用户问"这个思想整合进架构了么"时, **必须用调用点核查, 不能凭模块存在就答"整合了"**。

```bash
# 模块定义存在?
grep -n "def local_intent\|def goal_intent" src/lerobot/memory/global_memory.py
# 但引擎真的调用它吗? ← 这一步才是"接入"的证据
grep -rn "global_memory\|GlobalMemory" tools/gui/state_space_sim_real.py    # 无结果 = 未接入
```

**实测审计结果(INTACT 四机制的落地程度, 供后续会话避免重复宣称)**:
| INTACT 机制 | 状态 | 证据 |
|---|---|---|
| 条件动作商(等价类折叠) | ✅ 真接入 | `motor_hub.build_quotient()` + 引擎 `SS_MOTOR_HUB` 调用点 |
| 二态意图语法 (`z_{t+1}−z_t` / `sg(z_g)−z_t`) | △ 只定义未接入 | global_memory.py 有函数; 引擎 grep 无调用 |
| 非对称端点梯度 | ❌ 未做 | — |
| **共享预测器(一个网络吃两种意图)** | ❌ 未做 | 这是 INTACT 的灵魂, 恰恰没做 |

**汇报纪律**: 说"整合了"必须能指出调用点; 只是"有模块/有画布节点"要说成"已定义, 未接入"。
画布节点能点开看 ≠ 参与控制。

## 五、性能: 评估循环里的模型类级缓存

多 seed 评估时, 每 `new` 一个 `RealStateSpaceSim` 就重载一次 625M 模型 → 慢 N 倍。
修法: 把 policy/pre/post 提升为**类级缓存**:
```python
_cls = type(self)
if getattr(_cls, "_L3_CACHE", None) is not None:      # 命中 → 零加载
    self._l3_pol, self._l3_pre, self._l3_post = _cls._L3_CACHE
    ...
_cls._L3_CACHE = (self._l3_pol, self._l3_pre, self._l3_post)   # 首次加载后写回
```
配套: `tools/eval_takeover.py`(多 seed 接管鲁棒性评估入口)。
注意: 与训练**抢 GPU** 时, 评估会显著拖慢训练(实测 4.5 → 6.15 s/step) → 评估要挑 GPU 空窗或错峰跑。
