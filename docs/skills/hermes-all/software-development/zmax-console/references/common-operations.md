### 2. 系统架构模块 (L2/L3/L4 对比)
ArchitectureModule 在 PluggingSceneModule 前定义。当前为三栏对比布局:
- L2 基线 / L3 增强 / L4 旗舰 — 每列三层 (SYS2 → SYS1[SYS11+SYS12] → SYS0)

**数据结构陷阱**: 每层数据是 `("标题", "模型名", color, [层列表])`。层列表每项是 `(sys_id, desc, color, items)`。关键：
- SYS2/SYS0 的 items 是 `[str, ...]` (字符串列表)
- SYS1 的 items 是 `[(sub_id, sub_desc, color), ...]` (元组列表)
- 两者结构不同，`_level_card` 用 `isinstance(items[0], tuple)` 区分
- **SYS1 必须有4个字段**: `("SYS 1", "边缘推理", SYS11_COLOR, [...])` — 缺字段会 ValueError

**修改步骤**:
1. 改 levels 数组中的文字
2. 确保每层4字段
3. python3 -c "import ast; ast.parse(open('tools/gui/studio.py').read()); print('Syntax OK')"
4. git add -A && git commit -m "说明" && git push
5. git tag -f v1.0.x && git push origin v1.0.x --force

**匹配PPT**: 严格按照用户手绘布局复现，不要自己发明配色/结构。用户画三层横排(SYS2→SYS1[SYS11+SYS12]→SYS0)就不能做成三列竖排。配色必须从PPT提取(取色#000000)。

### 8. 推理服务 — 多策略支持 (SmolVLA / ACT)
InferencePanel (studio.py) 的推理服务端支持策略切换:
- **studio.py `_build_server_panel`**: 模型行上方有"策略"下拉框 (`self.strategy_combo`, SmolVLA/ACT)。`_on_strategy_changed` 切换时自动换 ckpt 默认路径 (`outputs/act/checkpoints/...`)。`_server_start` / `_client_connect` 里取 `self.strategy_combo.currentText().lower()` 传给 server/client。
- **inference_server.py**: `POLICY_TYPES` 注册表 (`smolvla` → SmolVLAPolicy, `act` → ACTPolicy) + `load_policy()`。`start_server(..., policy_type=)` 透传。`_patch_preprocessor(checkpoint_path, policy_type)` 分流: ACT 走标准 `select_action` 管线 (patched_predict 按 `policy.config.input_features` 键名构建 obs, state + images, 归一化/255, select_action → chunk → TimedAction); SmolVLA 走原有定制 tokenizer 管线。
- **inference_client.py**: `send_policy(checkpoint_path, dataset_repo, policy_type, device)` — `RemotePolicyConfig(policy_type=...)` 不再硬编码 smolvla; image 特征匹配改为 `"image" in k` (兼容 observation.images.xxx)。
- **act_infer.py**: 独立 ACT 推理验证脚本 — `python3 act_infer.py [模型路径|HF ID]`。HF 预训练可用 `lerobot/aloha_static_act`; 合成 obs 用 `policy.config.input_features` 构造。`HF_ENDPOINT=https://hf-mirror.com` 国内镜像。
- ACT 是标准 LeRobot 策略: `ACTPolicy.from_pretrained(...)`, 输入键即 `input_features` 的键 (observation.state + observation.images.xxx)。

- **节点联动拖动 (2026-08-01 用户二次反馈 "还是跟着动" 后找到根因)**: 两个节点时拖动 A，B 跟着动。**第一轮修复 (super() 后强制单选) 不彻底 — 用户实测仍联动**。根因: QGraphicsScene 在 `mousePressEvent` 时就把所有已选中 movable items **缓存为拖拽集合**, press 之后再改 selected 状态无效 (Qt 内部行为)。**最终方案 (必须这样)**: ① SimNodeItem **移除 ItemIsMovable flag** (只留 ItemIsSelectable + ItemSendsGeometryChanges) — 让 scene 完全不参与移动; ② SimCanvas 完全接管拖动: mousePressEvent 里节点主体按下时记录 `self._drag_node = item` + `self._drag_offset = p - rp` 并 return (不调 super), mouseMoveEvent 里 `self._drag_node.setPos(p - self._drag_offset)`, mouseReleaseEvent 清空 `_drag_node`; ③ 输出端口按下仍走连线模式 (先判端口再判主体)。选中管理照旧: 非 Ctrl 点击节点清其他选中 + `item.setSelected(True)`, 空白处 clearSelection, Ctrl 保持多选。\n- **offscreen 验证真实拖动 (手动接管后可行, 2026-08-01 实测)**: 一旦拖动由 SimCanvas 自己接管 (不依赖 scene grabber), offscreen 下构造 QMouseEvent 直接调 `canvas.mousePressEvent/mouseMoveEvent/mouseReleaseEvent` 就能完整模拟 press→move→release 并断言场景坐标变化 — 本会话 10/10 验证通过 (A 移动 (150,140), B 原地不动 (400,100))。注意: `QEvent.MouseRelease` 不存在, 用 `QEvent.MouseButtonRelease`; 事件构造 `QMouseEvent(type, pos, Qt.LeftButton, Qt.LeftButton, modifier)`。若仍用 scene 默认拖动 (未接管), 则 QTest.mouseMove 无效, 只能退而断言 `scene.selectedItems()` + `item.setPos()` 验证 itemChange 同步。
- rebase 冲突多 (如 mac 分支大改同批文件) 时 `--abort` 后改 `merge -X theirs --allow-unrelated-histories` 更干净。

**核心模式: 阿里云安全组封端口 → 走 nginx 443 反代绕过**
- ECS 直接开 50053/39053 公网**都不通** (安全组未放行, ufw 放行也没用 — 安全组在 ufw 外层)。
- 解法: nginx 在 datadrive.world.conf 加 `location /api/relay/ { client_max_body_size 200m; proxy_pass http://127.0.0.1:39053/; }`, 公网访问 `https://datadrive.world/api/relay/...` 即通。

- 端点: `POST /upload` (数据/模型包, json 或原始字节 — **流式分块写盘**, 见下) · `GET /latest` (**弹栈式** 拉取即删, 中转不留存) · `GET /peek` (🆕 只读不删, 消费前确认队头) · `GET /status` · `GET /packages` · `POST /ci/validate` (Simulink 模型验证, 调 simulink_ci.py 的 run_checks) · **`GET/POST /command` (2026-08-03 新增, 采集指令端点)**。
- **/command 采集指令链路 (2026-08-03, 老倪 \"你得在ECS上做端口转发啊\")**: relay 加 `COMMAND_FILE = Path(\"/root/zmax-relay/command.json\")`; **GET /command** 读文件返回 `{\"cmd\":\"collect\", \"ts\":...}` (默认 collect), **POST /command** 写指令文件 (body `{\"cmd\":\"collect\"}`)。用途: 4060 主动下发采集指令给 Mac 守护, 形成 **4060→ECS→Mac→Orin** 指令链路 (与数据链路 Orin→Mac→ECS→4060 反向)。公网入口 = `https://datadrive.world/api/relay/command` (nginx 已反代)。⚠️ **Mac 端 zmax_auto_collector.py 的 BACKEND 仍是旧地址 `http://106.75.239.80:50053` (不是本 ECS 39.102.211.79!)** — 该脚本轮询 `{BACKEND}/command`, 要小芳更新指向 `https://datadrive.world/api/relay` 才能真正收到 4060 指令。补丁方式: 本地写 patch 脚本 → scp 到 ECS → `cp zmax_relay.py zmax_relay.py.bak_$(date +%s)` 备份 → python3 执行 → `ast.parse` 验证 → 重启 → curl 验证 GET/POST/公网三连。注意 relay 脚本端到端改完 grep 端口别回退 (见\"端口一致性陷阱\")。**实测 (2026-08-02): relay heartbeat 返回的 endpoints 数组 = [POST /upload, GET /latest, GET /status, GET /packages], 没有 /peek — 但 GET /peek 返回 `{"error":"no data yet"}` 是 404 语义而非端点缺失; GUI 采集轮询用 `/status` (含 uptime/packages/latest_meta) 而非 /peek。**
- **缓冲约束 (老倪要求)**: 总量 ≤100M, 超限删最旧; 拉取即删。
- **弹栈队列事故 (2026-08-02)**: /latest 取走即删, 第一次 GET 弹出 87MB 二进制未保存 → 队列空。**消费前必 /peek**; 二进制模型用 cicd_pull_deploy.py 或 curl -o 拉, relay_train.py pull 只拉 JSON 训练数据。

**ECS 后台服务启动模式 (start.sh)** — 直接 `nohup ... &` 或 ssh 单行命令会超时/被杀:
```bash
# start.sh 标准模板 (pkill 必须单独一条命令, 不能与启动同条 && )
pkill -f 'zmax_relay.py' 2>/dev/null; sleep 1
cd /root/zmax-relay
setsid nohup python3 zmax_relay.py > relay.log 2>&1 < /dev/null &
sleep 2; ps aux | grep zmax_relay | grep -v grep | head -1
```
- **pkill 自杀陷阱**: `pkill -f 'zmax_relay.py' && setsid nohup python3 zmax_relay.py ...` 在同一条 ssh 命令里, pkill 会匹配到自己要启动的那条 → 新进程起不来 (日志还是旧时间戳)。必须拆成两条或放 start.sh。
- **pkill 括号技巧 (2026-08-03 实测)**: 单条 ssh 命令里 `pkill -f 'zmax_relay.py'` 连**自己所在 ssh 命令行都杀** (bash -c 的命令串含该字符串) → 整个 ssh 会话 exit 255, 后续命令全不执行。解法: `pkill -f '[z]max_relay.py'` — 方括号让进程自己的命令行不匹配, 但目标进程 (命令行是明文 zmax_relay.py) 仍匹配。验证: `ps aux | grep '[z]max_relay'` 计数归 0。此技巧同时适用于本机 pkill studio.py 的场景 (见"修改 GUI 代码后必须重启控制台"陷阱)。
- **⚠️ 字符串补丁吞函数头 (2026-08-03 实测, 补 relay 加 /command 时把 enforce_buf_limit 弄丢)**: 用 python `s.replace(old, new)` 给服务端脚本打补丁时, 若 old_string 是 `def enforce_buf_limit():` 整行 + 后续 docstring, 而 new_string 是"新函数定义 + 原 def 行" — 一旦 new_string 里**漏写了原 def 行** (只插了新函数没补回旧函数头), 旧函数体 (docstring + 代码块) 就变成新函数尾部的一段孤儿代码 → 运行时 `NameError: name 'enforce_buf_limit' is not defined` (上传 400)。**教训: 服务端脚本补丁三连验证 = ① `ast.parse` 语法过 ≠ 逻辑过 (孤儿代码是合法语法!) ② grep 确认被替换函数仍在且只有一份 ③ 真实 curl 打一次端点做功能冒烟 (上传 JSON 包看 200)**。补丁脚本里用 `assert bad in s` 先验模式存在再 replace, 并打印 `s.count("def enforce_buf_limit")` 这类计数。
- ssh 执行 `nohup &` 后 ssh 命令本身挂起超时 — 用 start.sh 脚本 + `bash start.sh` 返回。
