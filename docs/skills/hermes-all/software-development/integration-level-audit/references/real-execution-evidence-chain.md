# "是真的么" —— 真执行证据链（2026-09-25 实测）

## 触发场景

用户（老倪）会**反复**用这些句式质疑，且每次都是同一类需求：

> 「是真正的在 GPU 上训练么？」「APP 是真正的训练么？进度是不是真实的？」
> 「APP 要把硬件负载/存储/算力都显示出来」「4060 呢？mps 呢？**app 要显示实际值**」

**这类质疑不是让你再解释一遍，是让你交证据。** 重复被问 = 上一轮给的东西不可信/不完整
（本会话连问 3 次，根因是前两次交的是**聚合数字**而非**可复现的取证**）。

## 铁律

1. **聚合/派生数字不是证据。** 「GPU 利用率 89.6%」「平均步速 3.1」可以被相信也可以不被相信。
   证据 = **可复现的原始观测**（进程表里的 PID、时间戳序列、两个独立源的数值对照）。
2. **中间过程的成功返回 ≠ 末端结果。** `ok=True` 只说明**启动动作**被受理，不说明真的在跑（见 §4）。
3. **证据链要环环相扣、每环可单独复核。** 五环式（见 §2），任何一环断了就如实说断了。
4. **一次给出，别让用户问第二遍。** 他问第二遍就是上一轮的交付不合格。

## 1. 铁证链范式（照抄结构）

**GPU 训练铁证（4 环）**
```
① nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader   → PID 在表内
② tr '\0' ' ' < /proc/<PID>/cmdline                                       → 就是训练脚本
③ 利用率时间序列（连续采样 3-5 次）util/temp/power                          → 持续高位, 非瞬时抖动
④ 训练日志步数推进（step 500 → 750 → 1000）                                 → 不是在空转
```
实测产出：`PID 78745 / 1344 MiB`、利用率 `100 99 99 99 98`、温度 `69-71°C`、步数 `500→1750`。

**APP→训练 铁证链（5 环，工具 `tools/app_train_proof.py`）**
```
① APP API 启动 → 返回 jid + pid
② 该 pid 出现在 nvidia-smi GPU 进程表
③ /proc/<pid>/cmdline 是训练脚本, 且参数来自 APP 模板（含 APP 生成的 --progress-file）
④ 双源同源: 进度文件 step 与 日志 step 一致（口径见 §3）
⑤ 进度单调递增（时间戳序列）
```

## 2. ★ PID 解析：包装进程 ≠ 真进程（最容易把整条链判假）

APP/控制台用 `subprocess.Popen(cmd, shell=True)` 启动 → 返回的 pid 是 **`/bin/sh -c ...` 包装进程**，
真正的 CUDA 进程是它的 **python 子进程**。直接拿包装 pid 去查 GPU 进程表 → **永远是"不在表内"**，
于是「② pid 在 GPU 进程表 ❌」把一条本来健康的链判成造假。

```python
def resolve_real_pid(pid):
    """包装进程 → 真训练进程: 优先取 GPU 表内命令行匹配的, 其次取子进程"""
    for gp in sorted(gpu_pids()):                      # nvidia-smi 自己的进程表最可信
        if "backbone" in sh(f"tr '\\0' ' ' < /proc/{gp}/cmdline"):
            return gp
    for ch in sh(f"pgrep -P {pid}").split():           # 退路: /bin/sh 的 python 子进程
        if ch.isdigit() and "backbone" in sh(f"tr '\\0' ' ' < /proc/{ch}/cmdline"):
            return int(ch)
    return pid
```
同源坑：`gpu_proof_sampler.py` 与 `find_pid(--match)` 都有这个毛病。
**任何"某 PID 在不在某表里"的判据，先问一句：这个 PID 是包装还是本体。**

## 3. ★ 双源比对必须同粒度（否则必假失败）

两个独立源**粒度不同**时，逐点相等比较是错的：
- 进度文件：每 **10 步**写一次（为进度条服务）
- 训练日志：每 `--stats 250` 才打一行

→ 「双源一致」若按逐点 `pf == lg` 统计，实测只有 **1/8 次**相等 → 误判"不一致 ❌"。

**正确口径**（两者互为约束而非要求相等）：
```python
not_ahead = all(log_step <= progress_step for ...)   # 进度不得超前于真训练
boundary  = [lg for pf, lg in pairs if pf == lg]     # 在 stats 边界必须精确相等
ok = not_ahead and boundary
```
一般化：**比对两个不同采样率/聚合度的源，只能比"单调约束 + 在共同边界上相等"，不能比逐点相等。**

## 4. ★ "看起来在发/在跑" ≠ "真的通"（本会话抓到 3 个）

| 现象 | 真相 | 该查什么 |
|---|---|---|
| DDS 发布端日志正常刷 `📤 ...`，订阅端**收到 0 条** | 多网卡主机默认多播选错网卡 | `matched_publications` 是否 > 0；改单播配置 |
| 控制台"启动训练"返回 `ok=True` | `stage_moe_backbone.py: error: unrecognized arguments: --progress-file` → **进程秒退** | 读该 job 的**日志尾部**，不是看返回码 |
| 进度文件始终不生成，功能"没生效" | 目标目录不存在 → `FileNotFoundError` 被 `except: pass` **静默吞掉** | `makedirs` + 首次失败**必须打印原因** |

**铁律**：验证要落到**末端可观测结果**（远端收到了吗？文件生成了吗？进程还活着吗？），
不要停在"我这边的调用返回成功"。上表第 2 行尤其阴 —— 我自己的测试脚本还先读错了字段，
把 `cmd含进度文件: False` 当成根因，是**日志尾巴**才暴露真正的报错。

## 5. ★ 静默吞异常 = 自毁取证能力

```python
try:
    json.dump(..., open(p, "w"))
except Exception:
    pass                       # ❌ 真故障(目录不存在)被吃掉, 现象是"功能没生效"
```
修法：**保留不崩，但首次失败打印一次原因**（后续去重避免刷屏）：
```python
except Exception as _e:
    if not getattr(a, "_warned", False):
        print("⚠️ 写入失败(不影响训练): %s: %s" % (type(_e).__name__, _e), flush=True)
        a._warned = True
```
配套：启动时就 `os.makedirs(dirname, exist_ok=True)` 把根因消灭在入口。

## 6. ★ 改配置类参数必须核验"真的生效"（否则把同一个结果报成两个）

`--aug-scale 0.90,1.10` 的 **setter 从未被写入**（补丁锚点没命中），只有读取侧存在
→ 新训练的 ckpt 与上一次 **sha256 完全相同**，却当成"新结果"上报了（几何指标也照抄了上一版）。

**核验三板斧**（改任何配置类参数后至少用一条）：
- **打印生效值**（`🎨 增强: 开 | 缩放范围 0.90~1.10`）—— 没这行就说明没生效
- **产物 hash 比对**（`sha256sum`）—— 与上一版相同即"没变"，不是"变好了"
- **数值微差**（step1 loss 0.3079 vs 0.3080 说明增强确实换了）

**推论**：把"配置生效"做成**启动横幅的一行必打印**，比事后核验更省事。

## 7. ★ 同一个函数常有多个调用点 —— 改行为必须 grep 全部

本会话同日第三次犯：`--cache-gb` 只传到 `make_loader`，**真调用点**（fork 前那段）仍用自动上限
→ 大缓存照装 → OOM。同类：`--aug-scale` setter 锚点未命中（§6）。

**纪律**：改一个函数的**行为/默认值**后，`grep -n '<func>('` 看**所有**调用点逐个确认；
再用"改后必然不同的可观测量"（hash / 打印 / 行为差异）复验。

## 8. ★ 指标本身必须先能被证伪

MOE 门控的"阶段-专家一一对应率"在**某个专家吃掉全部阶段**时也判 **7/7 通过** ——
因为每行的最大值都是那同一个专家。→ 这不是指标，是绿灯生成器。

**修法：换成能失败的判据（单射性）**
```python
tops = [argmax(row) for each stage]      # 各阶段的主导专家
n_inj = len(set(tops))                   # 去重后还剩几个 → 全归 E0 时 = 1
```
实测：旧判据报"6/7 分化成立"（假阳性，已撤回），新判据显示**单射性 1 个 = 完全坍缩**。

**通用问句**：如果一个"错误/退化"的输入也能让这条判据通过，那它就不是判据。
**判据上线前先构造退化输入打一次**。

## 9. 长任务进度：由被观测方自己产出，粒度要匹配用户感知

进度条"看起来是假的"往往不是造假，是**粒度太粗**：训练脚本 `--stats 250`（约 80 秒一行），
从日志里猜进度 → 80 秒才跳一次 → 用户认定是装饰。

**修法**：训练脚本加 `--progress-file <path> --progress-every 10`，每 N 步写 JSON
（step/total/pct/loss/sps/best/ts/pid/running），**与 `--stats` 的日志粒度解耦**；
控制台直读该文件。实测采样：`1/150 (0.7%) → 10 → 50 → 100 → 140 → 150/150`，每 20 秒一跳，真实推进。

**配套约定（跨端展示更重要）**：取不到的字段填 **`-1.0`，绝不填 `0`** ——
`0%` 利用率、`0W` 功耗是**合法实测值**，必须与"没测到"可区分；前端把 `< 0` 渲染成 `—`。
反例：笔记本 GPU 不报 `power.limit` → 三级回退
（`power.limit` → `power.default_limit` → `enforced.power.limit`）后仍取不到，
就给**明确文本**"本机 GPU 不报功耗上限(笔记本)"，而不是留 `None`（前端会渲染成空/undefined）。
