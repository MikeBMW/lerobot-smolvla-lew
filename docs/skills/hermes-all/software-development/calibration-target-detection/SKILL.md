# 标定靶标检测 — 从「检不出」到亚像素（实测配方）

## When to Use
- 手眼/相机标定要检圆点阵列或棋盘格，`findCirclesGrid` / `findChessboardCorners` 反复返回失败
- 检出了点数但拟合不出标准形状，或 `solvePnP` 重投影 rmse 异常偏大（几 px 以上）
- 需要在设备被常驻进程占用时，抓一帧高分辨率标定图

## 排查顺序（固定按此序，别跳）
各根因的表现完全一样（检出 0），按序 0→4 一次定位，别乱调参：
0. **板型** — 先确认是哪一种靶标，别拿预设阵列硬套（见下「第 0 步」）
1. **分辨率** — 先量圆点像素直径。<12px 基本没戏；低分辨率下**任何前处理都救不回来**（放大 3/5/8/12 倍都试过）。同一块板在 640×480（~10px）检出 0，切到 1280×720（~29px）一次命中
2. **极性** — `findCirclesGrid` 找的是**暗斑**。白点黑底（或白底黑点）与检测器预期相反时必然失败 ⇒ 先 `cv2.bitwise_not()`
3. **阵列模式** — 对称 `SYMMETRIC_GRID` vs **非对称** `ASYMMETRIC_GRID`（奇偶行错半格）。用错模式 = 检出 0，且同一块板只有一种模式对
4. **裁剪框** — 放大检测时框是否真的框住整块板（四周留 ~60px 余量）

## 第 0 步: 先读板型, 再选检测器 (实测: 预设阵列能把整轮拖死)
现场那块板**不一定是**"4×5 非对称圆点"。实测遇到的是一块**规则对称、密集的圆点阵列(约 5×5)**,
板旁边还有带腰形孔的浅色安装支架、键盘、PCB、托盘(全是假阳性来源)。
板型不对时, 下面 1→4 全试一遍(裁剪/放大 2.2×/反相/网格 3×3~8×8)**一个都检不出**, 而失败现象与"分辨率不够"一模一样 ⇒ 容易往错方向查两小时。
做法(30 秒): 裁板区 → **放大 3×** → 交给 VLM 读四件事: **①对称/非对称 ②行×列 ③圆点像素直径
④深底亮点还是浅底暗点** ⇒ 再决定 `SYMMETRIC`/`ASYMMETRIC`、要不要反相、要不要先放大。
- 规则对称阵列 ⇒ `SYMMETRIC_GRID`(行×列); **奇偶行错半格**才是 `ASYMMETRIC_GRID`(物点顺序也不同)。
- 大倾角(实测 40~60°)会把行距压扁 ⇒ 对称密集阵列在大倾角下更难, **先把板转正再采**(现场就能做)。

## 检测链（已验证：20/20 点，rmse 0.298px）
```bash
gui-venv311/bin/python <skill>/scripts/detect_circle_grid.py --image frame.png --box 453 708 448 608
gui-venv311/bin/python <skill>/scripts/detect_circle_grid.py --image frame.png --box ... --depth d.npy   # 顺带自标定间距
```
1. 裁板区 → 2. `resize(fx=2.2, fy=2.2, INTER_CUBIC)` → 3. 灰度 + **反相** →
4. `findCirclesGrid(inv, (4,5), CALIB_CB_ASYMMETRIC_GRID)` → 5. **映射回全图坐标** `pts/S + [x0,y0]`

多种前处理会命中同一检测，可互相印证（任选其一）：原图+反相 / CLAHE+反相 / CLAHE+自适应二值逆。

## 三个会让整轮数据作废的坑
1. **裁剪/放大后的点直接配全图内参** —— 主点错位一整个裁剪偏移量（实测 153px）⇒ 重投影 rmse 从 **0.298px 恶化到 5.5px**，解出的间距/平移整体错 **2 倍**（并会连带把尺寸解成 2 倍大）。检出后立刻映射回全图坐标再配 K，或把 K 的 `cx/cy` 减掉裁剪原点。**rmse 一异常，先查是不是同一个坐标系。**
2. **自己凑的点阵不能当天生对应关系** —— 连通域/晶格投票能凑出「间距一致到 45~48px」的漂亮点集，却拟合不出任何标准形状（给出 9×11 假 span）⇒ 点集里混了杂点。判据：**强行拟合给不出标准形状（4×5/5×4/2×10…）就回退到 `findCirclesGrid` 给的真顺序**。检出点数对 ≠ 对应关系对。
   ⚠️ **`HoughCircles` 尤其不能单独当对应点来源**：实测在含键盘/PCB/托盘/墙面的画面里检出 **19 个“圆”，仅 10~12 个真在板上**，其余全是静止杂物的假阳性 ⇒ 报“检出 N 个点”毫无意义；必须同时报**拟合出的格型 + 残差**，否则一律按没检出处理。
3. **单位** —— 物点用 mm、位姿用 m 混用 ⇒ 解出的距离整整 ×1000。任何「距离 ×1000」先查单位。

## 非对称阵列的物点顺序（错序 rmse 也不报错）
4×5 `ASYMMETRIC_GRID` 的标准物点：行 `i`(0..4) 列 `j`(0..3) ⇒ `x=(2*j + i%2)*spacing`, `y=i*spacing`, `z=0`。
漏掉「相邻行错半格」时 `findCirclesGrid` 输出与物点不匹配，**但图案近似对称 ⇒ 重投影 rmse 仍然很低**
（实测 0.15~0.44px）⇒ **rmse 抓不到这个错**。只能靠下面的几何判据暴露。

## 判据（宁缺勿假）
- 靶标 `solvePnP` 重投影 **rmse ≤1px** 是**必要不充分**条件（实测 0.298px / max 0.770px）。
  ⚠️ rmse 低 **不等于**解出的几何对：物点顺序错、镜像解、对应关系错都能在低 rmse 下发生。
- **必须再加一条与物理世界对照的独立判据**：靶标已知的物理朝向在目标坐标系下是确定的
  （如标定板平放台面 ⇒ 其法向经 T_target→base 转过去必须 ≈ 竖直）。做法：
  逐视图 `findCirclesGrid` → `solvePnP` → 取 `R_target2cam[:,2]`（板法向）→ 左乘外参的 R →
  算与已知方向的夹角。实测: 正对板的视图 **9.1°/11.3°/15.3°**、斜视角视图 **29.3°/38.8°**。
  读法：小角度 ⇒ 方向对、精度待提高；大角度且集中在斜视角 ⇒ **那些视图的 PnP 法向本身不可靠**
  （板在画面边缘、只能靠全图低倍检出），判精度**只看正对靶标的视图**。
- 板在基座系的一致性（各视图把靶标中心投回 base 系应处处相同）比单帧 rmse 更有说服力 ——
  但它同样只是**自洽**指标，能被一个偏掉的解同时满足 ⇒ 要与上面那条物理判据一起报。
- 多解算方法交叉验证时要报**方法间离散度**，离散大说明数据/对应关系还有问题。

## 靶标物理尺寸未知时：用深度自标定间距
不信标称值也能解，而且能反过来复核标称值：
1. 物点用**单位间距**跑 `solvePnP` → 得单位制下的靶标位姿
2. 板中心在相机系的 z ÷ **该处深度实测值**（每个圆点邻域取深度中位，再对所有点取中位）⇒ 真实间距
3. 用真实间距重跑 PnP，迭代 2~3 次到收敛

实测独立复现出 **19.38mm**（标称 20mm 的 3% 内，互为印证）⇒ 这套自标定可以当**尺寸复核**用。
深度尺度必须实测，不能假定：D405 `get_depth_scale()` = **0.000100 m/unit = 0.1mm/单位**（不是 1mm；读数 4013 = 401mm）。深度图与彩色 align 后可用同一像素索引。

## 相机自己会动时: 靶标升级为「每帧基准」
笔记本/USB 相机(甚至被人碰过的固定相机)不能只标一次 —— 外参一变之前解的全作废。
做法: 每帧 **检板点 → `solvePnP` → 当帧外参** 再投影; 真值带必须打出**该帧重解残差 + 参与点数**,
残差大就是没解出来(**不许把框画上去糊图**)。
- 板的 **base 系 3D** 优先用**已标定过手眼的深度相机实测**(见上「用深度自标定间距」), 不信标称尺寸 ——
  标称值错会让残差假小。
- 板必须**每帧都在视野里**、姿态别太大倾角; 板被挪位就得重测它的 3D 锚。
- 另一条路是让板**随夹爪走**(eye-to-hand): 每张图配**同名 `.json` `{"tcp":[x,y,z,qx,qy,qz,qw]}`,
  内参另跑棋盘格目录 —— `tools/calib_real_cam.py --handeye <目录>` / `--intrinsics <目录>` 就是这个口径。

## 拿高分辨率帧（设备被常驻进程占用时）
```
停守护 → 停节点(kill -9, 确认残留=0) → 1280×720 单次抓帧(彩色+深度+内参+get_depth_scale)
→ 按原配置重启节点 → 重启守护
```
- 一次约 35s，画面中断几秒；多位姿采集就每位姿跑一遍
- **重启节点那步必须 `source /opt/ros/*/setup.bash` + 工作空间 `install/setup.bash`**：非交互 ssh 不 source ⇒ `rclpy` 找不到 ⇒ 相机起不来
- 起完立刻核 `/stats` 的 fps + 日志里的 depth_scale/DDS 行，确认真回来了再往下走
- **换了分辨率就换内参**：720p 与 480p 的 fx/cx 不同（本机 720p 为 fx=655.06/fy=654.08/cx=637.41/cy=357.77），沿用小分辨率 K 会让 rmse 虚高

## 排位姿前先量相机安装偏置（不需要靶标）
深度 RANSAC 拟合台面主平面 → 法向(相机系)；台面水平 ⇒ base 系法向 =(0,0,1)；与 TCP 四元数算出的工具 Z 轴比对 ⇒ 直接得到相机相对工具的偏转。实测某机 相机相对工具**装偏 ≈90°**。

⚠️ **报角度必须写清是哪两个向量的夹角**。这个量测的是【平面法向 vs 相机光轴】，
**不等于**【相机光轴 vs 竖直】—— 后者要再乘上相机外参才能得到。两个数混用（拿去对手眼解出的光轴倾角）
会白查半天。写结论时把两个向量都写出来。

⚠️ **RANSAC 平面只适合做“装在哪种”的定性判据，不能当精度 oracle**：内点数会远超靶标占的像素面积
（实测 1/16 采样下 4000+ 内点 ≈ 7 万像素，而 136mm 板在 450mm 处只 ~2 万像素）⇒ 拟合到的可能是台面或别的面，
给出的角度偏差高达 59°。要精度就用**已知图案的对应点**（圆点/角点 PnP），不用 RANSAC。

**用途**：绕工具自身轴旋转时刀尖在轴上 ⇒ **位置零位移、零碰撞风险**，是间隙很小（台面贴板、上方有横梁）时唯一敢用的姿态变化。但相机装偏多少度，绕轴转 θ 度光轴就跟着偏 θ 度 ⇒ **可用角度只剩靶标视角半宽 `atan(板宽/2 ÷ 距离)`**（135mm 板 @0.39m ⇒ 仅 ~10°）⇒ 旋转幅度必须按这个算，超一点点就丢靶、整轮数据作废。
