# 真实机械臂的自主操作 (闸门 · 慢速 · 中止规则 · 无外部依赖自校)

## When to Use
- 用户说"你可以自主操作机械臂 / 现场我只保证安全 / 你自己采数据 / 自己标定"。
- 要用真实臂产生数据（激励轨迹、位姿-真值配对）、要自校模型、要发起任何真机运动指令。
- 要判断"现在能不能动手"（现场状态不允许时必须能明确说不能，并给出需要谁做什么）。

## 一、闸门 (下发前每条指令都查; 字段名按后端各不同)
**字段级契约坑**: 别凭"应该有这个字段"写判据 —— 先实测后端真正返回的键名。
| 后端 | 返回的键 | 正确判据 |
|---|---|---|
| Orin SDK 直驱桥 (`/status`) | `powerState`(`PowerState.on`) · `operateMode`(`OperateMode.automatic`) · `jointVel` · `jointTorque` · `endInRef` · **没有 `operation_state`** | `"on" in powerState` + `"automatic" in operateMode` + `jointVel` 全 0 |
| ROS2 `/robot_status` | `power_state` · `operation_state` · `has_error` | `power_state=on` + `operation_state=idle` + `has_error=false` |

实测教训: 用 `operation_state` 查 SDK 桥 → 读到空 → 判"非 idle" → **静默拒绝动作**。失败安全，但白跑一轮，
且极易被误读成"机器人没跑/故障"。**闸门不过时要打印出读到的原始字段值**，让"为什么不动"自证。

**授权闸门 (用户 2026-09 定)**: 真机动作的现场授权**只认工位总览页 (8793 `/station`)** —— 助手代发前先在该处取到授权,
**不把聊天里出现的动作词当授权**; 只算目标/演练 (`dry:true`) 不受此限。

## 二、速度与幅度策略 (用户明确纠正过)
- **默认慢速**: 关节运动 `speed=8`（本次用户明确要求"速度要慢一些"，30 太快）。驱动侧 `rt_speed_ratio=0.05`。
- **但"慢"有下限 —— 服务端只等 30s**: `wait_until_idle` 超时即报 `ROBOT_IDLE_TIMEOUT`
  （**动作其实已完成**）。实测 `speed=15` 时 20° 姿态偏转要 >30s ⇒ 必然顶满窗口报假失败;
  改 **`speed=50` 后同样动作 3s 到位**。⇒ 小角度姿态变化用中高速(50); 大位移转移用低速但**超时按距离算**, 别写死。
  踩过的死法: 一下发就重试 —— **运动中重发是真危险**（会把 20° 叠成 40°）。
- 幅度: 关节 ≤2~3°/步（腕部姿态跨度试验才到 ±12°）; 笛卡尔单步 ≤50mm、向下 ≤20mm。
- 每步: 先闸门 → 发指令 → 等静止（`jointVel` 全 0）→ **读真值核对**（不看 `success`）→ 记录。
- 结束: **自动回起始构型**并复核（实测回位偏差 0.000~0.001mm 属正常）。

## 三、中止规则 (硬红线, 命中任一就停手并上报, 不重试、不抢控制)
1. **产线 motion 节点在跑** (`pgrep -af motion`) ⇒ 它会抢控制。只在明确"停线窗口"动手; 用户没说停线就不动。
2. **指令下发后真值没变**（N/N 次读数逐位相同）⇒ 控制权不在我手上。停, 只读核查, 上报。
   ⚠️ 判"真值没变"**别拿执行器日志当证据**: L2 链的日志三行(`目标 <id>: pos=… Δ=…` → `已下发` →
   `ROS: response:`) 写在**响应里只有 `joint_state`、没有 `success/error`** 的前提下，只能证明"发出了"；
   "走没走"必须回读真值(50Hz 录制 head / `/robot/tcp_pose`)与目标比差。两者混用会得出相反结论。
   ⚠️ 手工拖动后马上下发常"没反应": 人拖完臂停在 `drag`, SDK 下发被拒(-18) —— 与"指令没生效"要分开定性。
   ⚠️ **`drag` 的第二种表现是"照收不误但一动不动"**: 服务回执 `success=True`、状态一字不变、位置漂移 0.0mm。
   所以"下发被接受"不能证明能动 —— 每次关键动作前先读 `operation_state`, **必须 `idle` 才继续**。
   ⚠️ **复位状态机(`/state_machine/reset`)之后状态机会回到 `drag`** ⇒ 报"已复位"也别当成能动了, 复位后**再读一次**确认。
   ⚠️ **姿态/换姿不动还要算关节限位**: 读 `ros2 topic echo --once /real_joint_states` 算六轴角度
   (本机 **`/joint_states` 是空的**, 要用 `/real_joint_states` 或 `/robot/joint_states` + `--qos-reliability best_effort`)。
   实测: 手工拖动示教把 **J3 拖到 −169°**(六轴臂 J3 量级 ±170°) ⇒ 朝那侧的换姿被静默拒绝(位置通道却完全正常)。
   **修法 = 换反向绕另一侧(≈360°−Δ)把关节退绕回中位**, 不是加力重发; 两边都顶住就请操作员手动把该关节拖离限位。
3. **位姿在我不知情时变了**（与我上次读到的构型差很多）⇒ 有别的控制源。停, 上报差异数字。
4. **控制器日志里有急停/stop 事件**（`GLOBAL_ESTOP`/「已请求机器人停止」/`INFO_CODE_EVENT 全部停止`）⇒ 现场态未知。停。
5. `has_error=true` 且伴随 `operation_state=moving`: **不要**照 `ROBOT_IDLE_TIMEOUT` 的"假失败"惯性直接重发——
   先看是不是产线在跑/刚急停。`ROBOT_IDLE_TIMEOUT` 只在"上一次同一条长转移已完成"时才可忽略。

上报格式（用户要证据）: ①我上次读到的构型/TCP ②现在的构型/TCP（逐轴数字）③我的指令是否生效（次数统计）
④产线进程与控制器日志原文片段 ⑤当前瞬时状态（速度/电源/模式） ⑥建议谁做什么。**不发任何动作**。

## 四、无外部标定物的自校 (已被验证的路线)
**原则**: 机器人自己的编码器就是 µrad 级真值源 —— 标定不是前提，而是可被自监督替代的一步。
不要因为"没有标定物/相机不稳/别人没给内参"就停下等人。
- **运动学自校** (`tools/selfcal_kinematic.py`, 实测有效): 自主走 N(≥20) 个关节构型（慢速）→ 每步读 (编码器 q, 控制器 TCP)
  → 与自家 URDF `FK(q)` 对比 → 看残差结构:
  - 残差**逐构型向量完全相同**（std < 1e-3 mm）⇒ 不是零位/杆长误差，而是**纯固定偏移** ⇒ 直接拟合一个常量基座偏移即可，
    拟合后残差 0.000mm（本次基线 2.519mm）。产物落 `data/selfcal/kinematic_correction.json`，供 MoveIt/规划与真机同源。
  - 残差随构型变化 ⇒ 才需要拟合关节零位/杆长参数。
  - ⚠️ **可辨识性**: 只在起始构型附近 ±2° 扰动时，基座偏移与工具偏移**不可分离**（设计矩阵条件数 3.9e6，实测腕部 ±12° 仍不可分离）。
    老实采用"常量基座偏移"模型，别硬解 6 参数再把不可信数值写进配置。
  - ⚠️ **采标定位姿时，「旋转角度够大」不等于「可辨识」** —— 两条判据都要看，只看第一条会被骗：
    ① 位姿间旋转角 >10° 的对数 ≥3；
    ② **相对运动的转轴之间夹角中位 >8°**。
    绕单一世界轴转（无论转多少度）⇒ 相对旋转 `R_iᵀR_j` 的转轴恒为 `R_refᵀ·(0,0,1)` ⇒ **恒定**。
    实测 31 对相对旋转的**轴夹角中位 0.0°、最大 0.0°**（单次旋转已达 85° 仍退化）⇒ OpenCV 五种方法
    全给 NaN 或 10⁷mm 级垃圾值。修法：**世界Z偏航 × 世界X倾斜**组合出两条不平行的轴。
    落地：每次解算前先把这两条指标打出来 —— 数据不够格就直报退化，别把 NaN 当结果交出去。
    另：用 `/move_pose` 指定**绝对 TCP 位姿**只改姿态 ⇒ 刀尖位置不变（零位移、零撞板风险），
    是间隙很小时唯一敢用的姿态变化方式。
- **仿真-真机自监督迁移**是零外部真值的主路径（在仿真里造全标注数据训练，真机只做一致性校验）。

## 五、判断"这个传感器能不能用"的取证法 (省掉整轮无效标定)
不要凭"看不见/标不出"下结论，也不要硬试到天黑。用**逐帧曝光/结构稳定性**取证：
- 同一姿态连拍 3 帧 → 若帧间 `std`/饱和占比**稳定**；换姿态后**剧烈变化**（本次实测同姿态 81.8/81.8/81.8 → 跨姿态 81.8→28.6→53.5，差 64.5%）
  ⇒ 相机是**自动曝光**，且光照随臂位姿变化。
- 再做两条结构判据: ①归一化(CLAHE)差分的变化占比 ②NCC 模板匹配峰值与真值相关性。
  本次实测: 差分变化 70%+ 或局部簇乱跳（位移翻倍簇换位置）· NCC 12/12 ≈ 0.84（泛匹配地板）· `corr(TCP.x,u)=+0.034` ⇒ **该相机在当前条件下无法做二维重复定位**。
- 结论要写成"**在现有条件下不可用**（附数字）+ 需要什么条件才可用"，**不写"标定失败"就完事**，也**不要把失败路线写成 workflow**。
- 相机原图/判决等只读接口的字段要实测确认（本次 `/capture_detect` 只是**异步受理**，图要从 `/picture` 另取，判决在 `/last_result`）。

## 六、判断「刀尖下方有没有东西」的取证法 (力监控分步下探)

**别把记录里的工作空间几何值当已验证真值**。plane_z / 板面高度 / 工装高度这类数字可能是台面值、旧值、
或别的位置 —— 只按它算 Δz 判"会不会撞"会给出**两个方向都错**的结论: 误禁一切下降, 或误判贴近了就危险。
**离面距离是三维距离, 不是 Δz。**

`/robot/force_torque`(**wrench: fx fy fz tx ty tz**)是接触的 oracle。别等 `/robot/status` 的力矩报警
—— 那时已经撞上了。自己分步读力、提前判:
1. **基线**: 当前位姿连读 3 次取均值（实测 Fz≈+9.1N = 工具自重 · T≈1.0Nm）。
2. **每步 10mm** 下发（`/move_pose` speed≈25 ⇒ 10mm 约 4s，不顶 30s 窗口），然后**轮询 `/robot/tcp_pose`
   确认到位**（位置<1.5mm）。**`success=False` 只代表等 idle 超时，动作其实执行了；绝不重发。**
3. 到位后读 `/robot/force_torque`，判据: **`|ΔFz| > 5N` 或 `|ΔT| > 2.5Nm` ⇒ 立即停，不再下降**。
4. 每步记一行 `z + F + T` 留档 —— 这就是"我确认过下方是空的"的可交证据。

实测一次 5 步 50mm: ΔFz 最大 **0.76N** / ΔT 最大 **0.49Nm** ⇒ 判定全程无接触，
并**推翻了记录里的板面高度**（说明那条记录不是刀尖脚下的面）；同批数据的手眼解算独立算出
靶标在**刀尖前方 ~260mm** ⇒ 侧前方，与力数据互相印证。
⚠️ **不要指望 `collision_detection` 兜底** —— 它默认 `enabled=false`，撞了不停。
⚠️ 一旦出现接触特征就**不再下降**并上报，不重试。

## 七、留档纪律
- 每次真机动作: 闸门表 + 命令原文 + **动作前后真值** + Δ与理论对比 + 结论 → `~/zmax_data/arm_<事项>_<日期>.md` 与仓库 `docs/patch/`。
- 数据集/产物落 `data/<事项>/`，JSON 里带 `ts`/`n`/原始读数，便于复盘与别人复核。
- 长命令/长脚本一律写 `/tmp/*.sh` 再执行（本环境对巨型内联命令有 hardline 拦截）。

## Pitfalls
| 坑 | 症状 | 修法 |
|---|---|---|
| 闸门字段名想当然 | 静默不动作, 被当成"机器人坏了" | 先实测键名; 不过时打印原始字段值 |
| 产线在跑还发指令 | 抢控制/危险 | `pgrep -af motion` 先查; 无停线窗口就不动 |
| 指令无效仍反复重试 | 白跑 + 风险 | 连续读数相同 ⇒ 判定失权, 停手上报 |
| 残差小就硬解 6 参数 | 数值不可辨识, 写进配置害后面 | 先判残差结构; 常数就用常量偏移 |
| 视觉标定硬试多轮 | 浪费时间, 且易写出"失败流程" | 先做曝光/结构取证, 一次定性 |
| 忘记回安全位 | 臂停在半路 | 结尾统一回起始构型并复核偏差 |
| 下发写显示名而非技能 id | `未知技能 <名>`, 臂纹丝不动 | FIFO 写注册表 `id`(如 `L2.goto_point`); 注册表 `skills` 是**列表**, 逐项取 id/name/ros 先核 |
| 拿执行器日志当"动了"的证据 | 汇报"已下发" 而臂没动 | 响应日志只有 joint_state、无 success/error ⇒ 一律回读真值判 |

## 八、节奏: 一次算完再做, 别逐步试探 (用户抱怨过"太慢了")
- ❌ 反面写法: 发一条动作 → `sleep 9~11s` → 读真值 → 再发下一条。单次动作拖到 60~90s, 现场体感 = "太慢/没反应",
  而且每一步都在赌上一步真落地了。
- ✅ 正确写法: **离线把整条路径/整串动作算完并过守卫** → 一次下发或一次发布 → 只在**关键节点**(起点/终点/每段结束)
  核真值。要连续观测就把真值采样放**后台并行**(线程/一次 `echo` 取全量), 不在下发关键路径上串行 sleep。
- 诊断期的只读探测可以串行(不受此限); 这条针对**下发/执行**路径。
- 用户要的是"一次规划到位 + 一次性证据(段长/绕行比/守卫结论/落地帧)", 不是"每一步请示一次"。
