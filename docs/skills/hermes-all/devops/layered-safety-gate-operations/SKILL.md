# 分层安全闸 · 诊断 + 授权 + 下发反馈

## 慢层大模型: 必须非推理型 + 调用方等待上限 > 真实单轮耗时 (实测铁律)

- 推理型模型把 token 花在 reason_content 上 ⇒ content 空 ⇒ 慢层落"降级不安全" ⇒ **fail-closed 拒掉一切动作**,
  现场现象="点了半天不动"。同一端点实测: `deepseek-flash` 140s/空 ✗ · `deepseek-v4-pro` 141s/空 ✗ ·
  **`deepseek-chat` 135s/有真 JSON ✓**(唯一非推理档)。判据: reason_len==0 且 txt 非空且能解出 JSON。
- **延迟与图片大小无关**(64x64 也要 122s) ⇒ 缩图/降灰度都不提速, 别浪费时间。提速只有: 换非推理档 + 裁决复用窗。
- max_tokens 给小 JSON 500~2000 就够; 9000 会让单轮 >600s, 太小又会被 reasoning 吃光 ⇒ content 空。
- 执行器等裁决的上限必须 **> 单轮耗时 x 重试次数**(慢层 135s x 3 次 ⇒ 等待/复用窗配 600s); 否则慢但正常的轮次
  被判"未给裁决 ⇒ 从严不安全"。

## 物理缺席的相机 = 慢层永久判"关键视角缺失 ⇒ 不安全" (最隐蔽的全拒根因)

- 现象: 裁决 1~2 秒返回且理由含"关键视角缺失/丢帧"(远快于模型耗时) ⇒ **根本没调模型**(本地兜底或复用旧结论)。
- 查法: `ls /dev/video*` 对不上映射(如顶视要 /dev/video4 而机器只有 0~3) ⇒ 相机物理不在位;
  快照接口仍返回**冻结旧帧** ⇒ 拼图混进陈旧格, 模型每轮报"丢帧/缺失"。
- 处置: 可缺席视角从"必须"集合移出 + 拼图剔除, 并在**裁决字段 + 拼图标题**如实写"缺席: xxx";
  剔除后行宽不等, 用 np.pad 补黑再 vstack。**是否接受覆盖降级必须用户/现场定** —— 不擅自放宽关键视角判定。

## When to Use (触发)
现场说「技能/按钮又不好使了」「点了没反应」「怎么半天不动」而设备真的没动; 或下发的动作被拒、
被闸门拦住、同一按键时而能时不能; 或要让点击后"立刻动"(需评估现场一次性授权);
或给带安全闸的按钮写回执/进度反馈时。先分清三种: 「**被拦**」(日志有拒发行) / 「**还在等裁决**」(有意图登记、无受理) / 「**受理了却没走到设备**」
(见 3f: 执行器多实例抢队列 · 命令通道静默卡死) —— 处置完全不同, 第三种最容易被误判成"设备坏了/网络断了"。

适用面: 任何"上层给意图、下层在真动作前做安全裁决"的系统(真机运动、触发类设备、产线 AOI 收口)。
别先查网络/注册表/驱动。

## 1. 否决链: 先定位是哪一层拦的

典型顺序(任一不安全即拒发, **fail-closed**):

```
下发 → 命令通道是否活 → 语义层(慢, 模型裁决) → 反射层(快, 本地判据) → 真设备调用
```

- 每层都要有独立裁决文件(JSON) + 日志行, 否则现场无证可查。
- **被拦时受理行必须点名是哪一层 + 为什么**; 写「通道不可用 或 闸门拒发(见日志)」等于没说,
  现场只会得出"没反应"。分档: 语义层/反射层/通道, 各带一句原因。
- 反射层的判据(亮度、纹理、遮挡)容易因为**输入本身错了**而恒定 unsafe: 画面"有帧且在动"但像素质心不对
  (例如采到无照明的 IR/GREY 那一路, mean≈6/median=0)。**先确认喂进闸门的是真现场那路**,
  设备号/取流按**名称+能力**解析, 不要写死索引(重启后会变)。

## 2. 裁决的时效与 seq: 为什么每条动作都要重新等

- 裁决带时间戳 + **意图序号(intent_seq)**; 执行器每次动作前登记意图(seq+1, desc=本次动作),
  **只接受 seq 匹配的裁决**。**不同动作之间绝不复用** —— 拿上一次的结论放行新动作等于取消闸门;
  但**同一动作**在复用窗内(`VL_REUSE_S`, 本机 300s)可直接复用上次裁决 ⇒ 现场体感是:
  **同方向连按秒发; 一换方向(或隔久了)就要重新等一整轮**。现场说"按了十下只动一次"基本都是这个机制,
  不是故障 —— 先解释机制再谈要不要授权, 别含糊成"闸门抽风"。
- 判"这次为什么要等"直接读裁决行原文: 「等针对该动作的裁决, 上限 Ns · **动作不同**(最近裁决=<上一条动作>)」
  = 换了方向, 得重跑一轮; 出现「**复用** Ns 前同一动作的裁决」= 直接放行。
- 因此"点一下"到"真动"= 语义层为该动作跑完一轮。实测 45~190s(远端模型 29~137s/次 + 偶发空返回重试)。
- 缓冲窗口(保鲜期)只用来描述"结论有多旧", 不能用来跳过本轮。
- **调用方超时上限必须 ≥ 单轮耗时**, 而且**要大于现场实测的最大值**: 设 150s 面对 137~168s 的真实轮次,
  每轮都落「未给出裁决」→ 从严判不安全 → 现场看到莫名其妙的拒发。改 env 默认值后**必须重启该守护进程**才生效。
- 只读诊断: 读两个裁决 JSON(看 `safe/why/risk_level/latency_s/intent_seq/age`) + 尾执行器日志;
  日志有「已把本次动作告知评审」但没有「受理: 已下发」, 且裁决 `intent_seq` 落后 ⇒ **正常在跑, 等即可**。
- 🔴 **一次"回点"= N 段 = N 轮审议, 总时长 ≈ 段数 × 单轮时延**: 多段转移(就地抬升 → 高位横移 → 竖直下降 → 落点)
  每段各自过一次闸 ⇒ 4 段 × 25~30s ≈ 2 分钟起, 而**段与段之间臂是静止的**(正等下一段裁决)。
  现场看到的就是「停在半空不动、也没报错」—— 最容易被判成"卡死/设备坏了"。
  判据(只读, 十几秒出结论): ① 连采独立真值 `~/zmax_data/rokae_sdk/tcp_out/latest.json` 10~20s,
  算**到目标点的距离序列** —— 距离在缩短=在走(只是段间停), 恒定=真停; ② 看**尾日志最后一行**:
  「已把本次动作告知评审 · Δ=…」⇒ 在等下一段裁决, **别重发**; 「受理: ✅ 全部 N 阶段完成」⇒ 走完了;
  停在「已下发 阶段 k/N」而真值不动 ⇒ 才按 3f 查通道。③ 汇报按**段**给时刻表(第 k 段/几点下发/几点到位/距目标 mm),
  否则现场不信"它在走"。
- 🔴 **界面授权窗会被「等裁决」吃掉 —— 这是"点了半天最后什么都没动"的一个独立成因**。
  逐条授权是有限窗(本机 10 分钟), 而一轮裁决最长 300s ⇒ 现场常见的白等 =
  「先授权 → 隔几分钟才点 → 等裁决期间授权到期 → 收口回『🛑 被拦(真动授权): … 等慢层期间被撤销, 本条作废(未下发)』」。
  处置三条: ①先读授权剩余秒数, **剩余 < 单轮等待上限就直接叫现场"先重新授权再点", 别让他干等**;
  ②告诉他**复用窗的截止时刻** = 最近一次该动作裁决时刻 + `VL_REUSE_S`(本机 300s);
  在窗内重新授权后立刻点 = 秒过, 过期则重跑一轮;
  ③汇报把"被授权窗拒绝"与"被裁决判不安全"分开 —— 两者都是零下发, 但一个要重新授权、一个要清场, 处置不同。

## 3. 「点一下立刻动」的唯一正路: 现场一次性授权

- 授权只**跳过语义层**, 反射层照旧强制(遮挡/糊化仍拦)。
- 授权文件字段(示例口径): `{enabled, ts, ts_str, ttl_s, max_uses, used, scope:[技能id…], by:<现场人+理由>, note, revoked_ts}`
  + 同目录一份审计 `*.jsonl`(授权/撤销/每次使用各一行)。
- 铁律: `scope` 逐条列 id **不用通配**; `ttl_s` 与 `max_uses` **同时**设上限;
  - 唯一例外, 且要**同时**满足: 现场要的是"一段时间内别拦"而不是"某几条动作"(原话形如「人在活动区 关闭这个功能」)
    + 实现里有"只越慢层"的那份授权文件(快层仍在) ⇒ 给 **空 scope(=全部) + 短 TTL(≤1 小时) + 有限次数(如 40)** 的版本,
    并当场复述 TTL / 次数 / "还剩什么保护"。它比总闸安全(快层遮挡反射照旧)、比逐条 scope 省事; **能用逐条 scope 就逐条**。
  - ⚠️ **写之前先读旧文件**: 里面常留着上一次的 `scope` 与 `note` —— note 往往直接解释"现场为什么老被拒"
    (如某路相机缺失 ⇒ 每轮 fail-closed 全拒), 闭眼覆盖既丢证据又可能把别人正在用的授权改掉。汇报时旧值一并说清。
  撤销 = `enabled:false` + 写 `revoked_ts`(**撤销永远允许, 不需要授权**);
  **只能由现场人在场时给**(他要能看见现场), 事后把 scope/TTL/次数/理由复述一遍再落盘;
  汇报里必须写明「授权期间语义层不参与判定」+ 它的到期/核销状态。
- ❌ 不要用「放宽 seq 匹配 / 复用最近一次裁决 / 放大保鲜期」换速度 —— 那是拆安全边界, 不是优化。

## 3b. 现场要求「关闭安全」时怎么做(唯一正路)

触发: 现场操作者本人就在机器旁并明确说「关闭安全 / 别拦了 / 我要直接调」。那是他的设备、他在场,
不要空谈风险推回去; 但必须按下面这套做, 否则等于留一个"关了忘了开"的隐雷。

1. **开关做成"运行时文件 + 到期时间"**, 不要改代码绕过、不要加永久 env。执行器每次下发都实时读
   `~/zmax_data/<gate>_off.json = {enabled, ts, until, by, note}`; `until` 一到就**自动恢复 fail-closed**,
   不需要任何人再操作。env 开关只用于一次性手工运行 —— 写进 keepalive/cron 就危险: cron 拉起的新进程
   会静默继承它, 现场再也不可能知道闸门是关着的。
2. **一个 `_disabled()` 判定函数, 必须被两条路径同时尊重**: ①闸门函数 ②"等本次动作裁决"的等待路径。
   只改闸门函数 ⇒ 关闸后**每条动作仍要干等一整轮(上限 300s)**才下发, 现场体感还是"点了不动"。
3. **每次下发把开关状态写进审计日志**: 「安全闸: **已关闭** ⇒ 本条直接放行 (到期 HH:MM:SS · by=… · note=…)」。
   关闸这个动作本身也要可追溯(谁、何时、开到几点)。
4. **回复里逐条说清"还剩什么保护"**, 至少四点: ①停机/复位类指令永远放行(不受闸门拦, 本来如此)
   ②物理急停/示教器属机械层, 不受影响 ③上电/idle/无报警这类前置检查仍在读并记录(只是不再因画面判不安全而拒发)
   ④**如实点出这条通道上被关掉的下游保护**(例如控制器碰撞检测按既有口径就是关的) ⇒ 现在实际保护
   = 控制器限位 + 人在现场。缺了④点就是粉饰。
   ⑤**说清这个开关关掉的是哪几层**: 多数实现里它是**总闸** —— 语义层(慢)与反射层(快)一起停;
   而第 3 节的现场授权只越语义层、反射层仍强制(遮挡/糊化照旧拦)。若现场只是嫌慢,
   **优先给逐条 scope 的现场授权**(保住反射层), 再问他是否真要总闸;
   汇报里别把"关掉的是总闸"说成"只关了慢层" —— 那是两种后果完全不同的说法。
5. **默认设到期**(按调试窗口, 例 4 小时)并给出恢复方式: 一句话恢复 = 删掉那个 JSON(或 `enabled:false`),
   不需要重启。**永远不设永久关闭**。
   - 🔴 **到期是静默的 ⇒ 症状复发时第一件事是读这个文件的 `until`**: 现场说"上次明明关过、今天怎么又拦",
     基本都是旧文件已过期、闸门自动恢复 fail-closed ⇒ 先把 `~/zmax_data/<gate>_off.json` 的 `until` 与当前时刻
     比一下, 别去翻执行器代码、也别重新论证该不该关。现场再要求关 = **写一份全新的文件(新 `until`)**,
     并把**到期时刻当场念给他**(他会拿它当"什么时候又会变慢"的答案)。
   - ✅ **关闸后"在途"的那条计划会自己续上 —— 不要重发**: 等待路径每段都实时读开关(见第 2 条),
     所以正在等裁决的那条计划会直接放行、原样走完。现场催「快去X」时的正确动作 =
     关闸/清障 → 盯**同一条**计划逐段走完(日志逐段「安全闸已关闭 ⇒ 本条直接放行」),
     而不是再点一次或重发 —— 重发会并起第二个计划(见 6b 末条"原地反复升降")。
6. **验证(零动作, 照第 5 节)**: ①import 执行器模块 → 读 `_disabled()` 返回值, 再拿**一条真实下发调用串**
   过闸门函数, 期望"不拦"+ 审计行出现; ②走真链路发一条 `dry:true` 规格, 终端要出现「受理: DRY-RUN(未下发)」
   **且没有审议等待**。这两条过了才算关成功 —— 别拿"我改了代码"当证据。
   现成探针: `scripts/verify_gate_off.py`(把①写成可直接跑的命令行工具; 不改状态、不下发动作)。
7. **闸门开关 ≠ 界面授权**: 页面/面板那层「🔓 授权真动」(带 5 分钟自动失效窗)是独立的一层,
   关安全闸不会替它授权。关完必须提醒现场: 仍要重新两步授权, 否则点击只会落在演练档。
8. **现场把决定权交给你时**(「闸的事你决定」): 这是要你**做决定**, 不是要你再问一遍。判据两条 ——
   ①操作者本人在现场 ②这段时间该闸逐条裁决**本来就是通行结论**(日志全是 risk=low/放行) ⇒ 就给
   **带到期的临时授权**(照 3b 第 1~6 条做), 并写清"为什么敢关"(人在场 + 逐条本就放行 + 到期自动恢复 fail-closed)
   与"还剩什么保护"。反例: 出现过"不安全/看不清"的裁决、或现场无人 ⇒ 不授权, 只给
   "**同方向连按**(复用窗内秒发)"这条退路。授权后**必须自己用执行器判定函数复验一次**再回话。

## 3c. 「点了没反应」的第三种原因: 执行器**位姿读不到**(与闸门无关)

现场说「回到某个示教点/点1 还是不好使」时, 日志若反复出现
`拒绝: 位姿读不到(直读失败且常驻缓存过期)或点位不存在` + `受理: 位姿缓存未就绪` ⇒ **不是闸门, 是执行器拿不到当前 TCP 位姿**,
任何运动技能(含点动)都会被拒。判据链(全只读):
1. `_pose_direct()` 有两条路(见 `tools/l2_daemon.py`): ① ROKAE SDK 直采文件 `~/zmax_data/rokae_sdk/tcp_out/latest.json`
   (要求文件龄 <10s **且位置非全 0**) ② 退回容器里 `ros2 topic echo --once /robot/tcp_pose`。
2. 零副作用判法: `importlib` 加载执行器模块 → 直接调 `_pose_direct()` / `_pose_best()`(返回 src=direct/cache/none),
   这样量到的是**执行器眼里的**位姿, 而不是你自己另开一个订阅者。
3. 🔴 两条路都可能**静默失效**, 都踩过:
   - SDK 会话陈旧时 `robot.posture()` **返回全 0 而不抛异常** ⇒ 采样器把它当成功写进 latest.json,
     执行器判"位置全 0"无效 ⇒ 拒发一切动作; 而采样器因为"没异常"永不重连(实测容器日志里 读失败 0 条)。
     修法(已落在 `~/zmax_data/rokae_sdk/tcp_direct_sampler.py`): 把全 0 当读失败 raise ⇒ 触发既有的".每 5 次失败重连"路径。
   - DDS 话题的发布者**端点已过期**: 老订阅者(长连的录制器)还在收 5Hz 真值, 但**任何新订阅者 0 帧**
     ⇒ `ros2 topic echo --once` 拿不到 → 执行器的第二路兜底形同虚设。别用"录制器还在收"证明"话题是好的"。
4. 先看网络: `ip -br addr` —— **产线网卡(USB 网口)一不在位, .66/.23/.23.160 全不可达**, SDK 直连报
   `RuntimeError: network: network connection`, DDS 也只剩本机缓存值(实测位置值恒定 + 容器时标是 UTC, 别把它当新鲜)。
   这条判据一次就能把"按钮坏了"与"现场网络断了"分开。
5. 页面侧要**如实分级回执**: 执行器已收到·在等裁决 ≠ 已下发。定式: `/ctl/move` 回执加 `pending` 字段 +
   只读 `GET /ctl/log?n=` 给页面追日志尾, 页面每 5s 追到 `受理:`/`🛑 被拦`/`⇒ 拒发` 那一行原文为止(上限 = 闸门 300s + 余量)。
6. **绕对点位技能的按钮**: 点位锁在技能定义里(`point_locked` + 示教点 JSON), 页面只送 `{"skill": id}`;
   手动控制白名单要按"无数字参数"的技能单独收(本机 `_CTL_ABS_SKILLS`) —— 只把它塞进 d_mm 白名单会直接报"不在白名单里"。
   **加一个新技能按钮 = 三步, 少一步就是"点了没反应"**:
   ① 页面 HTML 加按钮 + JS 函数(抄已有那套: 写 `/ctl/move` → 未授权只演练 → 追 `/ctl/log` 到受理/拒发行);
   ② 服务端白名单加技能 id(带数字参数的表 / 无参数的表, 选错 = 拒);
   ③ **重启承载该接口的服务**(白名单在代码里, 不是热读)。
   ⚠️ 先确认**哪个文件是页面真源**: 服务端常按 mtime **热读**一个 HTML 文件, 而代码里另有一份**内嵌死码**页面 ——
   改错文件的现象就是"改了但页面上没有"。判据: `curl -s :<port>/<page> | grep -c '<新按钮文字>'`(改完必须 >0),
   再数 `<div`/`</div>` 平衡 + 抽内联 `<script>` 喂 `node --check`(页面 JS 语法错 = 整页白屏; 长连接画面又让
   浏览器打不开页面, 所以只能静态验)。
   **零动作验技能 id/参数对不对**: 走 `dry` 空跑, 执行器会把**将要真发的字节**原样打出来
   (`DRY-RUN <skill> → ros2 service call <服务> <接口> "{...}"`) ⇒ 用它核对技能 id、服务名、量纲与
   **语义方向**(例: 夹爪 `target_pos: 0`=合 / `1000`=张 —— 按钮文案与它写反了现场会夹坏件)。
   🔴 **同一个 dry 空跑还要用来查"字段有没有被中间层吞掉"**: 把调用方发的 payload 与 dry 打印的字节
   **逐字段 diff** —— 服务端代理常只转发一份**白名单字段**, 放行/豁免类字段(如"允许抬升 Nmm")会被**静默丢弃**,
   现场现象 = 「我说了动、臂一步不动」而且日志里只有拒发行。判据: payload 里有 `X`、dry 打印里没有 `X` ⇒ 是代理吞的,
   **别去改执行器判定**。绕法优先改**几何**而不是加字段(见下条)。
   - **多段计划的"抬升量"闸门是相对"计划起点"判的**: 目标点本身比起点高时, 相对抬升必然超限 ⇒ 别急着开豁免字段;
     先**降横移净空重注册**该技能(`--traverse-dz 30` 之类; **注册表热读**, 不用重启执行器) ⇒ 最高点 = 点位+30mm,
     抬升 = (点位z − 起点z) + 30, 常常自动过闸。改完**必须重新 dry 空跑**确认新的段数与目标 z。
     同一闸门对**单段**下发只警告不拦、对**多段**才拒发 ⇒ 单段能过不代表多段能过。
   📎 按钮工程的完整定式(三处同口径 · 服务端判据驱动绿/灰 · 一行均分布局与几何取证 ·
   「点了没反应」读日志梯队 · 可用性上限 vs 防撞红线 · 四元数分量数体检验收)见
   `references/console-button-engineering.md`。

## 3d. 授权必须做成「单一真源 + 单调 epoch」, 并在**下发收口**强制

现场问「我都取消授权了, 设备怎么还在动」时, 把授权只做在界面上/某个服务进程的内存里就是**假闸门**。
三条并存的漏洞(实测):
1. **会动的路不止一条**: 除了那个页面, 还有一堆脚本/GUI/自动流程直接写执行器队列
   (`grep -rl <队列文件> tools/` 常是十几个文件) —— 授权只活在一个进程的内存里, 这些路径完全绕开它。
2. **执行器下发前不校验授权** ⇒ 点授权 → 命令排队等语义层(上限 300s) → 期间人点撚销 → 照样下发。
3. 已经交给设备的慢速动作(几十秒才到位)**不会因为点撚销就停** —— 用户看到的"还在动"就是它。

改法(照搬):
- 授权状态**落文件做单一真源**(本机 `tools/ctl_auth.py` → `~/zmax_data/ctl_auth.json`): `armed = until>now`
  (到期自动失效, 无人操作也安全) + **单调 epoch**(每次授权/撚销都 +1)。界面与执行器读同一份。
- 界面写队列的命令**带上签发时的 epoch**; 执行器在**所有下发收口**校验: ①此刻必须有授权(不是"签发时有")
  ②命令 epoch 不旧于当前(撚销即作废) ③**等裁决期间每一步复核**, 一撚立即作废本条。
  收口往往不止一处: 运动 / 服务步(力控) / 夹爪 三条路都要堵, 只堵一条等于没堵。
- **带外叫停已在途动作**: 撚销只拦新命令; 已下发的要靠主动停止服务(本机 `/robot_stop` = `std_srvs/srv/Trigger`,
  实测 `success=True … 'ec': 0` —— 它内部的 `rt_stopMove` 子步会回"非实时模式"异常, 不影响 stop 生效)。
  写一个**独立常驻小进程**轮询授权文件: 一旦"epoch+1 且未授权" = 有人**显式撚销** ⇒ 若最近 N 分钟有
  真下发留痕(执行器每次过闸后写一份 `<skill, ts, epoch>` JSON) ⇒ 立即调停止服务, 全程审计。
  (**自然到期不 bump epoch ⇒ 不叫停**, 只记录 —— 否则会每 5 分钟无意停一次。)
- 真源缺失时执行器 **fail-closed 一律拒发**; 停/复位类白名单永远放行(闸门不许挡急停)。
- 界面要**如实分三种情况回话**: 撤销后"已对在途动作下达停止" / "近 N 分钟无已下发动作, 无需叫停" /
  "已交给设备的动作收不回来, 只能等它走完或按急停"。只说一句"未授权了", 现场仍会判"闸门没用"。

**三条取证缺一不可**(缺一条现场就当没修):
① 未授权 + 界面带真动标志点按钮 → HTTP 403 **且执行器日志零新增行**;
② **绕过界面**直接往队列写一条真动命令 → 执行器回「🛑 被拦(<授权层名>): … 拒发」(臂零位移);
③ 授权 → 写一条真动命令 → 让它进入"等裁决" → 点撚销 → 1s 内日志出现"本条立即作废(未下发)"
   且 `grep -c 已下发` = 0, 同时叫停服务日志出现 `success`。

## 3e. 代发边界: 什么时候我可以替现场下发

判据三条**同时**成立才代发: ① 该点位**不是**现场判危险的新点位(是已现场确认过的安全位, 如已录的准备点)
② **已授权**(授权窗内; 先读一次剩余秒数) ③ **用户明确要动**(原话形如「已经授权, 动啊」)。
三条齐 ⇒ 发**页面同一个技能 / 同一个 `/ctl/move` 口径**(不另开通道、不自己拼坐标), 发完只读盯,
逐段报 `已下发 阶段 N/M` → `✅ 到位 · 真值偏差 N.Nmm`(日志原文) + 方向/行程/偏差。
**缺任一条就不发**: 危险点/新点位永远是他先做我先看(连演练也别抢发); **他正在手动点动/微调时一律不发**
(哪怕刚说过"动"); 他只抱怨"慢/不动"而没让你发时, 先解释机制或给授权入口, 不要自己动手。

## 3f. 「已下发」但设备一步不动: 执行器**多实例抢队列** + 命令通道**静默卡死**

第四类「点了没反应」, 与闸门/授权/位姿都无关。前提认知: **受理成功 ≠ 调用发生**。

- 🔴 「受理: 已下发」只证明命令被那个进程收下了, **不证明它走到了设备**。真下发的硬证据是日志里那条
  **服务调用输出**(`ROS: requester: making request: …TargetPose…` / `DRY-RUN <skill> → ros2 service call …`)。
  判法: 取日志里**最后一条该行的时刻**, 与现在比 —— 若差了几分钟以上、而期间日志明明排着一堆「已下发」,
  ⇒ 命令全卡在受理之后, 设备从未收到(现场体感正是"点了一小时什么都没动")。
- **一条 `waiting for service to become available...` 就能把常驻命令通道永久卡死**: 服务端没就绪时
  `ros2` 客户端会**无限等**, 而通道是"一条长连 stdin 循环" ⇒ 这条命令占住循环, 后面的技能全在通道里排队,
  却仍会被逐条记成「已下发」。这是通道架构的固有失效模式, 不是网络抖动、不用去查网线。
- **先数实例**: `pgrep -af "<执行器脚本>"` 必须只有 **1** 个。多实例(实测同时 3 个)在抢**同一个队列文件**,
  命令被某个已卡死的实例吃掉、另一个只负责打日志 ⇒ 症状与单实例卡死一样, 而重启一次只解决一半
  (保活脚本/cron 很快又拉起一个, 除非加了锁)。
- **排除法(证明"不是设备拒绝")**: 同一条 SDK 会话上读控制器报警日志 —— 无新报警、**也无新警告**
  ⇒ 请求根本没到控制器。对比: 真被控制器拒会留下编号 + 物理量 + 阈值的记录。
- **修复顺序**:
  ① 清掉**全部**实例 —— 用现成的一键全停脚本, 不要手敲 `pkill -f <模式串>`(会匹配到执行它的 shell, 自杀);
  ② 用**保活脚本**拉起(它带启动前 ssh 探针, 避免"通道建完即死"变僵尸);
  ③ **根因加锁**: 执行器入口做**单实例锁** —— `flock(锁文件, LOCK_EX|LOCK_NB)`; 拿不到锁就读出持有者 pid、
     `SIGTERM` 请退(最多等 3s 再 `SIGKILL`)、然后接管; 规则是**"新实例赢"**; 锁 fd **故意不关**(关了锁就释放);
     取不到锁只告警、不阻塞启动。锁防得住多实例, 防不住通道卡死 ⇒ **两条都要**。
- **验证: 先最小代价探针, 再上真目标量**。发一条最小步进的运动(本机 `L2.lower d_mm=1`, 参数下界 1mm),
  三件一起看 —— ①日志出现**新的**服务调用行 ②真值位姿**真的动了那么一点**(1mm 也读得出)
  ③控制器无新报警。三条齐 ⇒ 通道真通, 再发真正的目标量。别拿"再试一次大动作"当探针。
- ⚠️ **排障期间每条下发都要核验效果**: 回读"服务调用行有没有新增" + "真值有没有朝目标走";
  只把「已下发」转达给现场 = 下一条仍然白下, 而他会以为在推进。
- 关掉闸门(3b)之后这条判据更干净: 日志里不再有审议等待, 只有「安全闸已关闭 ⇒ 直接放行」+ 服务调用行
  ⇒ **没有服务调用行就一定不是裁决问题**, 别再往闸门方向查。

## 4. 下发反馈: 让点击"有感觉"(现场最常抱怨的一条)

- **立即回执 + 后台补回**: 点击后马上回「✓ 已下发」,**不要死等回读**(一个回执动辄十几~上百秒,
  等待上限设几秒 ⇒ 界面永远显示「未回读」= 用户判定"点了没用")。回执/原因由后台轮询日志补打到
  **用户看得见的那块终端**, 并同步一份到主控制台底部日志栏。
- **等的时候要说话**: 每 **15s** 一行「⏳ 已等 Ns · 原因」, 原因要能区分:
  ① 评审正在为本次动作重跑(带 本动作 seq / 最近裁决 seq / 上轮多久前 / 单轮耗时范围)
  ② 本次裁决已到, 正在下发/等设备回执。等待上限 = 闸门等待上限 + 余量(例: 300s → 320s)。
- 点击那一刻先打一行**闸门现状**(两层 safe + 帧龄 + 原因) —— 被拦时它能当解释用。
- 被拦时补一行:「↑ 这一条就是「没动」的原因」+ 现状。
- ⚠️ 读日志增量时**偏移量口径要统一**: 若函数吃的是**字节偏移**(`os.path.getsize(log)`),
  传行数会把历史结果行(如 `受理:`)当新行读回来 → 自测里**假成功**; 判"真完成"只认结果行。
    两条同族坑: ① 执行器日志里混有二进制字节 ⇒ `grep` 只回一句 `binary file matches`、什么都看不到, 一律加 `-a`;
    ② **别用时间戳串(`HH:MM:SS`)过滤"只看新的"** —— 日志是跨天累积的, 昨天同一格式的行比较起来同样"满足 ≥ since",
    会把**上一轮的结局**当成这一轮的终态(实测据此误报过"被拦", 而当时计划正在跑); 判新行只认"下发前记下的字节偏移或行数"。
- 反馈文案别用自报式「已发送」, 要带**设备侧原始行**(可复制)。
- ⚡ **面板填的速度可能被"技能级限速"截掉** ⇒ 现场抱怨"速度慢"时先比对**日志里实际下发的 `speed NNN`**
  与面板值(两者不等 ⇒ 是技能字段截的, 本机 `speed_max`, 例: 面板填 200 实际发 150), 再去改那个数字 ——
  不要去调控制器/驱动。**技能定义(注册表)是热读的**: 改完**下一条真实下发即生效, 不必重启执行器** ——
  复核口诀 = 改完盯下一条下发的 `speed NNN`(实测改完几十秒后的请求里就是新值)。

## 5. 零副作用验证(不动真设备)

1. **过闸自检**: import 执行器模块, 直接调它的闸门函数(`_gate_blocks(<真实调用串>)`) → False/True + 原因串。
2. **空跑规格**: 走真链路(FIFO→受理→回读→界面)但只算目标不下发(如 `{"skill": ..., "dry": true}`),
   终端要依次出现「已下发 / 目标与增量 / DRY-RUN / 受理」才算整链通。
3. **界面侧离屏起真类**: `QT_QPA_PLATFORM=offscreen` 下 import 真模块、实例化真对话框/面板类,
   调真方法(读闸门状态、模拟"已等 17s"调一次轮询), 不需要桌面/不弹窗。
4. 改完代码**重启对应进程**(GUI/守护)再验 —— 已 import 的旧模块不会自己更新。

## 6b. 现场反例与读法 (每条都被判过"没动")

1. **授权状态的历史包袱: 曾经只存在服务进程内存里 ⇒ 重启承载它的服务 = 授权失效**(现场现象: 刚授权完,
   点方向键「不动」, 复核 `auth.armed=false, ip=""`)。⇒ 改完流服务/任何承载授权的进程后**要复核授权状态**;
   把它落成**文件单一真源 + epoch**(见 3d)之后, 重启不再清授权(文件在、未到期就仍 armed),
   所以**不要**再无脑让现场重新授权 —— 先读一次授权状态再决定怎么回话。
   恢复(等价于页面两步授权, 源 IP 必须与被授权页面一致 —— 连本机 LAN IP 才会用该源地址):
   `curl -X POST -d '{"on":true,...}' http://<本机LAN_IP>:8793/ctl/arm`; 撚销同理 `{"on":false}`。
2. **判"动了没"只看真值采样 —— 但采样窗口必须盖住动作结束**。
   - 只看真值(TCP/关节逐点采样), 不看 `success`、不看日志「已下发」、不看「到位 0.0mm」这类自报。✅ 这条一直成立。
   - ❌ 但**采样太早会得出反向错判**: 驱动的 `success=True` 只代表服务端受理完成, 慢速单次动作(`speed=8`)实测
     十几~几十秒才停; 在回执后 60~80s 采样仍见位姿一位未变, 据此报过"控制器回成功却没动" ——
     之后同一目标位置(= 起点 + 10mm)出现在读数里, 说明动作其实执行了, 那条结论是错的、必须显式作废。
   - 纪律: 采样要**持续到出现目标值或跨过整轮超时**(单次慢动作至少看 60~90s 再回读一次), 过了窗口才允许说"没动";
     之前基于早采样发出去的结论, 要在回复里明说"作废", 别让现场拿着错结论往下追。
   - ⚠️ 这类机器上时钟会被 NTP 回拨(实测小时级回跳; 驱动侧 ROS `stamp` 可差 ~2 天) ⇒
     **判事件顺序用文件追加顺序, 不用时间戳; 判新鲜度用帧龄(now − ts), 不用绝对时刻**。
     日志里出现"未来时间戳"的行 = 写入时时钟曾前跳, 不代表它在文件里排得更后。
3. **三查(上电/急停/碰撞)必须读"当下还活着的那条路"; 缓存 JSON 一律不作数 —— 但"驱动 topic"本身也可能是死的**。
   实测两代死法, 都要能认出来: ①缓存 `robot_status.json` 帧龄 87381s(>24h) —— 它只说明"上次谁写过";
   ②该 topic 的**发布者也不再通告端点** ⇒ 任何新订阅者 0 帧(`ros2 topic echo --once` 拿不到),
   而**位姿那条直连控制器会话一直新鲜** ⇒ 三查改走与位姿**同源**的那条路读 SDK 原生状态
   (`powerState / operationState / operateMode`), 由采样器顺带写一份 `state.json`(2s 一刷),
   页面按 `ts` 算帧龄; 直连也不可用时才退回缓存, **并如实标成旧值**(不许把小时级旧值当"当前无报警")。
   判据: `state.json` 的 mtime 与 `date` 差 <5s = 活; 别用"某个长连老订阅者还在收"证明一条话题是活的。
   报警类真值见第 7 条。

7. **事故/报警的真值 = 控制器自己的报警日志, 不是任何推测**。日志给到 编号+时刻+物理量+阈值, 一次说清
   "谁在什么时刻撞了什么、撞的是哪个关节"(例: 「检测到碰撞，关节传动力矩超限！触发柔顺停止。
   2轴 101.024243 Nm > 限定 101.000000 Nm」+「RSC检测到关节[2]碰撞力超限，触发安全停止」)。
   读法(只读·零下发): 与位姿同一条 SDK 会话上 `queryControllerLog(N, {LogInfoLevel.error/warning}, {})`;
   现成探针 `tools/rokae/dump_controller_log.py`。页面/汇报里"急停/碰撞"按**报警时刻的年龄**分级:
   3 分钟内的当"当前"(拦得住动作), 更早的只当历史(「上次碰撞 07:55 关节2(安全停止)」) ——
   既不能把历史当现在, 也不能因为"当前无报警"就把历史抹掉(现场要的是"每一次"都留痕)。
   📎 死源/活源怎么分辨、怎么把显示接到活路(含页面字段映射与"一行状态"契约)见
   `references/status-source-forensics.md`。
   🗂 **"每一次都留痕"要落成自动台账, 不靠人记**: 从控制器报警日志自动识别碰撞条目(力矩超限码 + RSC 超限码),
   ±N 秒配对同一次事件只留一行; **事件当时的位姿只在"事件后 N 秒内首次看到"才采**(设备触发保护后会停住 ⇒
   那时读数 ≈ 事件点), 采不到就如实写"未采到", 倒序落一份原子写的 JSON; 展示挂在页面同栏的列表卡上
   (形态约定见 `user-facing-dashboard-delivery`)。上游日志缓存只有最近十几条 ⇒ 老事件靠落盘文档留档。
   📎 **撞后处置顺序**(停执行器 → 主动停设备 → 撤授权 → 取证 → 落档)与台账口径见
   `references/incident-and-alarm-ledger.md`。
4. **授权与通道都正常时, 下一步是去找慢层的"拒发"行**(最容易被漏掉的一步)。
   - 判据链: `auth.armed=true` + 点击记录 `dry=false` + 真值位姿不变 ⇒ **先按 3f 排除"受理了却没走到设备"**
     (最后一条服务调用行的时间 vs 现在 · 实例数必须 = 1 · 控制器无新报警) —— 确认通道真发出去了, 才轮到这个分支 ⇒ 去执行器日志找
     ⚠️ 别用"位姿没变"排除通道问题: 通道死掉时位姿同样一丝不变, 两者现象完全一样。
     「🛑 被拦(慢层·VL 判断): **不安全**(risk=… · <裁决时刻> 裁决) … ⇒ 拒发」这一行, 它带风险等级 + 危害列表原文。
   - **逐条**把危害读出来, 并把每条翻译成现场能做的一个动作(「人臂伸进围栏内工作台上方」→ 人退到围栏外;
     「全局相机被近距人脸/身体遮挡」→ 人别站在该视角正前方)。只回一句"不安全"= 等于没答复。
   - 同时给反证: 真值位姿全程不变 = "被拒没发", 不是"发了不动" —— 两者的处理完全不同。
5. **裁决输入里有一路死源 ⇒ 每轮都带坏图, 永久抬高拒发率**。
   - 语义层的输入是多路拼图(工具相机/全局/顶视/深度…), 任一路停更(实测深度路死在 26.6h 前那一帧)
     都会持续出现在裁决画面里, 每轮被判「画面异常/伪彩混乱/时间戳与其他画面不同步」⇒ 拉高拒发率。
   - 体检: 读每路状态里的 `age_s` / `stalled` / `dead` / `frames_served`; `dead=true`、`frames_served` 不增长、
     `age_s` 到小时级 ⇒ 那一路要修, 别用"其它几路正常"放过。
   - 修那一路往往要重启承载它的服务 ⇒ 会触发第 1 条(授权失效), 修完让现场重新两步授权。
   - ⚠️ **“设备整路缺失”比“帧停更”更硬, 症状是“全部动作都被拒”**: 相机根本没枚举到
     (`lsusb` 里就没有那台设备 · 设备解析脚本输出 `-1` · 页面那格恒 `无帧`) ⇒ 拼图里是**空白格**,
     语义层每轮都写「关键<某视角>画面缺失, 无法确认动作路径无侵入」⇒ fail-closed ⇒ 不只
     某一类动作, 是**所有**运动全被拒(现场会当成“闸门/机器坏了”)。判据一次定性: 列 USB 设备 +
     跑一次相机解析; 处理只有两条路 —— **把设备插回**(换口/供电/换线) 或 按 3b 关闸,
     **不要去调闸门阈值/保鲜期**。
6. **防抖规则会让现场觉得"时好时坏"**: 有的实现里"同一动作相邻两轮结论不一致(上轮原始=安全) ⇒ 从严当不安全"。
   ⇒ 现场看到"刚才还能动、现在不动了"不是随机故障; 解释时要带上这条规则, 并给出稳定通过的判据
   (清场后连续两轮都 safe, 或对这一段用现场一次性授权)。

**「机器在原地反复升降」= 同一"回点"技能被重复下发, 不是循环/自走。** 多段回点技能的结构是
①就地抬 50mm(相对) ②高位平移到目标正上方(绝对) ③垂直下落(绝对); 臂**已经在目标正上方**时,
第②段的目标就是当前位置 ⇒ Δ=0 空段不下发 ⇒ 现场看到的运动只有"抬 50 → 落 50"= 原地上下, 连点 N 次 = N 遍。
判据(只读): 执行器日志里**数计划** —— 一个完整计划是一对 `已下发 阶段 1/N` … `受理: ✅ 全部 N 阶段完成`,
数出几对就是下发了几次(`grep -a -c '已下发 阶段 1/'` 对 `grep -a -c '全部 3 阶段完成'`);
再用 `GET /ctl/status` 的 `last_cmd` 看是不是同一点位技能、来源是不是同一个按钮。
⇒ 汇报要把"第几次点击 = 第几个计划"对齐给现场, 别只说"动过了"; 也**别把现场自己的重复点击当成执行器自走/死循环**去查
(慢层复用窗内秒过时, 连点会连着起好几个计划)。

## 7. 「断点打不中」/ 想看下发链: 先定执行发生在哪个进程, 别为看日志改执行器

现场问「我在跑 L5 / 点了 MoveIt 节点, 为什么断点进不去」时, 按这个顺序答, 不要先怀疑调试器:

- **上层节点逻辑 ≠ 执行器**。画布/编排节点里的实现常常只做「构造 + 探针」(三查 / plan / 读状态),
  **一行下发调用都没有**; 真下发在**常驻执行器进程**里: 队列(FIFO) → 执行器 → `ros2 service call …`。
  先证伪路径: `grep -rn "\.move_pose(\|move_pose(" src/ tools/` 看这条链到底调没调那个函数, 再谈断点。
- **断点只在被调试的那个进程里生效**。IDE 的调试会话是它自己新起的进程, 与常驻执行器不是同一个 pid。
  判法: `pgrep -af <执行器脚本>` 取真实 pid + 启动时刻; 想断就 attach-by-PID 到它。
- 🔴 **别把断点留在'可能正在动'的真实执行器里** —— 断在那 = 暂停下发。只在设备静止时挂/停, 或干脆不用断点。
- 🔴 **不要为了看日志去改执行器源码**: 执行器常带热加载(`maybe_reload`), 存盘可能触发重载 ⇒ 现场在跑的时候
  等于动生产进程。零侵入定式 = **只读追日志镜像**: tail 执行器日志 → 解析 `ros2 service call <服务> <接口>` 行
  → 追加落 JSONL(时刻 / 服务 / 接口 / 技能名 / 是否 DRY-RUN), **不写队列、不碰进程、不改判据**(实测工具:
  `tools/l2_dispatch_watch.py`)。这比断点更适合现场: 不暂停执行。
- 镜像必须**同时解析新旧措辞**, 并把每行归类成 `pending(目标) / verdict(放行·否决·已关闭) / dispatch(已下发) / accept(受理)`:
  执行器日志文案换过之后, 只匹配旧关键词(如 `ros2 service call`)的镜像会**一条都抓不到** —— 现场明明在动, 镜像却恒 0 条。
  判据: 镜像条数为 0 时**先怀疑解析词**, 从现网日志里搜出真实动词再改(用 `search_files`), 别急着说"没下发";
  改完**要让镜像进程重启**(已 import 的旧模块不会自己更新), 再复验它抓得到新动作。
- **"这段时间到底有没有下发"的零侵入判据(三件一起看)**: ①队列文件(FIFO)的 mtime ②执行器日志最后一行时刻
  ③日志里的 `受理: DRY-RUN(未下发)` / `已下发` 行。三者都停在同一个旧时刻 ⇒ 那段时间**根本没有下发到执行器**,
  现场说"我点了"也就不是执行链的问题 —— 结论要这么给, 别含糊成"可能是网络"。
- **同源调用点要分清**: 同一个执行器类可能只被**脚本**直接 import(跑那些脚本时断点会命中), 而生产路径走
  「队列 + 服务」。汇报里必须写明"哪条路径命中断点、哪条不会", 否则现场会拿调试脚本跑通当成生产链也通。
- **三类证据凑齐再回话**: 真实执行器 pid+启动时刻 · 队列文件 mtime · 执行器日志尾。缺一条就别下结论。

## 6. 汇报口径(给现场工程师)

按**时刻表**给证据, 一行一步: 点击时刻 → 裁决时刻(耗时/结论) → 下发时刻 → 设备回执时刻,
再给出「点击到真动 = N 秒」这个总数, 并说明这段等待是设计还是故障。
把"被拦"与"在等"分开说。没跑通就说没跑通, 不要拿"应该有动作"当结论。
