# 机械臂末端位姿路径规划 (只规划 · 不下发)

## When to Use
- 用户说「规划一条路径抓起 X」「**先不要发出真实移动指令**, 你只要规划路径, 并把路径画到场景中」。
- 要复算/核对示教抓取点是否可达、会不会被既有守卫挡住。
- 要把路径画进现场画面给人看(而不是下发运动)。

分工: 本技能管**规划与自检**; **下发与现场闸门**归 `real-arm-motion-control`; **叠加图/相机侧画法**归 `sim-real-scene-overlay`。

## 0. 先立口径
- 路径 = **base 系 TCP 位姿序列**(位置 + 姿态)。
- 位姿来源 = **示教库**, **不自己编**: `data/skills/l2_atomic/taught_points.json`(字段 `frame="base_link"`),
  抓取点 `<名>` 与预抓取点 `<名>_up`(实测两者差 +66.6mm)。
- 起始点 = **实时 TCP 只读**(`scene_overlay.read_tcp()`), 不假设臂在哪。
- 规划只写规格文件 + 只读 ⇒ **零副作用**。发运动是另一件事(要过 `real-arm-motion-control` 的解锁序列+现场请示)。
- 写规格前先 `cp -a` 备份; 写完回读条数。

## 1. 生成 waypoint
1. `W0` = 实时 TCP(只读)。
2. **L 形平移**: 先在**当前高度**横移到目标正上方(同 z) ⇒ 规划全程**上升 0mm**, 天然不碰"抬升 ≤90mm 上方横梁"红线。
3. 下降段 → 预抓取点(示教 `<名>_up`); 再下降 → 抓取点(示教 `<名>`)。
4. 抓持后抬回预抓取点(后续搬运另规划)。

## 2. 逐段过守卫 (这里是规划会翻车的地方)
每段单独算长度并核: 上升 ≤90mm(横梁) · 直线 ≤500mm · **下降 ≤40mm** · 绝不低于示教抓取位。
- 🔴 **下降守卫按*段*判, 不是按"一腿"判**: 实测 `当前高度 → _up` = **43.9mm**、`_up → 抓取点` = **66.6mm**,
  两段都超 `dz_down_limit_mm=40` ⇒ **各拆一段中继**(21.9+21.9 / 26.6+40.0)才过闸。
  只看"总下降量"会得出"规划通过"的假结论; 报告里**逐段列长度 + 标 ≤40mm ✓**, 现场会按段核对。

## 3. 从示教姿态读出真实接近方向
- 别假设"从正上方抓": 由示教四元数算 `R`, 看工具 Z 轴 `R @ [0,0,1]`。
  实测 `[0.996, 0.008, -0.093]` ⇒ 工具 Z **几乎水平**, 且与竖放模块长轴反向
  ⇒ 真实抓法是**顺槽长轴侧向滑入**(这就是"夹爪倒装"的实际含义)。
- 手指张开方向往往**不在库里** ⇒ 别从姿态推出来当真结论, 如实标"需现场确认/或一次实测标定"。

## 4. 自检: 路点投影必须落在物体上
- 逐点投回像素打印 (u,v), 与相机实测的物体框/端头比对。实测抓取点投到模块可见区**端头** ✓。
- 🔴 **示教点与相机实测盒"对不上"时, 先沿物体长轴分解再下结论**:
  实测 Δ=(52.8, 10.9)mm、`|Δ| = 53.9mm`, 但**沿模块长轴分量 53.4mm、垂直分量≈0** = 模块长 106mm ÷ 2
  ⇒ 示教点 = **端头(抓取点)**、相机盒 = **本体中心**, **两个都对**。
  不分解就会误判成"标定或示教有一方错了"。
- 示教库记录可能**四元数只存 3 个分量**(`|xyz| ≈ 1` ⇒ 缺的 w ≈ 0): 可从**同姿态的兄弟点**(另一槽位)
  取完整四元数并整体取负(实测两者差 ~1.4°) ⇒ **如实报"库记录异常 + 借用"**, 不要静默改示教库。

## 5. 画进现场画面 (细节归叠加技能, 这里只要不踩这几脚)
- 🔴 **用真折线元素, 不要把路径拼成一串盒子**: 把每段画成细长 3D 盒(哪怕管径加大、每 8mm 插一段)出来的
  是**一串独立方块** —— 每个盒子都画自己的 12 条棱与面, 用户看到的是「一个个方块的叠加」, 会直接问「线条呢」。
  定式 = 给渲染器加**一个折线元素**(`{"kind":"path3d","pts3d":[[x,y,z],…],"width":4}`), 逐点投影后
  `cv2.line` 画成**连通笔画**。插值只用来平滑视觉, **替代不了元素类型**。
- 🔴 **折线分支必须有投影限幅**(只判 `z>0` 不够): 贴近相机的路点会投到画面外**极远处**(u≈2000),
  与近点连一条线就拉出横贯全帧的长条(实测糊掉 **64%** 画面) ⇒ ①`zc>0.12` 且 uv 在 `[-1.5W,2.5W]` 才参与
  ②单段像素长 > `1.2×对角` 跳过并记 skipped 原因。
- 线的可见性: **亮色 + 线宽 ≥3~4px**(实测 4px 在 640×480 上够看); "管径越粗越好"那套是给盒子用的。
- 🔴 **路径上一个字都不要**: 渲染器给**每个框**打一个不透明标签芯片(填色底 + 黑字),
  而插值段有几十个 ⇒ 画面糊满白底黑字(实测被连否两次: "你写那么多白底黑字是什么? 我要的是线, 不是字")。
  定式 = 该层**每个元素**置 `no_label: True`(`scene_overlay` 已支持这个 box 级开关), **一个标签都不画**;
  要交代的编号/段长/守卫结论写在**聊天消息**里。标签若必须有 ⇒ **只能 ASCII**(Hershey 画不出中文, 会变 `?`)。
- 来源用**独立 origin**(如 `plan` 亮白), 别借 `human`(灰白, 暗背景上几乎看不见) —— 规划**不冒充**模型/检测器输出,
  且只重写自己这一层, 不冲掉 sim/meas/vlm/det。新增 origin 要加进 `scene_overlay.ORIGIN_STYLE`:
  离线渲染立即生效, **实时画面等推流服务重启**(改 .py 才要重启; 改规格不用)。
- 🔴 **清旧层不是传空列表**: `merge_origin(spec, cam, origin, [])` 是**空操作**(实测旧层原封不动 ⇒ 新旧两层叠在画面上)
  ⇒ 真清法 = 过滤 `cam["boxes"]` 去掉该 origin + `cam["by_origin"].pop(origin)` + 把每个 `origin|label`
  追加进 `deleted[cam]`; 改完**回读每层计数**确认。
- 交付后要说明画面上**看不到什么**: 元素在 base 系 ⇒ **臂一动它在画面里的位置就跟着变**(正常);
  臂相机**装在末端上** ⇒ 越靠近起始位(相机所在高度)的路点越投出画面(实测 W1 投到 y=-53 已在框外);
  要"用别的相机看夹爪/看全程"得先给那一路做**外参标定**(只有臂相机有手眼+K 时做不到就是做不到)。
- ✅ **验收要证"服务返回的帧里有它", 不是"我在本地渲染里有它"**: 把**只画该层**渲到空画布上得到**掩膜**,
  再拿"服务端取的叠加帧" vs "同刻取的原始帧" 在**掩膜处**比亮像素数（实测掩膜 8613px 处: 叠加帧 4657 vs 原始 626
  ⇒ 多出的 4030px 就是那条线）; 并单独数**该层自己的颜色**（实测纯白 ≥250 有 1320px）证明**新配色代码真的在跑的进程里**,
  而不是旧模块 —— 这一步同时把"服务僵死显示旧图"和"代码没生效"两个假象一次排除。

## 5b. 轨迹的"正源"= 状态空间画布的 🧭 MoveIt 节点 —— 但用之前必须过同源闸
用户会追问「轨迹线应该是状态空间工程里 moveit 节点规划出来的, 对不」⇒ **架构上对**: 画布里
`sslimit → sssk1..8 → n_moveit → ssact` 就是"任何执行通路都经 MoveIt"。别把手写折线当终态交出去,
但**也不要在没验运动学之前就把 MoveIt 的轨迹贴到真机画面上** —— 那和编一个没有区别。
- 拉起与调用配方(镜像/配置/plan-only launch/服务调用/坑)见 `references/moveit-plan-only.md`;
  入口工具 `tools/moveit_plan_only.py`。
- 🔴 **同源闸(唯一硬判据)**: 拿**真机关节角**当 MoveIt 起点, 比 `FK(真关节)` 与真 `/robot/tcp_pose` ——
  实测差 **261.5mm、姿态差 137.5°, 两次独立复现数值一致** ⇒ 该 URDF 的运动学与真机**不同源**,
  它规划的轨迹是**它自己模型里**的, 不能当真轨迹画到实机画面上。判据: **位置 < 5mm 且姿态 < 2°** 才敢用。
- 两个现成入口(别每次都现写脚本): `tools/moveit_real_state_probe.py`(domain0 只读抓真机状态,
  BEST_EFFORT 双订阅) + `tools/moveit_same_source_check.py`(同源闸, 落独立证据 JSON, 退出码 5=不同源);
  证据落 `reports/moveit/`(`real_state.json` / `same_source_check.json` / `plan_slot7.json`)。
- 不同源的常见原因是厂家 **CAD URDF 的关节零位/符号口径** ≠ 控制器(SDK)报的关节值 ⇒ 别把矛头指向"图纸拿错",
  URDF 往往就是从产线工作空间拷来的; 要对齐的是**零位**。修法 = 采真机 (关节角, TCP) 配对拟合 6 个零位偏移。
- 未过闸时的答法: **架构上认同 + 如实说现在出不来真轨迹** + 说清那条手写折线的真实身份(由示教位姿 + 真机 TCP 推出),
  不要含糊成"这就是规划结果"。

## 5d. 把 plan-only 轨迹**镜像成 DDS 一条话题**(逐帧对, 2026-09-29 已交付)
老倪要的形态 = 「独立窗口里逐帧对」⇒ 轨迹必须上**全局数据空间**(不是只落 JSON 文件):
```
真机只读 tap(state_*.jsonl) → tools/moveit_plan_req.py(systemd zmax-moveit-plan-req) → plan_req.json
   → 容器 zmax-moveit 内常驻 tools/moveit_plan_live.py(每 3s: IK→/plan_kinematic_path→逐路点FK)
   → live_plan.jsonl → ss_daemon.pub_plan() → DDS **zmax/ss_plan**(zmax::SSPlan, QoS state=latch)
   → 数据空间页/独立「🌐 数据空间窗口」逐帧对
```
- 一把梭: `bash tools/moveit_live_up.sh up|status|down`(可 `GOAL_POINT=金手指点1 PLAN_INTERVAL=2` 覆盖);
  单元 `zmax-moveit-plan-req.service`(常驻) + `zmax-moveit.service`(oneshot up/down)。
- **新增一条 DDS 话题要动 5 处, 缺一处就是“注册了但收不到”**: ①`dds/ss_types.py` 加 IDL 类
  ②`dds/zmax_node.py` 进 `_SS_TOPICS` + `QOS_CLASS` ③`src/lerobot/dataspace/topics.py` 进 `TOPICS` +
  `MODE_TOPICS`(各档) + `PRODUCERS` ④发布端 `tools/dds/ss_daemon.py`(自己的 MODE_TOPICS + `read_*` +
  `pub_*` + `tick` 里调用) ⑤`PYTHONPATH=src python -m lerobot.dataspace.busdb --build` 重建 DBC,
  再 `systemctl restart zmax-dds-ss.service zmax-dataspaces-probe.service`。
- 轨迹类产物用 QoS **state(latch)**: 新开的窗口立刻拿到最新一条, 不用等下一轮; 实测 100 路点 ≈18KB/帧,
  0.5Hz 无压力。
- 验证三层都要有: 第三方独立订阅者数条数(`ZN.Node().take("ss_plan")`) · `live.json` 的
  `hz/count/matched_pubs/verdict/lamp` · `busdb.counts.messages` +1。
- 坑: ①示教点四元数只存 3 个分量 ⇒ 补 `w=0.0`(实测 |q|≈0.9997 对得上), 不补就永远 `✗ req 缺 goal_quat(4)`
  ②`pkill -f 'xxx.py'` 会**杀掉自己这条命令行**(命令行里含同一串) ⇒ 用 `pkill -f 'xxx[.]py'` 或 `systemctl stop`
  ③容器内规划器被 SIGTERM 后 rclpy 会挂着刷 `rcl context is invalid` ⇒ 改码重起要用 `pkill -9`,
  且别让两个实例写同一个日志文件
  ④重新 `docker run` 时补上 `-v ~/zmax_moveit_plan:/ws/plans`(原容器只挂了配置 ro), 否则容器里写不回宿主机。
- 详细证据/复现命令: `reports/moveit/ss_plan_dds_mirror_20260929.md` + `references/moveit-plan-only.md`。

## 5c. 现场"我要开始移动手臂了"——先把录制与实时叠加架起来再让他动
用户说「我要开始移动机器人手臂，你要实时显示 3D 边界框，实时规划轨迹，实时结果叠加到手臂相机」时,
**先架管道再回"准备好"** —— 没有录制, 他这一趟动作的数据就永久丢了(不可重演)。三件套:
1. **50Hz 录制**(容器里常驻, 必须 `docker exec -d` 分离, 不能前台):
   `live_motion_recorder.py` 订 `/robot/joint_states` + `/robot/tcp_pose`(两话题都要 **BEST_EFFORT 双订阅**),
   落三个文件 —— 全量 `/tmp/live_motion.jsonl`(归档) + `/tmp/live_trace.json`(降采样折线) +
   `/tmp/live_head.json`(滚动最近 120 条)。
   🔴 **只轮询那个滚动小文件**: 全量 jsonl 在 50Hz 下几分钟就几十 MB, 每秒 `docker cp` 一次是自拖带宽。
2. **实时轨迹叠加**(宿主机循环, `live_trace_publisher.py`): 把 base 系 TCP 折线按**空间间隔抽稀**(>2mm 才留、
   上限 ~1500 点)当 `path3d` 元素 merge 进相机 spec, 新 origin `trace`(黄)。
   · **base 系轨迹用当前 TCP 投影是对的**(和静态物体同理: 相机动了它在画面里的位置跟着变) ——
   这就是"轨迹留在空间里"的视角, 不需要按历史相机位姿逐点回投。
   · 折线点数不设上限会把渲染拖死 ⇒ 抽稀 + 上限是必需项, 不是优化。
3. **参考点自动识别**(`live_pause_marker.py`): 用户说"中间我会停顿几个点"⇒ 别让他喊, 从 50Hz 数据判:
   TCP 速度 < ~2mm/s 持续 ≥2.5s **且** 离上一个参考点 ≥20mm 才算一个点(否则起始位姿会立刻冒出假 P1、
   同一姿态反复停顿会重复打点)。落 `reports/moveit/pause_points.jsonl`(wall 时间/关节/TCP/静止时长),
   同时在画面上打 ASCII 小标记 `P1..Pn`(中文标签渲染不出来)。
4. **实时"规划"要分清同源与不同源**: 可画的 = 用他实测停顿点当路点连成的轨迹 + 关节空间插值(构造上同源);
   MoveIt plan-only 并行跑但**不画到真机画面上**(未过同源闸就是骗人), 只进报告 —— 见 §5b。
5. 起完管道给"准备好"时一并交代: 他不用喊停、我会自动打点; 说"第几个点"我就按 P 编号复现那一刻的关节/TCP 与画面。

## 6. 现场流卡住时的降级: 离线渲染(必须证明口径一致)
真机流可能"进程活着但不回帧"。顺序:
1. **先打上游源**(如 Orin 侧取帧端口): 毫秒级 `HTTP 200 / 34KB` ⇒ 上游好 ⇒ 问题在**主机服务**。
2. 再 `ss -ltnp` 看服务在听、`pgrep` 看进程活着 —— 活着但不返回 = **卡住**(守护脚本"没跑就拉起"的判据抓不到)。
   卡住的**根因自己查完再动手**: 常见是 fd 表被继承满(连 accept 都做不了), 判据与根治见
   `low-latency-camera-streaming` 的「另一种活着但不响应」一节 —— 别只重启不修根因。
   重启时机口径: 服务**已经在僵死不出图**(用户正是来抱怨页面不动) ⇒ 重启 = **恢复服务**, 直接做并给回读证据;
   服务**正常出图**时重启才会打扰旁观者 ⇒ 那种情况先问。
3. 降级交付 = 用**同一台相机、同一臂姿态**的旧干净帧跑同一个渲染函数。
   **判据 = 抓帧时与渲染时的 TCP 读值逐位一致**(实测两次同值 ⇒ 臂没动 ⇒ 投影口径一致);
   交图时**明写"离线渲染"**, 不许当实时画面报。

## 7. 报告口径
- 表格列: 路点 / TCP 位置 / 段长 / 说明; 另起一栏写**逐段对守卫的结论**。
- 明写三句: **未下发任何运动指令** · 规划已写入高层级(来源/元素数 + 与底图差异像素数) · 图看得到什么/看不到什么。
- 发现类内容(真实接近方向、示教点=端头、库记录异常)单列, 这些是用户要看的东西, 不要埋在过程里。

## Pitfalls
| 坑 | 症状 | 修法 |
|---|---|---|
| 按"一腿"算下降量 | 规划自称通过, 下发时被守卫拒发 | 逐段算, 超 40mm 就插中继点 |
| 假设"从正上方抓" | 姿态与实际抓法不符 | 算 `R @ [0,0,1]` 定工具 Z, 以姿态为准 |
| 把示教点与相机盒的差当"谁错了" | 白查半天标定 | 先沿物体长轴分解, 半长=端头↔中心, 两者都对 |
| 静默补齐缺分量的四元数 | 库里埋一个假值 | 从同姿态兄弟点借用并如实报告 |
| 给路径的每个元素都打标签 | 画面糊满白底黑字, 用户只看见字看不见线 | 该层元素全置 `no_label`, 编号/守卫结论写进聊天消息 |
| 用一串细长盒当轨迹(管径加大也救不了) | 用户看到"一个个方块的叠加", 问"线条呢" | 加折线元素 `pts3d` + `cv2.line` 连通笔画; 插值只平滑视觉, 不替代元素类型 |
| 折线分支不做投影限幅 | 一条线糊掉大半画面(实测 64%) | `zc>0.12` 且 uv 在 `[-1.5W,2.5W]`, 单段像素长 ≤`1.2×对角`, 否则跳过并记原因 |
| 现场拖动前没起录制 | 这一趟动作数据永久丢失, 用户说的"停顿点"无法复现 | 先起 50Hz 录制 + 轨迹叠加 + 参考点识别, 再回"准备好" |
