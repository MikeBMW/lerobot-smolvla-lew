# 相机画面异常取证 (全黑 / 偏暗 / "图是不是真传过来了")

## When to Use
- 面板/窗口里图片框**全黑**, 或用户问「图片是不是真传过来了」「相机是否真在采集」。
- 检测节点(如 AOI 金手指/表面)喂进去的图没内容, 但接口返回 200 / 日志说"取到照片 N KB"。
- 相同时段**一会儿黑一会儿正常** —— 需要分清是"设备坏/参数跑偏"还是"现场光照/遮挡"。

## 铁律 0: 文件大小不是证据 (最容易骗人的一条)
纯噪声**不可压缩**, 所以一张"全黑"图也能有 2 MB+ 的体积。
实测: PNG 2448×2048 = 15,040,512 像素, 全图 `mean=3.35/255`, `max=5`, `std=0.52`
(只有读出噪声底, 全部落在最低灰阶桶) —— 文件 2,324,280 B。**只看大小会得出"图没问题"的错误结论。**

## 三步取证 (每步都要有数字, 不许用形容词下结论)

### ① 传输/显示层: 本机字节 vs 源头字节
```bash
curl -s -o /tmp/now.png "http://<dev>/picture"                    # 面板走的那条取图通道
smbclient //<dev-ip>/<share> -U 'user%pass' -c 'cd <dir>; get <同名文件> /tmp/src.png'
md5sum /tmp/now.png /tmp/src.png                                  # 相同 ⇒ 传输层无关, 问题在成像
```
顺带核一次**文件大小 ↔ 日志里的 KB** 是否精确对应(`2291901 B ÷ 1024 = 2238.2 KB`),
这是"面板收到的就是那只文件"的最短证据。再取 `?meta=1`(若有)要文件名/拍摄时间。

### ② 成像层: 像素统计(判定唯一依据)
```
mean / std / min / max / 低灰阶桶占比 / 中心与四角 200×200 均值
判据:  max ≤ 12 且 mean < 8   → ⚠️ 全黑(只在拍但进光≈0)
       mean < 25              → ⚠️ 偏暗(进光不足)
       否则                   → ✅ 正常
```
可直接跑 `scripts/image_health_probe.py <文件或URL>` (输出上述全部指标 + 判定)。

### ③ 采集真伪: 源头文件时间戳 + 序号连续性
- **触发时刻对秒**: 我按下技能/接口的同一秒, 设备侧出现新文件 ⇒ 每次请求都真拍真落盘。
- **文件序号连续性** ⇒ 采集服务**没有重启** ⇒ 曝光/增益参数没被重置(常驻相机参数只在首次
  open 时设一次) ⇒ 变量只可能是**光/遮挡**, 不是参数或代码。实测: 同进程内 23:14 全黑、
  23:15 正常(mean 75.2 / max 164)、次日早上全黑 —— 同一进程、参数相同, 黑/亮来回变。
- **两帧差分非零**(如 38.7% 像素有差异) ⇒ 传感器在实时重新曝光, 不是静态占位图。

## 🔒 用 webcam 做"量测"前先锁死曝光 (2026-09-27 实测: 差分/跟踪的共同前提)
笔记本/USB 相机默认 **自动曝光 + 自动白平衡**, 画面平均亮度会自己漂。
实测同一静止场景连拍: 帧均亮度极差 **5~20** ⇒ 任何**帧间差分/模板匹配**都会把静止背景当"动的东西",
连续 4 种自动找目标的方法全被这一个变量毁掉。
```bash
sudo apt-get install -y v4l-utils
v4l2-ctl -d /dev/video2 --list-ctrls | grep -iE 'exposure|gain|white_balance'   # 先看当前值
v4l2-ctl -d /dev/video2 -c auto_exposure=1 -c exposure_time_absolute=140 \
         -c white_balance_automatic=0 -c exposure_dynamic_framerate=0
```
锁死后同场景连拍 4 帧亮度极差 **20 → 0.20** ⇒ 差分才可用。
- `auto_exposure` 的值: **1 = Manual**(要的就是它) · 3 = Aperture Priority(自动, 出厂默认)。
  手动之外的其他控件会显示 **`(inactive)`** —— 看到 inactive 就是还没切手动成功。
- 判据不能靠"深色/面积大"找目标: 那样必然被**更大更黑但静止**的东西抢走(托盘/键盘/阴影)。
  唯一可靠的判别条件是**帧间位移**; 最稳的用法是**先让 VLM 在一帧上点准目标, 再用差分/光流跟到其余帧**。
- 反例记录(都实测踩过): 帧间差分→曝光漂移污染 · 深色团块→静止托盘 · 深色+运动→静止键盘 ·
  模板匹配→NCC 0.28~0.60 落在静止背景。⇒ 先锁曝光, 再谈算法。

### ★★ 锁曝光是**临时动作**, 用完必须恢复 (2026-09-27 自己踩的坑)
锁死只在"做差分/量测的那一会"需要。**用完不恢复 ⇒ 这台相机从此永久偏暗**, 而且现场会
把它当成"相机坏了/被挡了" 排错半天 ✗✗。实测(笔记本内置 `/dev/video2` = Integrated RGB Camera):
```
auto_exposure=1(Manual) + exposure_time_absolute=40   →  画面 mean=8.01, 84.7% 像素近全黑 ✗
auto_exposure=3(自动)                                 →  画面 mean=100.55, 低灰阶仅 1.8% ✓ (亮 12.5 倍)
```
**判据(画面长期暗, 30 秒定位)**:
```bash
v4l2-ctl -d /dev/videoN --list-ctrls | grep -iE 'auto_exposure|exposure_time_absolute|white_balance_automatic'
# value=1 (Manual) 且 exposure_time_absolute 远低于 default(实测 40 vs 默认 156) ⇒ 就是这个原因
v4l2-ctl -d /dev/videoN -c auto_exposure=3 -c white_balance_automatic=1     # 恢复
```
- **手动值会一直存着**: 切回自动后 `exposure_time_absolute` 显示 `flags=inactive` 但仍记着 40 ✗,
  此时写它报 `Permission denied`(inactive 控件不可写) ⇒ **将来任何一次误切 manual 会立刻再次变黑** ✗。
  要么彻底别锁, 要么锁完在同一处恢复。
- 判定"暗"必须用**像素统计**(mean/std/低灰阶占比), 不许用文件大小(铁律 0)。
- 一行防复发: 恢复后 `stats` 里该路 fps 应**不变**(实测曝光 40→自动, local 仍 15.09fps)
  —— 若帧率被长曝光拖低, 说明选到的是"靠拉长曝光补光", 需改增益/补光而不是继续加曝光时间。

## 显示链路自证 (别把"窗口显示不了"当显示 bug)
用**同一解码/缩放路径**解一张已知正常的亮图, 看统计是否正常:
```python
pm = QPixmap(path); img = pm.toImage()          # Qt 路径
# 亮图 mean=75.21 ⇒ 显示链路没问题 ⇒ 黑框只是"如实显示了一张黑图"
```
另外: **无论窗口能不能显示, 都把原图落到本机稳定路径并给出绝对路径**
(用户偏好原话: 「如果在状态空间的窗口显示不了，那就保存让我用别的看图工具打开」)。
命名带来源与时间戳, 例: `~/zmax_data/aoi_frames/gui_received_074402.png`、
`ref_bright_0919_2315.png`(对照组), 并保留一张固定名的"最新一帧"便于反复查看。

## 🧊 用画面下结论之前, 先证「源是活的 + 这一帧是新的」
画面能取回来 ≠ 它是现在拍的。发布端冻结(节点进程僵死/崩溃)时会**一直吐同一张缓存帧**, 而且回得极快
(实测连取 8 次 md5 全同、0.001s 秒回 —— 比正常还"快"), 最容易骗过"接口 200 + 图非黑"这一层粗判。
拿这种图去判读场景 = 把几小时前的现场当现在, 结论必错, 而用户会把画面当结果。
- **解释像素之前先过新鲜度闸**(顺序固定, 不许省):
  ① 连取两帧比 md5, **相同 ⇒ 已冻结**, 转采集/发布链取证(`references/ros-image-chain-forensics.md`);
  ② 读发布端自己的状态口(如桥的 `{"n","age_s"}`), `age_s` 大于一轮间隔就是停了;
  ③ 判读/标注/汇报一律挂**拍摄时刻 + 帧龄**, 帧龄大就明说"这帧是旧的, 不能当现场”。
- **确认源曾冻结后, 要回头作废用它得出的结论**: 冻结窗口内发布过的画面判读(物体在不在、槽里有没有料、
  姿态、朝向)**全部不成立** ⇒ 源恢复后重取一帧重判, 并在回复里明确指出"前面那条基于冻结帧, 作废”。
  省了这一步, 用户会拿着一个错结论继续往下追。
- **"源已恢复"仍要复测帧率**: 恢复只证明有新帧, 实测恢复后发布侧仍可能只有 0.2~2fps ——
  这时"画面不连续"的瓶颈在发布端, 别去优化显示/播放端。
- **多路拼图/多路状态要逐路看存活, 不要只看聚合 fps**: 状态口通常每路带
  `{fps, age_s, src_age_s, stalled, dead, dead_s, frames_served, age_basis}`。判死源就三条:
  `dead=true` / `frames_served` 不增长 / `age_s` 到小时级(实测某路 26.6h、`frames_served=1`)。
  一路死源不只是那一格难看——它会**被拼进下游判据/模型裁决的画面**, 每轮都被判成「画面异常/伪彩混乱/
  时间戳与其他画面不同步」, 抬高下游的拒发/误判率。⇒ 逐路修, 别用"其它几路正常"放过。
  ⚠️ 修那一路往往要重启承载它的服务 ⇒ 会清掉其进程内状态(如页面授权), 修完提醒现场重新确认。

## 结论口径 (四选一, 每条都要挂数字)
1. **没传过来** — md5 不一致 / 字节数对不上
2. **没采集** — 设备侧无新文件 / 序号不前进
3. **采到了但没进光(黑)** — 像素统计如上 + 序号连续 + 差分非零 ⇒ 查光源/镜头盖/工件在位/曝光
4. **显示/解码问题** — 同路径解亮图异常 / QPixmap 加载失败

## 自动化: 图像类 HTTP 取回应自带"健康度 + 帧龄"
在取图的客户端(常驻执行器/助手脚本)里落盘 + 量化输出, 而不是把二进制灌进日志:
```python
if raw[:8] == b"\x89PNG\r\n\x1a\n" or "image" in ctype.lower():
    open("~/zmax_data/aoi_last_frame.png","wb").write(raw)
    log("图像 %.0fKB · 2448x2048 mean=3.48 max=5 → ⚠️全黑(相机在拍但进光≈0) · 拍摄 07:56:38 · 帧龄 59s"
        % (len(raw)/1024,))
```
- **禁止** `body = r.read().decode("utf-8","ignore")` 打日志 —— 满屏 PNG 乱码且丢失一切有用信息。
- 支持 `?grab=1`(现场重拍一帧) 与 `?meta=1`(文件名/拍摄时间) 这类 query; **帧龄**要和画面一起给,
  否则用户看的是几十秒前的旧帧却以为实时(与"负帧龄拒用/画面要标状态"的红线同源)。
- 语义分离: 「读当前照片」与「重新拍一帧」做成两个入口 —— 检测判决是异步跑在**上一张**上的,
  若把读图改成重拍, 画面与判决就不同源了。

## 🔍 模糊/复焦判据 (2026-09-24 真实测, 三条"想当然"被否)

场景: AOI 图模糊 → 要不要移机械臂去"复焦"。相机在臂上 (eye-in-hand) ⇒ 臂动=相机动 ⇒ 沿光轴移动即对焦移动。

**① 有效帧闸放最前面 (真机实测缺口)**: 现役 AOI 帧 `~/zmax_data/aoi_last_frame.png` (2448×2048) 实测
**mean=8.4/255 · std=2.38 · 全图 Tenengrad≈4 · 9 宫格全平** = **黑帧/无结构帧** → 对 0 结构的图判"清晰度"毫无意义。
判据 `ten<50 或 std<5 或 mean<3%` → `no_target`: **不判不修**, 先查取图链路。

**② 模糊量用 σ_est(px) 表达, 且必须选对反演指标**: 高频能量比在 σ≥2px **下溢乱跳** (σ_est 4.7→18.3 非单调);
**拉普拉斯比** `σ = c·sqrt(1/√(lap/lap*)−1)` 在 **0.5~6px 全程单调** (0.41/0.77/1.02/1.47/1.85/2.44/2.96) →
只有它能当扫焦信号。`q = exp(−(σ/2)²)`, **q_ok=0.78 ⟺ σ≤1.0px**; 相对标定帧归一, **禁用绝对阈值**
(同一 σ 在细节丰富 ROI 上 lap 可差 10×; 旧 AOI 的 `focus_min=60` 就是这个坑)。

**③ 归因: 图像判"糊不糊", 系统状态判"为什么糊"**
- 运动模糊**不能**用图像方向性判: 实测 ① 方向依赖 (0°/90° 拖影 aniso 反降到 0.52×/0.62×基线, 漏检)
  ② **深离焦把方向性比抬得比真运动更高** (2.70× vs 2.17×) → 用它会误杀离焦。正解 = **臂速 (编码器真值) >0.15**。
- 曝光判据**相对参考帧** (`mean < 0.5×ref`): 暗场工件 mean 8.4/255 属正常, 绝对阈值 0.15 会全体误报欠曝。
- "能否修" = **扫焦后 q 峰值能否到放行线** (`q_best ≥ q_ok`), 不是"q 随 Z 变不变" (相机在臂上, 任意模糊都随 Z 变)。

**④ 扫焦律用对比检测式 AF, 不要梯度爬山**: 深离焦 (σ>4px) 时 q 落地板 ≈0.11 **无梯度** → 爬山实测
12mm 偏差走不回来。正解 = 微探 ±1mm 定方向 → **3mm 粗扫 ±travel/2 (不依赖梯度)** → 1mm/0.3mm 细化。
实测 (真机 D405 真图 + 合成离焦): σ 估计误差 0.056px · 单帧量测 2.75ms · 两方向起步 (-9/+12mm) 均复焦成功
· 扫焦峰值落点 ±0.00mm。

**⑤ 修不了的别修**: 扫焦后仍 `q_best < q_ok` (或曲线平坦 <5%) = 端面散射/破损/污染/遮挡 → 报 NG 转人工,
**绝不"移臂硬修"**; 也不在接触/插入段动 Z (阶段白名单 + L2 收口闸)。

实现/证据: `src/lerobot/policies/left_right/state_space/focus_quality.py` · `tools/blur_refocus_demo.py` (10/10 判据)
· `tools/probe_focus_metrics.py` (指标探针) · `tools/diag_aoi_frame.py` (真机帧诊断)
· 方案: `docs/design/fusion_localization_blur_refocus_20260924.md`

## 🧱 "面板某格没图像" 的第四类根因: 服务端状态端点挂了 / 载荷把页面拖死 (2026-09-28 实测)
源端、取图、解码都正常 (HTTP 200、图非黑), 面板/网页那格就是不出图 —— 先不要往相机上查, 查**状态端点**。
- **序列化崩**: 端点里 `json.dumps` 撞上 numpy 标量/数组 → `TypeError: Object of type ... is not JSON serializable`
  → 每次轮询都 500 → 前端拿不到状态、MJPEG 格不刷新 = 用户看到的"没有图像"。
  修法: 序列化统一走 `_json_safe()`/`_jbytes()`(带 `default=` 兜底), 不要注释改数据类型。
- **载荷带整图像素**: 产线 `/last_result` 的 `caliber_meta.natural` 是 2448×2048×3 的整图列表 = **5164.6KB**,
  原样进状态响应 ⇒ 单次 `/station/status` **10.4MB**, 而页面 **1.5s 轮询一次** ⇒ 页面假死/白屏。
  修法(对前端透明): 进状态前一律瘦身 —— 超长数组换成摘要, 字段名不动:
  `d.update({k: _slim(v) for k, v in kw.items()})`, `_slim` 把 `len>64` 的 list/`size>64` 的 ndarray
  换成 `{_omitted, _len/_shape, _dtype, _why, _head[:8]}`。修后实测: 10.4MB→7500B(1.8ms) · 5.04MB→1462B · 5.29MB→3232B。
- **判"真出图"的硬指标**(不看日志措辞): ①格元素 `naturalWidth>0 && complete` ②`/stats` 的 `frames_served`
  **在递增**(实测 aoi_gold 18 帧/1.11fps、aoi_surface 15 帧/0.78fps) ③每路 `ok=true` 带 `kb/shape`。
- **MJPEG 格要自带断线/停帧自愈**: 快照格会自己再请求所以自恢复, 长连接的 MJPEG 格不会 ⇒ 推流进程一重启,
  那格就**永远停在死连接**上。JS: `onerror` 1.5s 后换 `?t=Date.now()` 重连 + 每 6s 比对 `/stats` 帧序号,
  连续 2 轮不推进就换 src 强制重连 (页面把最新 stats 存 `window.__stats`)。
- **设备号一律按"卡名+能力"解析, 不写死索引**: 实测控制台按钮写死 `--local-dev 2` 打到 `/dev/video2`
  = 笔记本相机的 **GREY(IR) 路** (逐帧 mean≈6) ⇒ 那格全黑; 同时另两路串线。修后抓 DOM 自证:
  `i_local` 源 "Integrated RGB Camera" 640×480/15.1fps、`i_local2` 源 "WT15: MAXHUB-Camera" 1280×720/26.5fps。

## 🔌 "某格图冻结不动" 第五类根因: 生产者在**容器里常驻**, 重启后没人拉 (2026-09-28 实测)
表现: 某格图有内容但永远不变(用户叫"没有反映/看着是旧图"), `/stats` 是 `dead=true` + `age_s` 到小时级 + `frames_served=1`。
- **定性两步(不用猜)**: ①看**源文件 mtime** —— 若它与同目录其它产物在同一时刻冻结, 就是**生产者死了**(不是相机/带宽/曝光);
  ②看**容器内进程** `sudo docker exec <c> ps -eo cmd | grep -c '[r]<producer>.py'` —— 宿主只读落盘的 npy, 真源在容器里。
- **修法**: 按脚本自己的官方用法在容器内**分离**拉起, 不要另写一套:
  `sudo docker exec -d <c> bash -lc 'source /opt/ros/humble/setup.bash && export ROS_DOMAIN_ID=0 && python3 /repo/tools/<producer>.py --hz 5 >> /tmp/<producer>.log 2>&1'`;
  复核看**源文件齡降到秒级** + `/stats` 的 `stalled=false/dead=false/frames_served` 递增 + 快照非空(实测 640×526 · mean=121.3 · 非零像素 94.3%)。
- **必须同时做两件事, 否则下次重启再死**: ①把"拉起"写进开机脚本(check 段加“源文件齡 + 容器进程数”体检);
  ②把该路纳入已有守护(判据 = 容器进程不在 **或** 源文件齡 > 阈值 ⇒ 拉起; 正常静默)。
- **自愈验证必做**: 杀掉容器进程 → 守护应自己拉起并复核源文件齡 → 再跑一次应恢复静默(输出 0 字节)。
- ⚠️ `grep -c` 命中 0 条时**退出码是 1**(不是错误) —— 只解析 stdout 的数字, 依赖 returncode 会把"死了"误读成"查不了"。

## 常见误判清单
| 现象 | 真相 |
|---|---|
| 面板/网页某格"没有图像"但接口 200 | 先查**状态端点**是否 500(序列化崩)或响应体是不是 MB 级(整图像素进了 JSON) |
| 某格一直黑且怎么调都不亮 | 先核设备号是不是**解到 IR/GREY 那一路**(写死索引的经典坑), 按卡名+能力动态解析 |
| 多路面板里只有一路旧/坏，其它正常 | 逐路看 `dead/frames_served/age_s`; 一路死源会被拼进下游判据画面, 每轮都拉高拒发率 ⇒ 单独修那一路, 不要用"其它路正常"放过 |
| 文件 2 MB+ | 与内容无关(噪声不可压缩) |
| 接口 200 + "success" | 只说明请求成功, 不说明画面有内容 |
| 文件名写着 `..._W1600_H220_...` | 可能是硬编码名, 实际 2448×2048(名实不符, 别据此判断) |
| "窗口黑屏" | 先跑显示链路自证, 多数是图本身黑 |
| "相机坏了" | 先看序号/J基于同一进程的黑亮交替记录; 曝光参数常驻不变时, 变量是光 |
| 帧间差分说"到处都在动" | 相机**自动曝光漂移** ⇒ 先锁曝光(见「锁死曝光」节)再差分 |
| 自动找"动的目标"抓到托盘/键盘 | 打分条件只要含深浅/面积就必然被抓 ⇒ 判别条件只能是**帧间位移**, 且目标先由人/VLM 点准 |
| "标注图已经生成了" | 文件存在 ≠ 画上了框: **数一遍彩色像素**(红/蓝/绿各多少), 0 框说明标注链**上游**空了, 别把无框图当交付件发出去 |
| 画面判读结论后来被推翻 | 发布端冻结时也会秒回旧帧 ⇒ 下结论前先比两帧 md5 / 读 `age_s`; 一旦发现冻结, **作废并重判**已发布的结论 |
