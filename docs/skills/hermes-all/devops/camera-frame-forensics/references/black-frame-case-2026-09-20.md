# 案例: "图片框黑屏" 全链路取证 (2026-09-20, AOI 金手指 10082)

用户问句: 「能看到有信息(执行器 200 + 取到照片 2448x2048 2238 KB)，但图片框是黑屏，
你看看这个图片是否传过来了？你再查查工控机是否真的在采集图片？」

## 结论链 (每条都有数字)
1. **传输层无关** — 本机 `curl /picture` 取回的字节 md5 == 工控机共享里同名文件的 md5
   (`eb892f647c7195e2cb9f8b2ca4f0ff34` = `goldfinger_images/Finger_TopView_W1600_H220_No_6.png`);
   面板日志里的 `2238 KB` 精确对应 `No_5` 的 `2291901 B ÷ 1024 = 2238.2`。
2. **采集为真** — 用户点技能(07:44:02) 与工控机落盘 `No_5` 同秒; 我单独触发
   `GET /picture?grab=1`(07:56:38) → 设备侧同秒多出 `Finger_Image_W2448_H2048_No_7.png`(原图)
   + `Finger_TopView_W1600_H220_No_7.png`; 序号 `No_4→5→6→7` 连续 ⇒ 服务未重启。
3. **图像本身全黑** — 15,040,512 像素 `mean=3.35~3.48/255`、`std≈0.53`、`max=5~6`,
   全部落在最低灰阶桶(只有读出噪声底); 两帧差分非零像素 38.7% ⇒ 传感器在实时重新曝光。
4. **显示链路正常** — Qt 同一路径(`QPixmap.toImage`)解昨晚的正常图得 `mean=75.21`, 解当天图得
   `mean=3.35` ⇒ 黑框 = 如实显示黑图, 不是渲染问题。
5. **变量是"光"而不是"参数/代码"** — 同一进程内 09-19 23:14 全黑(`mean 4.52`)、23:15 正常
   (`mean 75.21 / max 164`)、09-20 07:44 又全黑; 相机常驻, 曝光(`EXPOSURE_US=10000us`)与
   增益(`GAIN_DB=1.0`)只在首次 open 时设置一次、进程未重启 ⇒ 参数没变。

## 陷阱: 文件大小会骗人
"全黑"图仍有 2.2 MB —— 读出噪声是随机的, PNG 压不动。**只有像素统计能判定有内容/无内容。**

## 交付动作 (用户偏好)
- 原图落到本机稳定路径并给绝对路径: `~/zmax_data/aoi_frames/` 下
  `gui_received_074402.png`(面板收到的那张) / `aoi_now_latest.png` / `ref_bright_0919_2315.png`(对照),
  以及固定名最新帧 `~/zmax_data/aoi_last_frame.png`(每次取图自动覆盖)。
- 用户原话: 「如果在状态空间的窗口显示不了，那就保存让我用别的看图工具打开」⇒ 先落盘再说显示。

## 顺手固化的客户端改进 (常驻执行器侧)
- 图像类 HTTP 响应**不再** `decode('utf-8','ignore')` 灌日志(满屏 PNG 乱码且丢信息) →
  落盘 + `mean/std/max` 健康度判定 + `?meta=1` 的拍摄时间/帧龄, 例如:
  `图像 2148KB · 2448x2048 mean=3.48 max=5 → ⚠️全黑(相机在拍但进光≈0) · 拍摄 07:56:38 · 帧龄 59s`
- 技能加 query 支持: `?grab=1`(现场重拍) 与既有 `?meta=1`; 「读当前照片」与「重新拍一帧」分成两个
  入口(检测判决跑在上一张图上, 混用会导致画面与判决不同源)。
- 名实不符提醒: 该服务 `/picture` 默认给 `topview`, 但透视校正输出尺寸写死整幅 ⇒ 文件名
  `..._W1600_H220_...` 实际是 2448×2048; 别按文件名判断分辨率。

## 复现脚本
`scripts/image_health_probe.py <URL或文件> [--pair b.png]`
