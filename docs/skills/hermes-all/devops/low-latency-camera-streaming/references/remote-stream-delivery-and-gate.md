# 出局域网的实时画面交付（只读闸门 · 出网隧道 · 带宽预算 · 地址发布发现）

适用: 推流机落在**被隔离的私网段**(同办公网的另一段、手机蜂窝网、云主机都够不到), 而用户要求在别处看画面。
本机只能**主动出网** ⇒ 通道必然是"本机挂隧道", 对端不可能直连。

---

## 0. 顺序：先算带宽预算, 再上通道

```
需求带宽 = (一轮刷新要搬的字节) ÷ (刷新周期)
```

两个都要实测, 不许估：
```python
# ① 一轮刷新搬多少(逐格求和, 页面/看板一格不落)
for k, p in [("arm", "/snapshot/arm.jpg"), ("ov_arm", "/snapshot/overlay_arm.jpg")]:
    print(k, len(urlopen(BASE + p).read()))

# ② 管道能给多少: 真视频吞吐按"收到几个完整 JPEG"数(SOI = b'\xff\xd8\xff'), 不看字节数
#    字节数会把"半帧/截断帧"也算成功
```
实测对照(同一台机器同一条隧道)：

| 路径 | 快照延迟 | 真视频吞吐 |
|---|---|---|
| 公网隧道 | 2.9s | **1.5 fps / 66 KB/s** |
| 局域网过闸门 | 0.00s | 10.3 fps / 497 KB/s |
| 直连源端口(基准) | — | 10.2 fps / 491 KB/s |

⇒ **闸门代理本身零损耗**(10.3 vs 10.2) —— 流量不够时不要怀疑自己的代理, 先量隧道这一跳。

## 1. 只读闸门（Gate Proxy）—— 源端口上还挂着动作接口

推流服务常与控制真机的接口同端口。**穿透只指向闸门**, 绝不整条映射。闸门三条：

1. **方法闸**: 只放 `GET`; `POST/PUT/DELETE/PATCH` 一律 403 —— 哪怕令牌正确也 403(动作接口多是 POST)。
2. **白名单**: 逐条正则全匹配放行页面/快照/流/清单/静态资源/交付件下载; 不在表内 → 403。
3. **点名拒绝**: 控制类、会真触发拍照或烧模型额度类、控制台页 —— 即使白名单放宽也永不外放。

```python
ALLOW = [r"/", r"/overlay", r"/overlay/[A-Za-z0-9_.]+", r"/scene\.json", r"/stats",
         r"/snapshot/[A-Za-z0-9_]+\.jpg", r"/[A-Za-z0-9_]+\.mjpg", r"/live\.json",
         r"/dl/[A-Za-z0-9_.-]+"]           # 也放行 APK/交付件下载, 否则远处的人拿不到包
DENY  = [r"/ctl/(arm|move)", r"/api/ctl/.*", r"/station.*", r"/gen.*", r"/tap.*", r"/move.*"]
```
注意 `DENY` 要**精确**：把 `.*` 写在 `/ctl/` 后面会连带拒掉只读的 `/ctl/status`(页面可能要用)。

**令牌闸(共享口令)**: 空口令=不校验(仅内网); 有口令时 `?k=<token>` 或 cookie `zmaxk=<token>` 才放行。
带 `?k=` 打开那次回一个 `Set-Cookie`, 页面内**同源子请求**(各条 MJPEG/快照)就自动过闸, 不必改页面 JS。

**MJPEG 透传**: 转发上游响应头时**去掉** `Content-Length/Transfer-Encoding/Connection`, 按块边收边发,
并补 `Cache-Control: no-store`; 自己合成的无限流要显式 `Connection: close` + `close_connection = True`
(HTTP/1.1 下没有长度又不断开, 客户端会一直等)。

**验收用案例表(每条实测, 不许凭信心)**:
```
页面(带口令) 200 · 页面(无口令) 403 · 页面(带 cookie) 200 · 快照 200 · 清单 200
★ POST /ctl/move?k=<正确口令>  403      ← 最关键的一条
★ POST /ctl/arm?k=<正确口令>   403
★ /gen(会真拍照/烧大模型) 403 · /station 403 · 随手路径(/etc/passwd) 403
```

## 2. 隧道常驻（本机只出网, 不开任何入站口）

ssh 型隧道免安装免账号, 自带 HTTPS(HTTPS 很关键 —— 站点是 HTTPS 时页面不能取 `http://` 的流, 混合内容会被内核拦死)。
```bash
ssh -T -o StrictHostKeyChecking=accept-new -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
    -o ExitOnForwardFailure=yes -R 80:localhost:8891 nokey@<tunnel-host>
```
systemd 常驻要点：
- `Restart=always` + `RestartSec`; 日志 append 到文件(**地址只会打在日志里, 必须能从日志取回**)。
- **依赖用 `Wants=`, 不要 `Requires=`**: 否则重启上游服务会连带重启隧道 ⇒ **隧道地址再变一次**。
- **地址漂移的真因是"隧道内没有真实流量"**: 服务端日志里能直接看到
  `Received disconnect from <ip> port 22:11: tunnel inactivity timeout` ——
  **ssh 自己的 `ServerAliveInterval` 保活不算他们的"隧道活动"** ✗。
  ⇒ 加一条**HTTP 层保活**: 每分钟经隧道取一次白名单里的图(如 `/wall.jpg?w=240&q=45`, 约 15KB/次,
  一天约 21MB 可忽略)。实测加完后地址不再漂, 给用户的链接能长期有效。
  保活脚本顺带两件事: ① 取不到(HTTP != 200) 就在日志记一行并**重新发布当前地址**;
  ② 别每分钟写日志(只在整 10/20/40 分记一行), 否则日志自己刷屏。
- **顺序: 先钉住地址(上面的保活) ⇒ 钉不住再走第 4 节的发布-发现。** 地址稳了, 对方 nginx 的
  `proxy_pass` 才是一次配好就不失效的。

### 2.1 交付前必须"从外面"验一次, 不能只在本机 curl
本机 curl 自己的隧道地址会"出去再回来", 通了也**不能证明第三方能访问**。两条独立证据(各 30 秒):
1. **借第三方服务器抓**: 用公共图片代理让它去取你的流地址(如 `https://wsrv.nl/?url=<URL编码后的流地址>`),
   回 `200 + image/jpeg` ⇒ 外部真能访问。
2. **再用浏览器 UA 抓一次**: 免费隧道常**只对浏览器 UA** 先弹确认/提醒页(对 curl 不弹) ⇒ 表象正是
   "用户看不到视频"。带手机 UA 取一次 `/wall.jpg`, 拿到 JPEG 魔数(`\xff\xd8`)才算过。
本机取流则用来证明"帧在变": 连取 3~5 次比 md5, 全不同才是活画面(单次 200 证明不了)。

## 3. 窄带专用的"多相机拼图"（一张图顶多格）

多格页面在窄带下永远刷不动(6 格 287KB/轮)。改成**一张拼图**: 逐路取最新快照 → 统一格子(等比缩放 +
信箱填充) → 底部贴一行标签(`路名 · 拍照时刻 · 帧龄 · fps`) → 合成一张 JPEG, 再按节流帧率做成 MJPEG。
- 标签是硬要求：用户会把画面当结果, 画面自己不标时刻/帧龄就分不清"实时"还是旧帧。
- 参数外露可调: `?w=每格宽&q=画质&fps=节流&layout=h|v`(手机竖屏用 `v`)。
- 窄带实测档位：`w=240 q=45` ≈ **14.6 KB/帧** ⇒ 2fps 约 29 KB/s、3fps 约 44 KB/s;
  `w=320 q=55` ≈ 25.3 KB/帧; `w=400 q=60` ≈ 28 KB/帧(局域网档)。
- 合成源用**已落盘的叠加快照**最简单(不额外占相机), 但要确认那些快照本身在持续更新。
- 单一目录里多种自造流类型(布局/尺寸/帧率)最好走同一套 query 参数, 便于对方照单调档。

## 4. 地址会变 ⇒ 发布-发现, 而不是写死

把**当前地址**定期 POST 到对接方已有的固定域名/中转, 对端用固定 URL 暴露成一份清单：
```python
payload = {"kind": "live_url", "url": url, "stream": "%s/wall.mjpg?k=..&w=240&q=45&fps=2" % url,
           "snapshot": "%s/wall.jpg?k=..", "token": TOKEN, "readonly": True, "at": now_iso()}
```
- **只在地址变化或心跳超时时推**(如 30min), 不要每几分钟刷一条 —— 对方数据目录会被几百个小文件塞满。
- 取"当前地址"时**倒序试最近几个**, 用一次真实取图(200 + JPEG 魔数)验活, 别只取日志最后一行。
- 客户端(APP/网页)只认对方那个固定清单地址 ⇒ 隧道怎么变都不用重打包。
- **先探对方中转能不能给固定文件名**: 很多中转把每次 POST 存成 `<prefix>_<时间戳>.<ext>`(看响应里的
  `name` 字段), 那就**无法**在它上面维持一个固定地址的图/流 —— 2fps 的流一天会塞几万个文件。
  这类中转只能当"一次性交付/清单"用; 视频仍走隧道或对方的端口转发。探法是发一张测试图 + 读回
  响应里的 `name`, 再按 `GET <base>/data/<name>` 取一次确认公网可读。

## 5. 与转发方的接口清单（照分工交付, 一次说全）

给"负责端口转发/打包"的一方这些：
1. **映射目标**：闸门端口(如 `127.0.0.1:8891`) —— 并明确 **别映射源端口**(上面有动作接口)。
2. **nginx 片段**(必带 `proxy_buffering off`, 否则"推了但不动")：
   ```nginx
   location /live/ {
       proxy_pass <当前隧道地址>/;
       proxy_http_version 1.1;
       proxy_buffering off;      # ★ 不加就是"没流/像静态图"
       proxy_cache off;
       proxy_read_timeout 3600s;
   }
   ```
3. **码率档位表**(哪个档位多少 KB/s、哪档给手机) , 让对方按管道选, 不靠猜。
4. **清单端点**(`/live.json`): 每个流的地址、参数、码率、口令一起给出。
5. **反代不生效时的排查顺序**：先 `proxy_buffering off` → 再量带宽 → 再看令牌 cookie 有没有带上。

## 6. 安全与诚实边界

- 公网暴露任何现场画面都应**加令牌**, 并在交付里说明"拿到链接的人能看到什么"; 只读闸门保证动不了设备。
- 触发类/生成类接口默认**不对外**; 远程点到会 403 是**有意设计**, 要在交付里说清(不是 bug)。
- 不要承诺"实时"除非实测帧率 > 1.5fps 且连续收到完整帧; 窄带档位要连带说清画质代价与"谁点头才能上大带宽"。
- 公网通道只作临时/旁路, 稳定域名+真视频仍应走对端服务器的端口转发(那样地址固定、带宽也够)。
