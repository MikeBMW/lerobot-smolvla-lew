# 阶段交接与"物化"纪律: 归档完整 ≠ 产物可用 (2026-09-13 实测)

配套: `hf-dataset-subset` → 「从大归档物化到消费路径」(原子落位配方) · `disk-redline-guard` (归档回收)

## 病案 (原样记录, 下次先按这个查)

用户拿官方评测的 debugpy 启动配置问「怎么报错了」:

```
FileNotFoundError: [Errno 2] Unable to synchronously open file (unable to open file:
 name = '/home/ubuntu/stable-wm-cache/datasets/pusht_expert_train.h5', errno = 2)
```

真相: 归档 `/home/ubuntu/dl_intact/pusht_expert_train.h5.zst` **13.14GB 完整躺在盘上** (`zstd -t` rc=0,
头声明解压 46300921856 B = 43.1GiB), 但**从没解压**。为什么:

- 解压那一步属于另一条流水线 (`l4_ab/intact_results/autopilot.log`, **09-12 15:30 已「流水线结束」**)
- 归档是 **09-13 03:51** 才下完的 → 交接断档
- 07:42 用户关机重启, 更没机会补

下游所以报的是一句"文件不存在", 而盘上其实躺着 13GB 的答案。

## 规则 (可直接搬进任何获取链)

1. **终态判据落在下游消费路径上**: `下游配置里写的那个路径` 存在 + 可打开 + 能真解码抽帧。
   `归档下完` / `stage 日志打了成功` 都**不是**完成。
2. **交接/重启后按产物重审, 别读日志**: 逐项 `ls` + 试打开最终消费路径。日志说"结束"与产物可用是两件事。
   (上面的病案里, 下载侧日志与流水线日志都是"成功"。)
3. **每个 stage 要幂等**: 归档晚于流水线结束时, 需要再审一次 (能独立重跑的解压/校验入口),
   而不是假设"它会在"。
4. **看门狗先判完成再判卡死**: 实测 `pgrep` 到 aria2 反复对**已下完**的归档报「卡住, 重启续传」
   (每 6 分钟一条, 还留下 `.aria2` 残留)。卡死判定之前必须先做完成判定
   (`zstd -t <归档>` / aria2 账本 / size+sha256 双核); 已完整就 `exit 0`。
5. **一发现"缺文件"先找归档, 不要重下**: `find <盘> -maxdepth 5 -name '*<task>*'` ——
   十有八九归档在, 只是没人物化。

## 汇报口径 (老倪零容忍)

- 说清"实际在跑什么": 修完要报的是「解压 → 字节数一致 46300921856 → 索引自洽 → 末帧 std 22.81 → 预检 PASS」,
  不是"应该好了"。
- 磁盘代价要同时报: 物化后 316G used / 61G free (85%), 越过了 `disk_redline.sh` 的 200G 告警线;
  可回收项 = 已解压的 `.zst` + 其它任务的归档残留 (逐项列出再问, 不擅自删证据)。
