# 多阶段训练编排: 逐阶段读 rc + 反复失败的 OOM 真凶 (2026-09-22)

适用于任何"一个编排器顺序跑多阶段长任务"(训练/评测/导出), 尤其当**整体 exit code 会骗人**时。

---

## 1. 「整体 exit=1」≠「任务失败」—— 必须逐阶段读 rc

实测 (`tools/joint_train_all.py` 一次串联, 4 阶段):

```
stages.jsonl:
  [L4]  rc=0   128.4s   INTACT 续训 + LoRA (基座冻结, 只训 lora_A/B)
  [L3]  rc=0   471.3s   SmolVLA+LEW 续训 + LoRA
  [L2]  rc=0    53.6s   真机标注帧域适应微调
  [LLM] rc=1     0.0s   权重/接口就绪**体检** (非训练)
整体 exit=1  ← 被最后那个只读体检阶段拖的
```

**读法**: 整体 `exit=1` 时, **逐行读 `stages.jsonl` 的 `rc` + `secs`**。
本例三层**训练全过**, 只有一个**只读体检**阶段失败 —— 若只看整体 exit code 就会误报"训练失败"。
**同时看 `secs`**: 有实质耗时(数百秒)且 rc=0 = 真跑过; `secs=0.0` 且 rc=1 = 前置检查就退出。

**报告口径**: 「三层训练 rc=0 全过 (耗时 Xs/Ys/Zs) · 第 4 阶段是**只读体检**, rc=1 原因=权重缺,
**不影响训练结论**」。别让一个体检阶段盖掉训练的成功。

## 2. 反复 rc=1 的**真凶是 CUDA OOM**, 不是配置/代码问题

同一天 `--only L3` 连跑 3 次全 `rc=1` (12:50/12:53/12:57), 日志尾部统一:

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 102.00 MiB.
GPU 0 has a total capacity of 7.62 GiB of which 53.75 MiB is free.
Process 2694 has 142.00 MiB | 5274 has 170.00 MiB | 5060 has 148.00 MiB
this process has 7.08 GiB in use (PyTorch 6.89 GiB)
```

⇒ 8GB 卡: **常驻服务 (推理 server 等) 占几百 MB** + 本进程要 7.08GB > 7.62GB。
**同配置在 GPU 空闲时跑, 一次就过** (GPU 3%/493MiB → L3 rc=0)。

**纪律 (省最多时间的一条)**:
- 跑前先 `nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader`,
  再对每个 pid `ps -p <pid> -o etime=,args=` 认**是谁**在占。
- 🔴 **判断"现在能不能起"看 `memory.used`, 不要看 `utilization.gpu`**: 实测见过
  `utilization 0% 而 memory.used 7267 / 8188 MiB`(上一阶段刚结束的间隙 / 别人在算的间隙)。
  拿 0% 断定"卡空着"⇒ 一起跑就 OOM。利用率是**瞬时**值, 显存占用才是容量事实。
- **不要因 OOM 就改模型/降精度/换配置** —— 先腾显存。把"资源冲突"误诊成"模型太大",
  会引出一串没必要的量化/裁剪工作, 而且结论是错的。
- 编排器通常内置"跑前查显存 / 不 kill 非本编排器进程", 但**它不会替你停常驻服务** ⇒
  跑全量前自己确认空闲窗口。

## 3. "联合训练"这类词先定性再回答 (顺序流水线 vs 共享梯度)

被问「所有模型是**一起**训练的吗？」时, **先 grep 编排器结构再答**:

```
判断依据: 各阶段是否共用 venv / 数据 / loss / 优化器 / 计算图
  共用 ⇒ 真联合 (shared-gradient joint training)
  各自独立、for 循环顺序执行 ⇒ **顺序流水线** (joint = 统一编排+取证+纪律)
```

实测本例: 4 阶段**各自独立 venv** (`INTACT-JEPA/.venv` py3.10 / `lerobot-venv` py3.12 /
`gui-venv311` py3.11) + 独立数据 + 独立起点 ⇒ **顺序流水线**;
编排器自述「把各层已有且验证过的训练入口统一成一条流水线 (不另造训练逻辑, 只做编排+取证)」。
⇒ 三个框架三个 venv **架构上无法塞进同一 autograd 图** ⇒ 真联合只有两条路:
**共享表征+梯度回传**(需同进程) 或 **蒸馏对齐**(松耦合, 不需同图)。

```
reports/joint_train_<ts>/
  stages.jsonl  {stage, layer, desc, cmd, rc, secs, log, evidence, ts}
  summary.json  {generated_at, steps, lora:{L4,L3,r}, gpu_free_mb_at_end, rows:[...]}

```

`lora:{"L4":true,"L3":true,"r":8}` + `gpu_free_mb_at_end: 7695` = 跑完已释放显存的旁证。

## 5. 删大归档前先验证它**是不是残留** (别盲从字面指令)

用户说「把 X 的残留数据删了」→ 实测:**没有残留** —— 压缩包已清理, 剩下的是
**93GB 完整有效数据集** (h5 可开: 键/形状/行数齐全)。

⇒ **先列清单 + 验证完整性, 报"要删的是资产不是垃圾"并请确认**, 用户确认后才删。
本例删后 312G → **221G** (释放 92GB, 回到红线内); **代价向用户讲明** (失去该数据集的官方 eval 能力)。

## 6. 同卡并发判定 = 显存预算**加法**, 不是感觉 (回答「所有模型能同时训练吗」)

- **让每个阶段申报显存**, 再和整卡比: 实测 8GB 卡上
  L4 阶段申报 **6000 MB** · L3 阶段申报 **6000 MB** · L2 阶段申报 **4000 MB**;
  实际单层训练中 `nvidia-smi` 实测整卡占用 **6395 MiB**(其中本模型 **5728 MiB**)
  ⇒ **6000+6000=12000 > 8188** ⇒ 两层并发物理上放不下。单层就贴边时
  (实测开 LoRA 后 batch 被迫 8→4; 8 会 `OutOfMemoryError: 需 816MiB, 仅余 330MiB`),
  任何"并发"想法先得减 batch / 减序列长 / 降精度。
- **答案分三层给全**(只答"能不能"用户不会满意):
  1. **一条命令串起来跑 = 可以** —— 编排器逐阶段串行 + 每阶段前 `wait_gpu(need_mb)`,
     每层从**当前在役权重续训**(零回退、不覆盖旧产物)、每阶段落 rc/耗时/产物路径;
  2. **真并发 = 不行** —— 把上面那条加法摊出来(数字比形容词有用);
  3. **要真并发就换架构** —— 多卡/多机分工(每层各占一张卡), 或把各层收成
     **共享主干 + 多头**的单模型(一个 optimizer 才是真并发; 代价 = 各头的任务阶段覆盖率必须一致,
     不一致会互相拖累); 松耦合时蒸馏对齐也行(见 §3)。
- **说清哪些阶段根本不训练**: 外部 API 层 / 只做"权重与接口就绪体检"的层(显存需求 0)
  不占卡也不排队 —— 不点明的话用户会以为它在等。
- **阶段边界看落盘的 rc/耗时(JSONL), 不要靠"日志尾部的进度条"猜现在在跑哪个阶段**;
  编排器默认给每阶段步数上限(`limit_train_batches` 之类), 别让一轮把卡占满几小时。
- **不要在同卡已有重任务时起第二个模型(含按需加载的推理服务)**: 分割/大模型这类"按需重"的组件
  峰值 2~2.4GB, 卡上只剩 ~1.8GB 时要**等**, 并在回复里给出"等训练结束再补"的 ETA ——
  抢卡换来的是 OOM + 两条链都不干净。
- **真在训的证据**: `nvidia-smi --query-compute-apps` 列出该 PID + `secs` 在走 +
  日志里 `step N/M` 递增且 loss 有值; 多个 worker 子进程同属一个训练, 别当成多个作业。
