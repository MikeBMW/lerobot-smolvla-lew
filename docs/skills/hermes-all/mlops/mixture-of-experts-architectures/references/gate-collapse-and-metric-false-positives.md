# 门控坍缩 与 判据假阳性（2026-09-24 实测 · 必须与 SKILL.md 的"路由分化诊断"同读）

> ⚠️ 本文件**修正** SKILL.md 中一条已被当场撤回的结论。
> SKILL.md 的指标表写着「④ 阶段-专家一一对应率 ≥ (k−1)/k」并在实测段写
> 「④ 一一对应 6/7 ✅ 分化成立 …这种部分分化才是健康结果」。
> **该结论是假阳性，已在同一会话内撤回。以本文件为准。**

---

## 1. 假阳性是怎么发生的（判据本身的盲区）

```
判据 ④ = "各行最大值的那个专家是否达标" 的比例。

若某个专家 E0 吃掉**全部**阶段：
    接近→E0 · 对位→E0 · 下降→E0 · 抓取→E0 · 抬起→E0 · 转移→E0 · 插入→E0
 → 每一行的 argmax 都是 E0 → ④ 自动 = k/k = **全部通过**
 → 而模型其实**已经退化成单头**（MoE 只剩一个有效专家）

实测两条 MoE（同数据 v6_sub25k、同步数 2500、同增强）：
  跑A: 有效专家 7/7 · ④对应率 6/7（曾报"分化成立"）· **⑤单射性 4** → 部分坍缩
  跑B: 有效专家 6/7 · ④对应率 7/7（看起来更"漂亮"）· **⑤单射性 1** → 完全坍缩
       E0 独占: 插入 100% / 转移 96.8% / 接近 94.4% / 抬起 70.2% / 抓取 60% …
⇒ **④ 越"漂亮"的那一次，坍缩越严重** —— 弱判据会给出**反向**信号。
```

## 2. 修正后的判据（以 ⑤ 为准）

| # | 指标 | 通过判据 |
|---|---|---|
| ① | 阶段→专家混淆矩阵 | 看主导占比 |
| ② | 路由熵 | 明显低于 log(k) |
| ③ | 有效专家数 | = k（否则有专家饿死）|
| ④ | 阶段-专家对应率 | **弱判据 · 会假阳性 · 仅作参考** |
| ⑤ | ★**单射性** `len(set(各阶段 argmax))` | **≥ k−1**（各阶段须分到**不同**专家）|

**口诀**：*任何只在"某专家独占"时才失效的指标，等于没有指标。*
诊断脚本**必须**打印 ⑤，否则会骗过自己（模板见
`scripts/moe_gate_diagnose_template.py`，已加 ⑤）。

## 3. 坍缩的根因（设计缺陷，非数据问题）

```
原实现:  g = softmax( stage_onehot @ P(eye×4.0)  +  MLP(h, stage) )
                    └─ 先验项(固定)                 └─ **自由学习项, 无约束**
训练后期自由项的 logits 量级超过先验项 → 先验被淹没 → 全部倒向 E0。

⚠️ 注意：文档里写的是"按 stage 先验路由"，但实现成了"先验 + 自由学习"。
   **实现与设计不符** —— 这是本会话第三次同类错误（另两次：配置项 setter 从未写入
   导致权重与上一版逐位相同；开关只改了 2 个调用点中的 1 个）。
   ⇒ 改架构/加开关后，必须验证"它真的生效了"（打印配置 / sha256 / 断点）。
```

## 4. 解法：硬先验路由 `route="prior"`

```python
if route == "prior":                      # 结构性保证不可能坍缩
    g = stage_p / stage_p.sum(1, keepdim=True).clamp_min(1e-6)
    g = torch.where(g.sum(1, keepdim=True) > 0.5, g,
                    torch.full_like(g, 1.0 / n_experts))
else:                                     # "soft": 学习门控 —— 实测会坍缩
    g = torch.softmax(stage_p @ gate_prior + gate_mlp(cat([h, stage_p], 1)), dim=1)
```

- `prior`：每个阶段**必然**路由到自己那个专家 → 单射性 = k/k（结构性，无需训练即成立）。
- `soft`：只在"路由信号本身需要从数据里学"时才用（如没有现成 stage 先验），
  且必须**加约束**（KL 到先验的正则、负载均衡 loss），否则会坍缩。
- ⚠️ 诊断/部署的 route 模式必须与**训练时**一致，否则测的不是真实行为。

## 5. 一个容易误读的副产物：容量 ≠ 分工

```
跑B 虽然门控完全坍缩，离线留出**仍优于密集版 30%**（观测 0.0091 vs 密集 0.013）。
⇒ 该增益来自 **7 个专家的额外容量**（即使输出被平均，参数也更多），
   **不是**来自"阶段分工"。
⇒ 结论必须写清是哪一种机制在起作用；"MoE 有效"不能默认归因为"分工有效"。
   要证分工有价值，就得让 ⑤ 达标后再比较（这正是 `route="prior"` 版要验的）。
```

## 6. 检查清单（MoE 改造收尾必过）

```
□ 数据里确有路由信号（每个混训 h5 都有该字段）
□ 训练日志打印了 route 模式（确认生效，不是"以为生效"）
□ 诊断输出 **⑤ 单射性**（不是只看 ④）
□ ⑤ ≥ k−1 且 有效专家 ≥ k−1  → 才可称"分工成立"
□ 离线增益注明机制：容量 or 分工
□ 有逐 seed 对齐的闭环 A/B（离线好 ≠ 任务收益，见 SKILL.md 末节）
```
