# 接管一个已有控制器: 保留内置兜底 + 一致性守卫 (2026-09-13 实测)

> 配套 SKILL.md 的 §5 (算力预算) 与 §6 (Pitfalls)。这里记"模型要接管一个**本来就能工作**的控制器"时的
> 正确接法与阈值实测 —— 与 §2 的"离线回放闸"互补: 离线闸判"模型有没有学会", 本文判"接管到哪一档才不掉分"。

## 1. 症状: 纯前馈接管 0/N, 而且守卫一次都不触发

实测: 自训 actor 离线 MAE 0.0028 (0.28mm 级, 好到不像话), 闭环 0/10。
诊断链最终定位到**引擎原版控制器自带保护被我们替换掉了**:

```python
class FeedforwardAccelerator:
    """主路径 = 蒸馏 MLP; **状态出训练域 → 解析守卫兜底** (全局稳定, 同教师)
       域判定: (a) hand→target 3D 距离 d_guard ≤ D_GUARD
               (b) 归一化逐通道 |x| ≤ DOMAIN_SIGMA (target 通道自身域外 = 布局偏离蒸馏数据)"""
```

我们把 `sim.accel` 整个换成自己的 wrapper → 兜底路径消失 → 模型在域外输出坏动作,
没有任何人接管 → 卡死。**替换一个带保护的控制节点时, 保护必须由你显式保留。**

## 2. 正确接法: 一致性守卫

```python
u_eng = inner.forward(obs)        # 先算引擎原版 (含域判定 + 兜底) = 安全基线, 永远保留
u_act = model(...)                # 模型建议
u = u_act if np.abs(u_act - u_eng).max() <= TOL else u_eng
```

同时统计 **actor 采纳次数 / 兜底次数** 并打进结果 —— 没有这两个计数,
"成功"就无法区分"模型在控"还是"退化成了原控制器"。

## 3. 阈值扫描 (10 seed, 同进程内确定性)

| TOL | actor 采纳率 | 成功率 | 判定 |
|---|---|---|---|
| 0.05 | 0% | 100% | **退化 = 模型只是摆设** |
| **0.08** | **24%** | **100%** | 工作点 |
| 0.15 | 27% | 100% | 同量级 |
| 0.30 | 86% | 0% | 介入过多 |
| 0.60 | 100% | 0% | 全模型 → 崩 |

- 同进程内 3 次重跑结果**逐位相同** (1024/2773); 换进程就变 → metaworld 布局跨进程漂移,
  **泛化证据必须跨进程重复** (实测跨进程 6 seed 全成功才算数)。
- 失败形态很整齐: 崩的 seed 都是 `actor≈100%`, 说明是"接管太多"而非"模型学得差"。

## 4. 两个反直觉结论 (都有实测数据)

### 4.1 补全可观测性**不能**突破参与上限
把引擎内部状态加进观测 (46D → 53D: `u_fb`(反馈动作) + `w_ff`(调度权重) + 上一建议),
并按**真正执行的动作**(`u_fuse = w_ff·u_ff + (1-w_ff)·u_fb`)当标签重训:

| 版本 | 观测 | 成功率 | actor 参与 |
|---|---|---|---|
| v3 | 46D (obs+stage) | 100% | 27% |
| v5 | 53D (信息完备) | 80% | 54% |

模型能力确实提升了 (参与率 27%→54%), **但 100% 成功率下的上限仍是 ~24-27%**。
⇒ 上限是**任务/控制器结构**决定的, 不是信息不足。别把"加观测维度"当万能解。

### 4.2 latent 预测误差守卫对"卡住"完全无感
世界模型 held-out MSE 6e-5 (极准), 于是守卫以为一切正常: **0/599 次触发, 成功率 0**。
原因: "卡住"的状态变化**同样可预测** —— latent 误差防的是"模型被欺骗", 不是"任务停滞"。
要检测停滞, 用**任务量**: 到目标距离 N 步无改善 / 阶段不推进。

### 4.3 硬限流 (CAP) 反而把参与率打死
"actor 累计采纳率 > CAP 就强制兜底" → 触及后 rate 回升很慢 → 参与率从 54% 掉到 **7%**。
要限流就**调 TOL**(平滑, 天然控制"多相似才采纳"), 不要用硬 CAP。

## 5. 完成判据与几何自检 (被用户目检戳穿的教训)

- 判据 `insert_depth=6mm` 太松 → `done=True` 时 peg 头离孔底还有 **5.03mm**,
  视觉上"像没插进去", 用户一眼看穿。收到 **2mm** 后成功率从 ~100% 掉到 73% (更真实)。
- 验证几何**别用记录数组的近似字段**: `tr["peg"]` 存的是 `obs[4:7]` = **速度**,
  用它算出的"离孔 135mm"是假结论; 引擎自己的口径 `peg_head()` 才是真位置 (实测残余 4.5-5mm)。
- 交付前自检顺序: ① 用几何量确认动作真的完成了物理目标 ② 再看 done 标志 ③ 最后才谈成功率。

## 6. 汇报口径

- 写清"模型真参与 N% / 兜底 M%" —— 只有成功率 = 无法区分接管与退化。
- 写清是**单进程**还是**跨进程**重复 (前者只能证明可重复性, 不能证明泛化)。
- 引擎解析链已最优时, 模型的正确位置是"安全的小修正"; 要真超越得靠 RL 或换数据分布,
  靠调守卫调不出来。
