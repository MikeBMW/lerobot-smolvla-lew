# 场景理解层 VLM (本地 Qwen2.5-VL / API DeepSeek-Vision)

面向"让大模型层**先看到场景**"这类活儿: 判读真实画面 → 结构化 JSON → 喂 L4 意图/L3 流程/L2 执行。
Z-MAX 现成落点: `src/lerobot/policies/left_right/state_space/scene_vlm.py` (SceneVLM) +
`tools/vlm_worker.py` (本地子进程 worker, stdio RPC: hello/ask/bye)。

## 一、先确认"权重到底下好没有" —— 默认缓存会骗人
`~/.cache/huggingface` **不一定是真缓存**(`HF_HOME` 常被指到数据盘)。
实测 2026-09-20: `~/.cache/.../models--Qwen--Qwen2.5-VL-3B-Instruct` 只有 **12M**(元数据空壳),
真权重在 `~/zmax_data/hf_home/hub/...` = **7.1G**。差点据此白下一遍。
```bash
du -sh ~/.cache/huggingface/hub/* ~/zmax_data/hf_home/hub/* 2>/dev/null | sort -rh | head
M=<hub>/models--<org>--<repo>
ls -l $M/snapshots/*/          # ① 配置 + 全部分片符号链接都在
du -sh $M/blobs                # ② 体积对得上(3B bf16 两分片 ≈ 7.1G)
find $M -name '*.incomplete'   # ③ 空 = 无残片 ⇒ 完整, 别重下
```

## 二、bash 坑: 赋值语句里 glob **不展开** (踩过)
```bash
SS_VLM_MODEL=~/zmax_data/hf_home/hub/models--Qwen--*/snapshots/*     # ❌ `*` 原样传下去
# → OSError: Repo id must be in the form 'repo_name' or 'namespace/repo_name': '.../snapshots/*'
SNAP=$(ls -d ~/zmax_data/hf_home/hub/models--Qwen--*/snapshots/*/ | head -1)   # ✅ 先解析再赋值
SS_VLM_MODEL="$SNAP"
```
bash 赋值右侧只做参数/命令/算术展开, **不做文件名展开**(POSIX) ⇒ 通配符必须用 `$(ls -d ...)` 解析。
传给 `from_pretrained` 的必须是**真实目录**, 不是通配式。

## 三、双路路由 (本地权重 ⇄ 云 API), 一键切换
优先级(现成实现): 显式 `SS_VLM_URL`/`SS_VLM_KEY` > 本机已配 API key > 本地 worker。
- `SS_VLM_PROVIDER=local` ⇒ 强制走本地权重(绕开 API key); `=deepseek` / 显式 URL ⇒ 走 API。
- `SS_VLM_MODEL` 可给本地 snapshots 目录或远端 repo id; `SS_VLM_DEVICE`(默认 cuda:0) / `SS_VLM_DTYPE`(bf16 等)。
- **每次判读都先打印 `status()`**(path/provider/model/detail) —— 否则"以为在用本地 Qwen, 其实在打 API"。
- 交付口径: 诚实报"当前哪条路 + 时延", 不夸大(用户红线: 真值+波动)。

## 四、慢? 先把"加载"和"生成"分开量 (不要把加载时间当推理延迟)
```python
p = subprocess.Popen([py,"tools/vlm_worker.py","--model",SNAP,"--device","cuda:0","--dtype","bf16"], ...)
t=time.time(); rpc({"cmd":"hello"})                                   # ← 纯加载
t=time.time(); rpc({"cmd":"ask","image":img,"prompt":"...","max_tokens":64})   # ← 纯生成
```
实测 (Qwen2.5-VL-3B-Instruct, RTX 4060 Laptop **8G**): **加载 3.4s · 单次生成 28~35s**(两次连续调用同量级
⇒ 不是"每次重载", 就是生成慢; bf16 权重已占 7.7G)。
- 优化候选(需量化后复测再下结论, 未验证): 4bit NF4(需 `bitsandbytes`, 安装走 `uv pip install --python <venv>/bin/python bitsandbytes`) / 降 `max_pixels` / **快慢分层**(快循环用 500M 级模型, 场景理解这种慢决策才用 3B 或 API)。
- 参考量级: DeepSeek-Vision API 单帧 **2.2s**(关掉 thinking: `SS_VLM_THINKING != 1`)。

## 五、判读结果谁说了算 (VLM 不是真值)
**同一张图, 两模型会互相矛盾**: 同一帧 DeepSeek 判 `目标可见=false`(太远/被前景遮挡/偏暗, 并给出具体线索),
本地 Qwen 判 `目标可见=true`(还编出"Z-MAX 光模块插拔工位") —— 而画面里并没有模块。
⇒ 规矩:
1. **VLM 输出只能当"假设", 必须与几何/物理真值对账**(YOLO 框 + 3D 坐标、夹爪开度、位姿)。
2. 让模型输出**结构化 JSON**(目标/位置/朝向/在夹爪上/画面质量/光照/背景线索/标定建议);
   `max_tokens` **不能收紧** —— 推理型模型把思考链也算进这个预算, 收紧会直接得到空回答(见 §七)。
3. 双模型交叉 = 可用的置信度信号: 一致才敢往下传, 不一致就报"不一致"并按几何真值走。
4. 用户的红线同源: **画面 ≠ 结果**; 判读要带帧龄/状态横幅, 别把旧帧当实时。
5. VLM 给的"标定建议/该挪相机"类输出**照抄给现场**, 往往就是最快的物理修复路径(实测有效)。

## 六、没有产线相机时的备选眼睛 (零接触产线设备)
本机 USB 相机抓帧 → 自证有效(std>5) → 交 VLM 判读认不认得工位:
```python
cap = cv2.VideoCapture(0, cv2.CAP_V4L2)
for _ in range(5): ok, f = cap.read()
cv2.imwrite(os.path.expanduser("~/zmax_ss_remote/local_cam_test.png"), f)
```
实测 1280x720 `mean=57.7/std=43.5`, VLM 判读出"白色机械臂/铝型材支架/黑色托盘/黄色立柱"
⇒ 相机确实对着产线(只是太远/被遮挡) ⇒ **挪相机比动产线便宜**。
链路断在发布端时的取证: 见 `camera-frame-forensics` → `references/ros-image-chain-forensics.md`。

## 七、推理型视觉模型: `max_tokens` 是「思考 + 回答」的总预算
症状: 单次调用耗时 130~150s 却返回**空字符串**, `finish_reason=length`。
机理(不读 `usage` 就看不见): `completion_tokens_details.reasoning_tokens` **把预算全吃掉了**, 留给回答 0 个 token。
实测同一张图、同一个模型:
```
max_tokens=40   → 134s · content='' ✗   (reasoning_tokens=40, 回答 0 字)
max_tokens=500  → 1.9s · 正常回答 ✓     (reasoning_tokens=225, completion=264)
```
⇒ **规矩**:
1. 给视觉模型的 `max_tokens` 是**思考 + 回答**的总预算 ⇒ 短问答一律 **1500~3500**, 别给几十/几百。
   **但加大预算救不了长提示/大 JSON**: 实测同一张图 4000 与 8000 连续三次全空, 而把提示词压到 **~250 字**
   + 只要 **4~6 个数字的小 JSON** 后**一次成功** ⇒ **先缩问题, 再谈预算**。
   工作点参照: 一直稳定跑着的 `vl_safety_monitor` 提示词仅 **941 字**、输出十几个字段, 每次都成功。
2. **每次调用打印 `usage`**(至少 `reasoning_tokens` 与 `finish_reason`)。空回答的唯一可见证据就在这里;
   不打印就只能猜"是不是超时了", 容易误判成网络问题。
3. **“一次吐大 JSON”是最不稳的用法**: 实测 145~152s 且返回空。改成**拆成多条短问题**, 每条只要求答一行
   (如 `<有/无> | <格位> | <一句话>`), 实测单条 **~2s** 且答案可用。**慢的从来不是单次调用, 是长输出。**
4. **框的精度不要指望大模型**: 让它做"有没有 / 在哪一格 / 什么状态"的语义判断, 精确框交给几何/检测器;
   模型给的框必须在图上注明"模型估计框", 不能写成"检测结果"。
5. **不要把"空回答"直接判成最坏结论**: 把空(看不清)映射成"不安全 / 从严 / 拒绝"的守护逻辑,
   在超时设短时会**每次都误报**, 而用户看到的就是一条理直气壮的"不安全"。收到这种裁决先分下清是哪种空,
   修掉原因再重测 —— 别拿它当真实判决去停流程、停交付或通知现场。

### 7.1 另一种"空": 调用方超时被提前掉 (与 max_tokens 无关)
同一支 API, 单次耗时实测 **29~137s**(随图大小与问题复杂度变, 且波动很大) ⇒ **调用方 `timeout` 一律给 ≥300s**。
给 100s 这类偏短的值, 结果是**请求被自己提前掉、根本没有响应对象**, 日志里只剩下"空", 很容易被归到
"模型/额度不行"。
**空回答分两类(同一步就能分)**:
| 现象 | 真因 | 修法 |
|---|---|---|
| 有响应、`finish_reason=length` | 提示词太长 / 要它输出的 JSON 太大 ⇒ 思考链吃满(加大预算无用: 4000/8000 实测均空) | **先缩提示词到几百字 + 只要几个字段的小 JSON**, 再谈抬预算 |
| **没有响应/客户端报超时** | **调用方 timeout 太短** | `timeout ≥300`; 不要动 max_tokens |
⇒ 排查空回答时**先看有没有拿到响应对象**: 没有就查超时, 有才去看 `usage`/`finish_reason`。
自测配方(先定标定上限再改代码): 拿一张小图直接打两次 API, 打印 `用时 / finish_reason / content 长度 / usage`
—— 两次都有正常回答就说明服务端无辜, 问题在调用方。

## 八、小模型(500M 级)会「复述提示词」—— 这不是识别
把候选词表写进提示词(「候选对象: 机械臂/夹爪/光模块/标定板/托盘/扫码枪」), 500M 级模型会把
**这张表原样吐回来**当结果(实测 SmolVLM2-500M: 每个对象的位置字段全填 `table`/`workcell`)。
识别特征: 输出的对象集合**等于**你给的候选集合, 且位置/状态字段全同质化。
⇒ 判据: **拒绝**把复述当识别结果 —— 提问要允许模型否定("图中是否有 X?" 能答"无"),
输出与候选完全一致 = 无效, 必须换 3B 级或云端 API。别把复述往下传给 L4/L3/L2。

## 九、相机装反 / 图像倒置: 让模型投票, 把结论固化成常量
现场常见"相机装反了, 图像是倒着的"。**不要凭肉眼判断**(也没有可靠的目检手段), 用**两张候选图投票**:
```
对 raw 与 rot180(cv2.rotate(img, cv2.ROTATE_180)) 各问一次:
  "这是机器人腕部相机拍的图。请只回答一行: ORIENTATION: upright 或 ORIENTATION: upside_down
   (判据: 桌面在下方、天花板在上方)。"
两张里答 upright 的那张 = 正确朝向 ⇒ 把结论写成代码常量(如 arm_rotate_deg=180),
后续所有标注/反投影/截图都用它 —— 结论落在代码里才算做完, 不能只写在报告里。
```
判读注意: 同一问法可能出现**一张答得干脆、另一张超时返回空**(空 ≠ "不是 upright")。
一次投票不足以定论时, 按用户现场说明取值, 并在报告里分开写明"模型投票"与"现场说明"两个来源。

## 十、多路相机 → 自动标注流水线 (N 路并行, 一批 ~3 分钟)

"开始理解这个场景 / 开始自动标注"这类需求 = 把 N 路相机各抓一帧交给视觉模型, 产出**结构化标注 + 画框图 + 追加式数据集**。
现成实现 `tools/auto_annotate.py`(Z-MAX 6 路 = 3 相机 + 深度双目 + 2 路 OPT), 每路: 取帧 → 缩到最长边 ≤1024 →
`gen_overlay_from_vlm.call_vlm`(严格 JSON/左上原点像素口径) → 解析 → **框映回原图** → 落 `<cam>.json` + `<cam>_ann.jpg`;
全批 `summary.json` + 追加 `annotations.jsonl`。`--watch N` 常驻一批接一批; `--push-overlay` 顺手把某路框写进场景叠加规格。

规矩(都是实跑踩出来的):
- **并发按"路"不按"张"**: 每路一次调用是**网络等待型**(实测单次 40~180s) ⇒ `ThreadPoolExecutor(max_workers=路数)`。
  6 路一批实测 **178s**; 串行就是 6 倍。别去抠单次时延, 那个天花板在服务端。
- **送模型前缩图, 收框后除回去**: 缩到 ≤1024 省 token 与时延, 但模型给的是**送出去那张图**的坐标 ⇒
  必须 `/k` 映回原图, 再 clamp 到画幅、丢掉边长 <4px 的碎框。不映回 = 框全挤在左上角的假标注。
- **给模型看原图, 别喂处理过的"判据图"**: OPT 两路页面上显示的是去死白/拉伸的判据图(给人目检用),
  送去理解只会得到"未见可辨识物体"(0 框) —— 结论诚实但零信息量。语义理解走 `?kind=origin` 原图, 判据图只给人看。
  ⚠️ OPT 带 `?grab=1` 可能回一个几十字节的 `{"code":500,"msg":"抓帧失败"}` JSON(不是图) ⇒
  **先断言解码成功再送模型**(cv2.imdecode 为 None = 拿到的是错误体, 不是画面); 失败就退回"不带 grab 取内存里上一张"
  并把真帧龄标出来 —— 别把错误体当图片送上去, 也别把"抓帧失败"讲成"画面暗看不清"。
- **0 个框是合法结果**: 料不在/画面糊就如实报空; **绝不许为了"看起来在工作"给提示词加料逼出框**(用户零容忍)。
  `n_objects` 与 summary 原样落盘, 每批涨跌可追。
- **中文标签别用 cv2 画**: `cv2.putText` 画不了中文(出问号) ⇒ PIL + 系统 CJK 字体(wqy/Noto), 找不到就退化成
  编号+图例, 别交一屏乱码。
- **长跑要给人留"一眼可读"的出口**: jsonl/summary 是给程序和数据集的; 现场/HIL/聊天端看的是 `LATEST.md`
  那种一行一景的快照。两边都要有, 否则自动标注跑得再欢, 现场不知道它到底看到了什么。
- **推到群里要限流去重**: 按批次名写一个 `.pushed` 标记, 定时任务只在**出现新批次**时推; 节奏取 10~30 分钟一档
  (用户明确讨厌刷屏)。发图走平台图片上传接口(先传拿 key, 再发 image 消息), 别把图塞进文本消息。

## 十一、守护/告警类调用: "空 content ≠ 现场危险" (2026-09-27 实测)

- **先抓原始返回再定论**：打印 `finish_reason` + `usage`(含 reasoning_tokens) + 原始 body。
  实测同一张 960×754 拼图: 三次调用 2.7s / 2.8s / 137s 全部 `finish_reason=stop` 且 content 正常；
  而守护进程里那次 **49.5s 返回、content 空** ⇒ **不是超时、不是 token 不够，是 API 侧偶发空 content**。
- **修法：空了就重试**（最多 3 次, 间隔 2s）。**别**按"慢返回空=忙, 不重试"跳过 —— 实测 137s 的调用照样出真裁决。
- **保鲜期必须 > 单轮最慢耗时**：实测 VL 一轮 中位 53s / 最慢 222s ⇒ 给 240s 太紧，下游会把新鲜裁决判成"过期"⇒ 拒动作（600s 合适）。裁决带 `intent_seq`/`intent_desc` 时，下游应按**意图匹配**判适用性，时效只兜底。
- **fail-closed 的语义要分清**：判不了 ⇒ 拒动作（对）；但上报文案写"本帧无法裁决(API 侧偶发)"、`hazards` 留空，**不要**写成"现场有危险"——否则用户收到的是误导性告警（本轮就因此被要求"别发了"）。
- **同一个 wrapper 的所有调用点都要修, 不能只修报错的那一个**: 空 content 的处理分散在各调用方
  (`grep -rn "call_vlm(" tools/`), 漏掉一处 = 那条链路继续静默出空结果。实测: 守护侧修好了,
  但 `tools/auto_annotate.py` 里同样的调用没加重试 ⇒ L5 自动标注整环产出为空、画面上一个框都没有。
- **阶段 rc=0 ≠ 成功**: 标注/生成类阶段拿到空 payload 时照样以 0 退出, 日志一片绿而产物是空的
  (实测 `{"cam":"depth","ok":false,"scene":null}` 被记成 rc=0) ⇒ 阶段收尾必须**断言 payload 非空**
  (n_obj/scene 有值), 空就按失败上报; 否则数据集里"加上了新标注"是假的。
- **下游产物为空, 先怀疑上游模型空返回**: 叠加图 0 个框、标注文件只有壳, 根因常不在画框代码,
  而在那一次 VLM 调用返回了空 content ⇒ 顺着"谁写了这个文件/谁画的这个框"**往回查一步**。
- **改完必须重跑一次取实证**: 修完立刻单独跑一遍并数产物条目(`annotations.jsonl` 里该相机路
  `ok/n_obj` 是否为真值), 用新记录当证据; 只说"已修复"不算。

## 十二、出框类提示词: 先拓扑+投影推理, 再自检修角 (2026-09-28 老倪: 「大模型VL得先理解拓扑关系，投影原理，自己修正角度」)
- 提示词里**强制**模型先输出 `topology`(槽位结构+平行边族)/`slot`/`slot_angle_deg`, 再出框; 每框带 `obj_axis_deg`+`axis_dev_deg`, 并规定 **|偏差|>3° 必须先修角再输出**。实测(deepseek-flash, 166s): 新字段全部出现, 横模块轴向 2° ↔ Hough 实测 3.3° 一致(§七 的 max_tokens 预算必须够: 该次 completion=6848, 其中 reasoning=**6629**)。
- **但模型的数值角不可当准数**: 同图 VL 自报竖槽角 84° vs Hough 实测 75.1°(差 9°) ⇒ 口径固定为「**拓扑/语义靠 VL, 角度/坐标靠几何实测**」。
- 落点: `tools/gen_overlay_from_vlm.py` 的 `PROMPT`(场景理解词, 带 `{W}/{H}` 占位) —— 改完要**真跑一次**核字段是否真出现(语法过关≠模型按格式答)。

## 十三、让 VLM 当**判官** (质检/校正已有标注, 而不是产新标注)

触发: 「哪里不对、该怎么样, 由大模型负责」—— 让模型审阅**已有**的框/标注并给出修正, 不是重新标一遍。

- **喂什么**: ①**已叠加的实帧**(模型必须看到"当前声称"长什么样, 不能只给它原图) ②**编号清单**
  (`#n · id=origin|label · 类别 · 像素框 · 有无3D几何`) ③一句硬要求: 「**必须对清单里每一个 id 都给一条判定**
  (ok/junk/fix), 不许漏」。实测不写这句 ⇒ 18 个框只回 3 个 ok, 读起来像"全部通过"。
- **输出格式**: 严格 JSON `{junk:[{id,why}], fix:[{id,box,label,why}], missing:[{box,label,why}], ok:[id]}`;
  并允许它说"不确定 ⇒ 归 ok"(宁可少给, 不许编)。
- 🔴 **权限必须分层**: 模型只能**自动改它自己那一层**; 其它层(传感器实测的 3D 几何、画布语义桩、
  检测器框、人工删改过的清单)只能作为**提案**记账给人看, 不得自动删改。机理: 2D 视觉模型**核对不了**
  几何与注记, 会把"无像素框的语义桩""参考点/轨迹注记""实测长方体"通通判成 junk ⇒ 一次就把别人用
  真数据量出来的东西删干净。同理, **轨迹/参考点/规划线这类叠加注记不进质询清单**(它们不是物体)。
- **判定必须走思考路径**: 关思考的 0.6~2s 回答 = "全都 ok"式无信息回答(时间也明显不对劲);
  开思考实测 18 框 **105s**。⇒ 判质类别总是慢层, 按事件触发(停顿点/人工指示), 不要逐帧跑。
- **`max_tokens` 按回答长度配**: 逐条判定类长 JSON 给 **10000~15000** —— 思考链会先吃掉几千(实测
  reasoning 6629/9500); 给 3000 实测**内容为空**。这与 §七"短问答 1500~3500"不矛盾: 预算跟着回答长度走。
- **模型改过的产物必须能整体回退**: 改前备份原件 + 逐条写台账(谁改/为什么/前后值), 并提供"**只应用台账
  里最后一条判定**"的入口(省一次 100s 调用, 证据可追)。回退要**从改前备份恢复** —— 只把"抑制清单"里的
  条目删掉是不够的: 应用时往往同时把条目从主清单移走了 ⇒ 画面缺一半东西而计数仍显示旧值
  (计数是记账字段, 会骗人; 手工改完按主清单**重算**)。

## 十四、产出要带**像素框**才准进规格; 判定调用要串行

- 🔴 **`box=null` 的条目一律拒收**(除非它带 3D 几何): 画不出来、也复核不了, 只会让"大模型=8"这类计数虚高,
  下一轮判定还会自己回一句"图上没有对应像素框, 无法定位"。实测一次"理解+校正"后 8 个大模型框里 **5 个是空条目**。
  ⇒ 两处都校验: 生成器写盘前、校正器应用前(校正的"补/改"同样会造空条目)。
- **同一时刻只跑一个 L5 判定/生成调用**: 多个调用并发(HIL 环 + 手工链 + 其它工具)会互相挤,
  表现为更频繁的空返回与超时 ⇒ 调用侧串行化。
- **空返回先重试一次并放大预算**(逐条判定给到 12000 仍可能被思考链吃光), 再谈别的; 两类空的成因见 §七/§7.1。
- 判定类产出要能**防误删自证**: 模型有时会把"无像素框的实测 3D 框"判成重复框要求删除 ⇒ 引用层的写权限
  必须真的把这类操作拦下(实测应用结果 `删0` 才是对的, 看到"已应用删N"要查是不是删了别人的层)。
