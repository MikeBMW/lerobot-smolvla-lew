# 真机 eye-in-hand 手眼标定 (现场实录 2026-09-19)

现场: 协作臂(珞石) + 相机装末端法兰旁 + 标定板 CGB-020 **5×4=20 白点圆点阵列 · 20mm 间距 · 白点黑底**
固定在台面(不跟臂动); 机器人处于拖动(drag)模式, **只能人工拖、不能下发运动指令**。
目标: 解 相机↔工具 (T_cam2tool) + 板在基座下的位姿; 验收: 重投影误差达标才落盘。

## 0. 铁律: 先写**合成数据自检**, 再上真机
`tools/handeye_selftest_synth.py` — 造物理正确场景(板在相机前方 z>0!)→ 投影 → 反解 → 必须复原真值。
教训: 合成测试里"板在相机背后"(z 为负)时 solvePnP 返回镜像解, 造成"解算器坏了"的假象。
**自检不过就不要碰真机数据。**

## 1. 八类根因 (按现场踩坑顺序, 每个都让整批数据作废)
1. **位姿源是缓存旧值** ★最隐蔽: 中转 state_*.jsonl 时间戳每秒刷新, 但里面 tcp/quat 是旧值(连续拖 30s 不动)。
   判定: 同刻读 Orin 实时话题 `/robot/tcp_pose` 对照, 值不同即坐实 → 采集**直读话题**, 不用中转流。
2. **四元数顺序**: ROS 侧发布 **x,y,z,w**(不是 w,x,y,z)。别用"首分量最大就是 w"的启发式
   (姿态接近 180° 时 x 最大 → 判反)。对照话题原始字段确认。
3. **单位不一致**: 物点 mm(20mm 间距) + 机器人位姿 m(0.45m) → 投影全错(残差上千 px)。→ 统一米制。
4. **图/位姿不同刻** ★最费时: 相机仅 **0.5fps**; 若"帧龄 ≤3s"就收, 移动快时图是上一动作的 → 逐视图残差 24~91px。
   判据: "**位姿连续 6~8s 极差≈0 + 同期画面内容稳定**"。
   ⚠️ md5 相同的判据无效(自动曝光漂移让每帧字节都不同)。用**内容差异**: 灰度缩略图帧间平均差 ≤2 灰阶
   + phaseCorrelate 位移 ≤0.3px。
5. **只按位置判"动了"**: 纯转手腕时 TCP **位置不变**(TCP 定义) → 必须同时比较**四元数**(≥5°)。
6. **`robot_status.operation_state`**: 手拖前必须 = `drag`; 变 `idle` 后手推不动(编码器纹丝不动),
   易误判成"采集器坏了"。该 JSON 字段被发布者截断(仅 ~110 字符) → estop/collision 读不到。
7. **标定板检测**: 白点黑底 → 必须**反色**再 `findCirclesGrid`; 图案是**非对称 4×5 = 20 点**(行间半格错位)。
   经典 `findChessboardCorners` 会把圆点间隙误检成 4×3=12 角点(假阳性, 曾据此错判一整轮)。
   判图案: PCA 看相邻行是否偏移半格; 自标定 `calibrateCamera` RMS 0.04px 可确认物点模型对。
8. **相机归属判定**: 让操作员**用手捂住怀疑的那台镜头** 5~20s, 我们取图亮度 107→7 即坐实是这台(反之是另一台)。

## 1b. 2026-09-26 复标新踩的坑 (机器人可下发指令, 非手拖)
9. **D405 深度尺度 = 0.1mm/单位**(不是 1mm) ⇒ 读数 4013 = **401mm**。必须 `prof.get_device().first_depth_sensor().get_depth_scale()` 直读确认,
   按 1mm/单位算会得 4m 的荒谬值(历史上曾据此误判"depth 话题勿用")。
10. **相机相对工具装了约 90°**: 相机光轴偏竖直 17.7°, 而工具 Z 轴偏竖直 71.2° ⇒ 照 RANSAC 拟合台面平面法向即可定量确认。
   后果: **绕工具 Z 轴旋转 = 相机视线甩出画面**(±45° 就丢板); 且 180° 倒像(需 rot180)。
11. **640×480 下板检不出** ✗: 20 点只占画面 1.4%(点径 ~10px)。
   ⇒ 必须**切 1280×720 抓帧**(点径 ~29px)才能 findCirclesGrid。内参随分辨率变(fx 655.06/cx 637.41)。
12. **裁剪坐标配全图内参 ⇒ rmse 虚高** ★隐蔽: 板区裁剪后点坐标是裁剪系, 若仍用全图 K 则主点错位 153px,
   rmse 从 0.3px 虚高到 5.5px(会误判"数据不合格")。**必须把点映射回全图坐标再用 K**。
13. **获得姿态多样性的安全手法**: 用 `/move_pose` 下发**绝对 TCP 位姿**(含抬高 +50~70mm),
   因为 move_pose 指定的是 **TCP 位姿 ⇒ 刀尖位置不变, 只有姿态变** ⇒ 取旋转自由度时零刀尖位移。
   配合抬高(≤90mm 红线)后刀尖离台面标定板 75mm(原仅 4.5mm), 彻底消除扎板风险。
14. **纯平移是退化输入**: OpenCV 会直接报 `Not enough informative motions--include larger rotations`,
   解出的 t 要么 0 要么 10^5 mm 级、5 种方法互相差 26 万 mm。判据: **位姿间旋转角 >10° 的对数 ≥3** 才够。
15. **cv2 5.0.0 有 CALIB_HAND_EYE_* 常量但没有 calibrateHandEye 函数** ⇒ 换 `/home/ubuntu/lerobot-venv/bin/python`
   (cv2 4.13.0 有完整函数); gui-venv311 的 cv2 5.0.0 只能做 solvePnP。
16. **板面物理尺寸自标定**: 未知间距时, 用单位间距做 PnP, 再用板像素处的实测深度定尺度,
   迭代收敛 ⇒ 本板算出 19.38mm(真值 20mm, 误差 3%, 可作为交叉校验手段)。

17. **单轴旋转是退化输入（比"角度不够"更本质）** ★★★ 最容易误判:
    绕单一世界轴旋转 ⇒ R_i = Rz(ψ_i)·R_ref ⇒ 相对旋转 R_iᵀR_j 的转轴恒为 R_refᵀ·(0,0,1) ⇒ **恒定**
    实测: 31 对相对旋转的转轴夹角 **中位 0.0° / max 0.0°**（即使单次旋转达到 85°！）
    ⇒ OpenCV 5 种方法全 NaN 或 10^7mm 级，而它自己只报 `Not enough informative motions` 或干脆给垃圾值。
    **判据（必须两条都看）**: ① 位姿间旋转角 >10° 的对数 ≥3；② **相对转轴之间夹角中位 >8°**。
    只满足①仍会退化（本次就是①满足②不满足）。修法: 世界Z偏航 + 世界X倾斜 组合。
18. **`wait_target` 轮询法（不信任服务 success 标志）**: `/move_pose` 的 `success=False` 只代表
    "SDK 等 idle 超时"，**动作其实执行成功了**（实测 TCP 已到位）。 ⇒ 正确做法: 下发后不管 success，
    轮询 `/robot/tcp_pose` 直到 位置<1.5mm 且 姿态<1° 才继续。 **绝不可在运动中重发**（旧版代码这么干过 ✗）。
19. **速度决定成败**: `/move_pose speed=15` ⇒ 20° 偏转要 >30s ⇒ 顶满服务端 30s idle 窗口 ⇒ 报 ROBOT_IDLE_TIMEOUT；
    改 `speed=50` 后同样动作 **3s** 到位。**惯性动作同时把 30s 窗口顶满的，先怀疑速度不足。**
20. **`-20` / `ROBOT_IDLE_TIMEOUT` 不阻塞后续下发**（实测 success=True），无需示教器复位。

21. **`error_code=-50021`：运动学不可达（与超时是两回事）** ★★
    `message='set_target_pose: moveExecution: 指定conf参数下目标点无解, 请检查数值或不设置confData'`
    ⇒ 同样一个位姿「有时成、有时败」的真相：**与当时的关节构型有关**（限位/奇异），不是 Orin 负载。
    修法：① 不设 confData（服务入参 `joint_state` 留空）② 失败就换更小的倾角/换个参考姿态重采，**不要重试同一串**。
22. **独立物理检验：板平放 ⇒ 法向必竖直** ★★★（比 rmse 可靠得多的判据）
    用 findCirclesGrid 检出的 20 点做 PnP ⇒ `R_target2cam[:,2]` 就是板法向 ⇒ 经 T_base_cam 转到 base 系
    ⇒ **偏竖直角度应≈0°**。若偏 90° 级 ⇒ 旋转全错；偏 9~15° ⇒ 方向对但精度不够；偏 30~40° 且集中在斜视角位姿 ⇒ 那些位姿的 PnP 法向本身不可靠。
    **不要用 RANSAC 拟合的平面做此检验**：内点数（≈7万像素）远超板面积（136mm 板在 450mm 处仅占≈2万像素），拟合到的是台面或其它面。
    另注：**“平面法向 vs 相机光轴”与“相机光轴 vs 竖直”不是同一个量**，不要混用（我混过）。
23. **闭环一致性 vs 旋转精度会互矛盾 ⇒ 要分开判**：本次 8 位姿闭环 std=1.74mm，但板法向仍偏 9~15°。
    闭环一致性只证明**位姿间自洽**，不证明旋转绝对正确；两者必须分别取证。

## 2. 解算: 自实现(OpenCV 5 已无 cv2.calibrateHandEye)
- 模型: `T_b2c = inv(T_t2b · X) · Y` (X=相机↔工具, Y=板在基座)。
- **别用自写 Park-Martin 做初值**(本机实现理想数据上都差 7°) → 用**交替优化**: 给定 X 平均出 Y
  (逐视图 `T_t2b·X·T_b2c`, 旋转用 SVD 平均) ↔ 给定 Y 平均出 X; 迭代 5 次, 再 `scipy.least_squares` 精修 12 参。
- 必须输出**逐视图残差**; 剔除 >3×中位的视图前先确认不是"全视图系统性偏大"(那说明数据本身不同刻)。
- 残差 px → mm: `≈ px/fx×Z`(本机 fx≈402, Z≈0.25m → 15px ≈ 9mm)。

## 3. 现场动作卡 (人机在环, 只读采集)
- 前置: 示教器切 **drag**; 人离臂/急停在手; 相机装法**目视确认**。
- 每位姿: 动到位 → **停 8 秒**(采集器自动判"位姿极差 0 + 画面内容稳定")→ 下一个。
- 板要在画面里(整块 ~200px 宽; 距离 10~30cm); 太远(板 <100px)姿态噪声大。
- 姿态多样性: **绕竖直轴转手腕** ±20~30° 最有效(板在画面里原地打转不跑出); 纯平移对平移分量几乎无信息。
  可辨识性: ≥8 视图, 建议 15~16。

## 5. 验收口径 (宁缺勿假)
- 一致性自检(工具转角 vs 画面转角; 取逆不变量)中位 <1° → 数据可用;
- 全解重投影中位 ≤1.5px(仿真口径); 真机手拖条件下按实测如实报(如 3~5px ≈ 2~4mm), **不合格不落盘**,
  报告里写清"多少 px ≈ 多少 mm" + 逐视图残差。

## 6. 结论: 手拖条件下改走"工序坐标系" (2026-09-19 现场拍板)

手拖(示教)模式下机器人上报位姿的非刚性误差 ~20mm → **标准手眼天花板就在这**, 且无法用算法消除。
可用替代(已跑通, 且更省事):
- 标定板固定在工作台 → 它就是**工序原点**;
- 模块在板坐标系 (x,y) mm 由**同一张图**直接算: 板检测(20 点/反色/排镜像) + YOLO 框射线 ∩ 板平面,
  精度 ~1mm, **完全不依赖机器人位姿**;
- 插入目标按 `基座目标 = 板位姿(粗定 ±5mm) × 板内相对量` 下发 → 绕开手拖精度天花板, 换料不重标。
- 工具: `tools/board_frame_module.py`; 整链运行器 `tools/perception_chain_real.py`
  (YOLO + 板坐标系 + VL → `data/scene_state.json` + `macro_memory.perception` + 可回放 jsonl)。
- 判据: 同一场景换视角重算, `模块在板坐标` 应基本不变(实测两次差 ≤2.5mm)。
