# 位姿源"活性"陷阱 — 时间戳新鲜 ≠ 数值新鲜 (2026-09-19 现场最深根因)

> 本文是 `references/eye-in-hand-quat-order-and-collection-gates-2026-09-19.md` ③ 节的**补强+更正**。
> 该节说"操作员说动了而位姿不动 → 查 operation_state / topic hz"。本案**两项检查全部通过**
> (topic 49.5Hz 正常发布、`operation_state=drag`、state 文件 mtime 每秒刷新、行内 `t` 距本机仅 0.04~0.11s)
> 而位姿数值**连续 30 秒一动不动** → 前两小时全花在错误方向上。**先做本文的活性判定, 再谈别的。**

## ① 症状与铁证 (照抄即可复现)
现场: 操作员连续缓慢拖动机械臂 **>20s**, 采集器读到的是**中转文件** `~/zmax_ss_remote/state_*.jsonl`。
```
轮询 30s (每 0.4s 读一行):  TCP [0.3544, 0.2746, 0.5075] quat [0.920, 0.079, 0.383, -0.016]  ← 数值恒定
                            位姿龄 0.00~0.10s (时间戳每次都是新的!)              ← 假象: "数据是新鲜的"
同时 ssh 直读 Orin:          ros2 topic echo --once /robot/tcp_pose
                            → [0.42472, 0.053667, 0.40891] + quat [0.859,0.097,0.470,0.177]  ← 与上面不同 ⇒ 源头是活的
```
**判据**: 同刻"中转值" ≠ "源头话题值" ⇒ **中转链路的数值是缓存旧值**, 整批采集数据全废
(位姿与图像不对应 → 手眼解算连崩: 荒谬平移 47m / 重投影 55~74px)。

## ② 活性判定三步 (先做, 10 分钟, 别先怀疑操作员/相机)
1. **数值变化率**, 不是时间戳: 操作员**连续拖动 20~30s**, 每 0.4s 采样记录 `tcp/quat`;
   数值变化次数 ≈ 0 ⇒ **源不活**(与 `t` 字段、mtime、topic hz **全部无关**)。
2. **对源头**: `ssh <orin> 'source /opt/ros/humble/setup.bash; …; ros2 topic echo --once /robot/tcp_pose'`
   (只读, 非自研进程) — 与中转值逐位对照; 不同 ⇒ 用源头。
3. **端到端延迟**: 同一轮询里同时打 **画面变化量** `mean(cv2.absdiff(img, ref))` 与 TCP —
   两者**同时**跳变 ⇒ 图与位姿都跟手; 只有一方跳 ⇒ 另一方是缓存。
   (本案附带证据: 操作员抬臂 30cm 后, 画面里**板直接出视场/检不到** ⇒ 相机确实在法兰上。)

## ③ 修法: 采集/标定**位姿直读源头话题** + 连读一致性判据
采集器 (repo `tools/handeye_collect.py` v6) 的做法, 可直接复用:
- 每个候选位姿 **连读 3 次** `ros2 topic echo --once /robot/tcp_pose` (每次 ~2~3s, 间隔 1s);
- **3 次位置极差 ≤1.5mm 且四元数夹角极差 ≤0.6°** 才算"真的停稳" → **这一条同时否掉了"缓存旧值"**
  (缓存值永远是 0 极差, 但与之配对的图会随臂变 ⇒ 解算自检必然不过);
- 图像侧: 帧龄 ≤3s **且** md5 与上次保存不同 (慢相机 ~0.5fps);
- 位姿变化判据: 位置 ≥8mm **或** 姿态 ≥5° (纯转手腕要算新位姿);
- 每个样本落盘 `tcp/quat/pose_spread_mm/pose_spread_deg/frame_age_s/board_points/src`,
  并**逐位姿回报操作员** `✅板20点 / ⚠️板不在画面` + 距上次 mm/°。
- 现场操作卡: **"停稳 10~15 秒再说好"** (要 3 次位姿读数 + 一张新帧) + **"板要在画面里"**。

**解析口径 (实测)**: `ros2 topic echo --once /robot/tcp_pose` 文本里只有 9 个数字
`[sec, nanosec, x, y, z, qx, qy, qz, qw]` → `pos = nums[-7:-4]`, `quat = nums[-4:]`;
按"≥14 个数"解析会**永远失败并静默重试**。写完 reg 解析后必须**回读打印一次**再进循环。

## ④ 顺序修正 (重要)
`eye-in-hand-quat-order-and-collection-gates-2026-09-19.md` ① 的结论 (顺序 **xyzw**, 已逐位对源头确证)
仍然有效。但要补一条**因果顺序**: 本案"工具动了 34~50mm 而板在画面里不动"曾被我判成
"换了相机/板在臂上"; 真因是**位姿流是缓存旧值**。
⇒ **先证位姿源活性, 再谈相机装法/靶标布置**; 顺序反了会浪费一个下午并误导现场操作员。
相机身份的唯一硬判定仍是**遮镜头实验**(测量亮度: 107.9 → 7.4 → 103.9 即同一台; 亮度扫描脚本见
`scripts/brightness_poll.py`)。

## ⑤ 通用教训 (跳出本项目也成立)
- **"数据新鲜"有两个维度: 时间戳新鲜 ≠ 数值新鲜**。中转/缓存/回放链路极容易给新时间戳配旧值:
  文件 mtime 在刷、行内时间戳是新的、话题频率正常, 而 payload 是冻结的。
  **判定活性只能看 payload 的变化率**, 任何时间元数据都不能作为证据。
- 采集类任务的设计原则: **位姿/真值只从源头直读**, 中转链路只用于"看一眼", 不进数据集。
- 反复"操作员说动了但系统没看到"时, 优先怀疑**自己数据链路的缓存**, 而不是人的操作。
