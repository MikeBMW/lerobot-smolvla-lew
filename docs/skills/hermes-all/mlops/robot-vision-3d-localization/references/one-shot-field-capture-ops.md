# 现场一次性动作的链路彩排 + 长驻进程卫生 (2026-09-18 实测, 差点白费一次现场动作)

适用: 标定/自监督数据**必须由人在现场做一次性动作**才能拿到 (拖机器人走 10 个位姿、示教零点、
摆件录样本)。这类动作窗口只有几十秒, 一旦跑在错误的代码/假设上就是"白做 + 存进假标定"。

## 1. 叫人动作之前的固定顺序 (顺序错就会白做)

1. **改完代码 → 先重启长驻进程**。长驻采集/推理进程在 import 时就把模块代码读进内存了,
   改动不会热生效。实测踩过: 采集进程 17:56 启动, 之后我给解算器加了"真机内参 K 模式 +
   R_rel 联合估计", 进程里跑的还是旧代码 —— 若这时叫人拖臂, 拟合会落在**最差配置**
   (不估 R_rel, 中心实测偏 77mm), 且观测会写进同一条 obs 流水。
2. **确认进程真的在跑新代码**: 看日志首行/启动行里的版本痕迹 (例: 第一行应出现
   `内参已知 (fx=394.1)`; 旧代码没有这句) + 确认**单实例**。
3. **先在合成数据上彩排整条链路**, 用**现场同一套函数** (不是"再写一个简化版"), 状态/产物写
   `~/zmax_data/rehearsal/` 或临时路径 —— **绝不碰现场的状态文件**。
4. **彩排必须有反例**: 除了正例 (前提成立 → 通过并落盘), 还要断言一个前提不成立的场景
   **必须被拒绝落盘**。实测: 正例 rms 0.86px/前提自证 IoU 0.874 → 落盘, 重载后留出 40 帧
   8 角点误差 5.23mm; 反例 (工件静放台面 + 机器人空手走位) rms 7.67px/IoU 0.226 → 拒绝。
   反例才是保险: 它保证现场录到的不是"要的东西"时, 链路自己拒绝, 而不是把假标定存下来
   污染之后每一帧。
5. 然后才叫人动作, 并**说清三件事**: 要你做什么 (动作/幅度/朝向) · 多久 (几十秒) · 我这边会
   自动发生什么 (攒够→拟合→前提自证→落盘→每帧出结果), 以及过期怎么重跑。

## 2. 长驻进程卫生 (踩过的两个坑)

- **别用 `pkill -f <脚本名>` / `pgrep -f <脚本名>` 直接 kill**: 会匹配到自己这条 shell 的命令行
  (实测被执行 SIGTERM, 循环里连着丢了一次)。用括号模式断掉自匹配:
  `pgrep -f "box3d_live[_]box.py"`, 或按 PID, 或直接用 harness 的进程句柄 kill
  (后台任务用 `process(action='kill', session_id=...)` 最干净 —— bash 包装层杀了子进程不一定跟着走)。
- **杀完必须复查**: 新进程启动后再数一次实例数 (bash 包装 + python 子进程会被数成 2~3 行,
  不代表多实例双开)。旧的 obs 流水可以继续用 (同一路径追加即可), 但日志会被覆盖 → 需要旧日志
  先备份。

## 3. "机器人静止"不是 bug

自监督/多样性门槛在静止输入下**必须拒绝**: 实测采集 1800+ 帧而 TCP 变化 0.0mm → 位姿多样性
(帧数/平面性/姿态散布) 不过 → 正确地不拟合、不落盘。见到"攒了很多帧却标定不出来"先查
**TCP 是否真的动过**, 别去调算法门槛。
