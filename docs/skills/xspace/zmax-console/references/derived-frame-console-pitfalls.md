# 派生画面控制台 + 产线相机源接入 (2026-09-24 外观质量检测窗口实测)

适用: 做「相机源(HTTP/工控机/OPT) → 裁切·拉伸派生画面 → 推理 → 显示/标定/训练」这类窗口。
每条都是现场被老倪抓出来的真 bug 或真风险，附可复用的回归断言。

## 一、四条铁律 (派生画面类窗口)

### 1. 派生画面必须与"原始帧刷新"解耦
- 症状: 圈选/过曝切除的结果**闪一下就变回坏图** (老倪: "拉伸后还是一片白" / "闪一下又变回坏图")。
- 根因: 500ms 定时器 (`_tick`) 每次都把**原始帧**重新塞进判据图面板 → 把派生结果冲掉。
- 规矩: **定时器只刷状态显示**; 画面更新只由显式动作驱动 (取图/拍照/框选/开关切换/自动刷新)。
  实现上给"派生源"分支提前 return，不要走 `_set_frame`。
- 回归: `for _ in range(3): w._tick()` 后画面逐位不变 (`np.array_equal(snap, w._last_rgb)`)。

### 2. "显示帧"和"推理帧"必须同时换 (最隐蔽的一条)
- 症状: 用户圈了框、画面也换了, **检测结果还是旧的** (老倪: "金手指检测没有拉伸到金手指部分")。
- 根因: 只调 `widget.set_frame_rgb(img)`, 没更新抽象层 `self._last_rgb` —— 而 `run_skill()` 吃的是后者。
- 规矩: 所有改画面的路径统一走 `_set_frame(img, tag)` (同时更新 显示 + `_last_rgb` + 标签)。
- 回归: `list(w._last_rgb.shape[:2]) == list(meta["out_hw"])`；
  更强的写法是"显示帧必须命中当前生效源的 meta"(见下 §三)。

### 3. 覆盖 (override) 不许被无关开关门控
- 症状: 「手动框选」在「过曝切除」关掉时被无视 → 掉回工厂图。
- 根因: 手动分支条件里混进了无关开关 (`and chk_expfix.isChecked()`)。
- 规矩: 优先级链**写死**并**在状态行点名**: `手动覆盖 > 自动算法 > 原始源`;
  界面显示 `判据图来源: 手动框选 · 框 (x,y,w,h)` / `自动裁切(原始图)` / `工厂拉长图`。
- 回归: 关掉另一个开关后, 手动覆盖**仍然生效** (判据图尺寸 == 手选框×k)。

### 4. "人圈不准"要给一键兜底
- 加「🎯 识别<目标>并框」: 算法定位 (边缘密集 + 未过曝的条带) → 自动设为目标区 →
  框**画在原始图上** + 输出坐标与框内指标。
- 实测对照 (同一帧): 人手圈 Tenengrad **8551** (且位置偏离目标带 541px) vs 自动框 **22213**。
  两个数字并排, 用户自己就能判断谁对。

## 二、两条工程纪律

- **生产相机禁用"连续真拍"**: 自动刷新**默认必须是不拍照模式**; 选真拍时**强制最小间隔 ≥10s** + 明确告警。
  实测教训: 「自动刷新·真拍」被开着 → 每 5s 真拍一次产线, 一次会话累积 **130+** 次拍照
  (审计流水能查到, 也是唯一的发现途径 → 任何会触发真机的动作都要写审计流水)。
- **"我看不到屏幕"就让窗口落盘**: 每次拖框/取图写 `reports/<console>_state.json`, 含
  `roi(k/来源/画面尺寸/框内指标/相机)`。没有截图通道且不读图时, 读这个文件即可核对用户的圈选与结果,
  不用让用户转述。配套: 需要人眼看的结果一律给**数字**(框内饱和%/死白行/Tenengrad), 别只说"看起来对"。

## 三、验证脚本设计 (这类窗口的取证套路)

- **断言对象选"显示帧"+"与之匹配的 meta"**, 不要假定哪条路径胜出。
  踩过的坑: 断言拿 `_roi_meta` 比 `_last_rgb`, 而实际生效的是 auto 路径 → 假红;
  正解: 遍历候选 meta, 取 `out_hw == 显示帧尺寸` 的那条再校验 (并记录"命中哪条")。
- **前置状态要显式清干净**: 记住的 ROI/持久化配置会让"自动路径"不再触发 → 测自动路径前先清
  (例: `w._manual_roi = None`), 否则测的是另一条路。
- **计数类断言要看"事件类型"**: 审计流水里失败记录也会追加 → 数"不新增真拍"必须只数
  `action == capture_detect 且 http == 200`, 不能数总行数; 且基准取在动作**之前**。
- **容忍后台干扰**: 产线上可能有别的窗口同时在拍照 → 这类断言给 `≤1` 的容差并打印 Δ。
- 剪贴板类断言**只能在真桌面** (`DISPLAY=:0`) 跑: offscreen 后端 `clipboard.image()` 恒 0×0。
- 真桌面还要查: 窗口在 `availableGeometry` 内、**每个按钮 `width() ≥ sizeHint().width()`**(防截断)、
  最大化 `isMaximized()` + 宽≈屏宽。
- 控件最小宽的实现坑: `_btn` 里 `setMinimumWidth(sizeHint())` 在**字体解析前**算 → 之后会被挤截断;
  正解: 布局落定/showEvent 后再 `_fix_min_widths()` 钉一遍, 并把控件多的行**从窄栏移到整宽行**
  (实测: 540px 画面条里塞 6 个控件 → 「记住此框」140<148 被截字)。

## 四、AOI 相机源侧的口径 (2026-09-24, 老倪定)

- **拉长口径 = 只拉短边 ×k, 长边不动** (k 默认 **2**, 界面可调 1~6)。
  原工控机把 1600×250 的窗映成 2448×2048 (横 1.53× / **纵 8.2×**) → 就是"拉得太长"的来源。
  实测: 条带 1623×135 → ×2 → **1623×270** (k=1/2/3 → 短边 135/270/405, 长边恒 1623)。
- **别依赖工控机 `?kind=topview`**: 同一天出现过 ①过曝死白(饱和 61.5%/死白行 532/960)
  ②近乎空帧(std 1.5 · `crop_info.score` 0.29 规整截取失败) ③正常; 而 `?kind=origin` **一直是好图**。
  ⇒ 判据图**以原始图为源自己裁切**(切过曝带 + 左右死白列 + 只留边缘密集条带 + 短边×k)。
- 每次取图后量一下可用性: `std` / 逐行均值波动 / `crop_info.score`; 不达标就如实报"工厂图失效"。
  相关技能 `zmax-aoi-service` (用户所有, 未采纳 curator 管理) 里有端点/端口口径。
