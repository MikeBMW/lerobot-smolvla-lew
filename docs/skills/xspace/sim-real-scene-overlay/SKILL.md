# 真实场景叠加 / 仿真↔真机几何投影

## When to Use
- 用户要"把仿真场景的边界框叠到真实视频流上""虚拟场景与真实场景叠加""同步渲染"。
- 需要把 base 系 3D 点/盒投到真机相机像素（或反向：像素 → base）。
- 要做真实深度建图（深度 + 手眼 → base 系点云/语义物体）。
- 验证手眼外参到底准不准（**正投影**比旋转法向检验靠谱得多，见下）。

## 核心: 一条链, 三个参数, 全实测
```
p_base --(实时 TCP 位姿真值)--> p_tcp --(手眼 X=T_cam2tcp)--> p_cam --(内参 K)--> (u,v)
```
```python
def base_to_px(P_base, K, X_cam2tcp, tcp7):   # tcp7=[x,y,z,qx,qy,qz,qw] base系 m
    R_g, t_g = quat_to_R(tcp7[3:7]), tcp7[:3]
    R_x, t_x = X[:3,:3], X[:3,3]
    P_tcp = (R_g.T @ (P_base - t_g).T).T
    P_cam = (R_x.T @ (P_tcp - t_x).T).T
    z = P_cam[:,2]                      # z<=0 的必须丢(相机背后), 否则投出幻影框
    return np.stack([K["fx"]*P_cam[:,0]/z+K["cx"], K["fy"]*P_cam[:,1]/z+K["cy"]],1)
```
3D 盒 → 2D 框：8 角点全投，取 min/max；**角点 x/z 只有 4 个有效时就不要画**（近平面劈开）。

## 内参按**流的分辨率**选, 不能换算
D405 的 1280×720 与 640×480 是**不同 FOV**（不是 2× binning）：
655.06/640 = 1.02 vs 394.06×2 = 788 ⇒ 720p 视角更宽。用错分辨率内参 ⇒ 主点错位。
`ros2 topic echo --once /realsense/color/camera_info` 取真值，别信记忆里的数。

## 验证: 正投影 vs 图上实检（首选, 比旋转检验强）
用**已知 base 位置的点**（标定板中心由多姿势闭环解出）**逐位姿**投回**该位姿自己的图**，
和该图实检的质心比。实测 8 位姿：**中位 5.2px ≈ 3.1mm**，最差 9.9px（斜视角位姿）。
- 口径必须同源：解算器闭环若用 `OBJ.mean(0)`（20 点质心），比对面也得取**实检点云质心**，
  不能比"图案原点" —— 否则差一个 68mm/40mm 的常量偏移，看起来像"算法错"。
- **闭环一致性(std) ≠ 旋转正确**，两者要分开取证。旋转精度想单独看，用板面法向投 base 系判
  偏离竖直多少（小角度好、斜视角 PnP 本身不可靠）。
- 双链收敛是最强证据：
  · `det` 链（纯图像）YOLO 实检框中心
  · `sim` 链（纯几何）深度 3D → 手眼 → 投影框中心
  实测中心差 **2.1px**（215mm 处≈1.1mm）⇒ 证明投影是真几何而不是画上去的。

## 视频流叠加的工程做法
- **独立渲染线程 + 独立帧槽**，只在开启叠加时才付出"解码→画→重编码"开销；
  原来的"JPEG 直转"最快路径**一字不改**（多条 RTSP/MJPEG 消费者的实况流禁不起往里塞 decode）。
- 规格文件（几 KB JSON）**每帧重读** ⇒ 外部生成器一写就生效，服务不用重启。
- 规格按 **provenance 分源**（sim/vlm/det），生成器**只替换自己那一类**（`merge_origin`）；
  若整体覆盖会把别的来源框冲掉。
- TCP 位姿**按 2s 缓存**：投影要实时位姿，但读 Orin 有开销，不能每帧读。
- 画面里必须画**真值带**（帧龄/时间/TCP/手眼/框统计）——不然无法自证状态，且用户会把画面当结果。

## 多相机并存（臂上 + 笔记本内置 + MAXHUB 电视顶摄）
- **路由写成正则通用表**，别逐条 `elif`：`^/(overlay/)?<name>\.mjpg$`、`^/snapshot/(overlay_)?<name>\.jpg$`、
  `/stats` 按 `_FRAMES` 现有键动态枚举 ⇒ 今后加第 4 路相机**不用动路由/统计**（只加 worker 和参数）。
- 相机源名和**物理相机身份**要分开：源名（arm/local/local2）是逻辑槽，身份必须
  **读 `/sys/class/video4linux/videoN/name`** 并随 `/stats` 下发 `label`，页面/画布直接显示。
  实测本机：`video0 = WT15: MAXHUB-Camera`、`video2 = Integrated RGB Camera`；
  靠"--local-dev 0 就是笔记本"这种记忆判断，换机器/插拔顺序一变就全错，页面还会误导用户。
- **真几何投影只对做过手眼标定的那一路成立**（臂上相机）。本机/USB 相机没有手眼，
  生成 sim/scene 框时要**如实拒绝**（"本机相机未标定"），不能假装画得上；
  纯 2D 来源（YOLO 检测 / VLM 理解）才三路都行。
- `/gen` 必须带相机参数（`?kind=…&cam=…`），否则"给哪一路生成框"只能静默落到默认路。
- 一路掉线（如 arm 走 Orin 网络超时）不能让整屏空：**只有真取到帧的相机进画面**，
  其余在真值带里标 `未接: xxx` —— 假画面比没画面更坏。

## 画布节点上的多路拼图
- 节点 `video_pixmap` 放一张**自己拼的 2 列马赛克**（每格 286×162 + 顶部 20px 真值带），
  逐格标 `相机名 · 框数 · 真值链 OK/断 · 规格龄` ⇒ 一眼看清哪路有框、哪路掉线。
- 拼图**自带真值带**后要把节点 `video_overlay` 置空，否则和 `paint()` 画的小字重叠成糊字。
- QPixmap/`QPainter` 只能在 GUI 线程建 ⇒ 拉帧在 worker 线程，**拼图与赋值放主线程 QTimer**；
  多路时节点自动放大（3 路用 580×350，单路 380×246）并在**放大前**做重叠检查。
- 验收要**逐格裁开数像素**（std / 近黑占比 / 两格互不相同）：只断言"pixmap 非空"会把
  "只有一路有帧"误判成"三路都通"。

## 按钮打不开"大图页"的三个真根因 (2026-09-27 实测, 挨个踩过)
1. **只等 8s 且只按标题认窗 ⇒ 窗口留在外接屏**: 本机 chromium 新窗开在**外接屏**(wmctrl 实测
   3884,288 3184x1784, x≥3200 = 第二块屏), 而窗口标题要等页面加载完才更新。8s 到点就 return
   "窗口没认出来, 未最大化" ⇒ 用户在他那块屏上**什么都看不到**(页在另一块屏且没最大化)。
   定式: 启动前记下已有窗口 id → 按"**新出现的 id**"认窗(不靠标题) → 等足 25s → 搬屏+最大化+激活
   **各做 2 轮** → **读回 wmctrl -lG 几何**并如实说落在哪块屏(不在控制台那块屏就别写"已最大化")。
   判断在哪块屏: `x` 与 XSpace Studio 窗口的 `x` 差 <200 即同屏(本机 132 vs 3884)。
2. **工作线程里调 Qt ⇒ 整个控制台 Aborted**: 兜底分支的 `QDesktopServices.openUrl()` 跑在 worker 线程 ⇒
   实测 `QThread: Destroyed while thread is still running` + `Fatal Python error: Aborted`(进程死,
   窗口全没)。浏览器兜底只允许纯进程调用(xdg-open / gio), 绝不碰 Qt。
3. **画布节点太小会被当成"小窗口"**: 572x344 的拼图在用户眼里就是"打开了一个小窗"。节点放大要
   **逐级尝试**(900x560 → 700x430 → 580x350 → 420x270): 一次直接要最大尺寸, 遇到邻居会被整体否决
   `有邻居 → 保持 280x110`, 反而比原来更小(实测踩过)。

- 验收(实测口径): 各入口 HTTP 200 且字节一致 · 真浏览器 DOM 里 `img.naturalWidth>0` · 横向溢出 0px ·
  JS 错误 0 条 · 逐个点过 原始图/并排/全屏/退出 · 其它通道端点仍 200(别把总览的路由删了)。

## 把「仿真元素」搭成一个场景投到真机上 (光模块/料盘插槽/插孔位置, 2026-09-28)

用户口径: 「你有三个相机 + 深度信号, 看着黑色治具, L2 还能 YOLO —— 你来指导,
把仿真元素都叠加到这个场景里: 光模块、料盘插槽、插孔位置」。**元件必须有来源、可查、不猜**。

**元素三来源 (每件都要在 `source`/`note` 里写清, 页面上才敢信)**
| 来源 | 拿什么 | 实测例 |
|---|---|---|
| 现场示教真值 | `data/skills/l2_atomic/taught_points.json`(slot1/slot2 抓握点) · `~/zmax_data/real_cell_geometry.json`(hole/goal/peg_head) | 差 40.9mm ≈ 模块长 40mm ⇒ 孔口/插到底自洽 |
| 深度实测 | L5/YOLO 框 + **框中位深度** × 手眼 × TCP 真值 | 模块1 (503,393,122)/(292,184) · 模块2 (513,255,126)/(420,181) |
| 手眼闭环实测 | 标定板等（本帧视锥外时**如实标 skipped**, 不画假框） | 视锥外 ⇒ 服务自报 `框退化(视锥外)` |

**工具 (可复跑, 都在 `tools/`)**: `gen_scene_cell.py`(组装元素→写 objects3d.json→`merge_origin(origin='sim')`→打印每元素 base/像素/画面内%→两层校验→`--report` 出 `reports/scene_cell_elements_*.{json,md}`) ·
`compare_scene_sources.py`(三源框对照: 仿真/L2 YOLO/L5 大模型, 算框心差+IoU) · `probe_anchor_color.py`(锚框内颜色采样, 定掩膜阈值用)。

**两层自校验 (出结论前必跑)**
1. **往返一致**: det 像素 → 深度 → base → 投回像素，应回到**它自己的来源框**。实测 **0.4px** ⇒ 手眼/TCP/K 自洽。
2. **凹陷检查**: 槽/孔是凹的 ⇒ 投影框**内**中位深度 vs 四周环带中位深度，Δ>+2mm 才算落在凹处。
   实测示教槽位 Δ=+4.1/+8.0mm、插孔 Δ=+2.3/+3.5mm、实测槽位 Δ=+4.0mm。
   注意: 环带里可能含**抬高结构**(料盘边) ⇒ Δ 只是"是否落在凹陷处"的辅助判据，不作唯一结论。
3. 最强证据仍是**三源交叉同一点**: L5「光模块」(291,181) ↔ L2 YOLO peg (292,185) ↔ 深度实测 (292,184)。

**三个真坑 (都踩过)**
- 🔴 **示教槽位 ≠ 当前被占用的槽位**。料盘是多槽的；`slot1/slot2` 只是"被教过的两个抓取点"，
  本帧看到的模块在别的槽上（实测距 slot1 182mm）。⇒ 示教点只能标成「示教·槽位N」，
  **不要**给它贴"光模块"标签；"光模块"这件元素必须来自**当前帧的实测**。
- 🔴 **纯颜色分割不可靠**：该曝光下光模块是很暗的灰绿(BGR≈(66,76,65)、HSV≈(45,36,77))，
  严阈(H 35~95,S≥60)只覆盖 14~17%；放开阈值后又把绿色电路板/线缆一起圈进来（实测 **22 个连通域**），
  且把同一个模块量成两个（偏移 20.8px）并漏掉第二个模块。⇒ 定式 = **检测框锚定 + 框中位深度**，
  颜色掩膜仅作 `--green-refine` 可选项且**默认关**（阈值理由写在 `--help` 里）。
- ⚠️ **单目视场装不下整个工位**：示教槽位/插孔与"相机此刻看的模块"会分别在画面两端，
  标定板干脆在视锥外。⇒ 元素清单必须报**画面内/画面外 + base 坐标**，画面外的不静默丢；
  想让全场景都可见得换相机位姿（或对**固定顶摄**做平面单应，那需要 3+ 已知 base↔像素点）。

**验收口径**: `mode=det+sim+vlm` · `_overlay_info[arm].origins` 计数(sim=元素数, det/vlm 各自) ·
`skipped` 列表带原因 · 页面 `nSim/nVlm/nDet/nSkip` 与之一致 · 叠加帧 vs 原帧差异像素占比(实测 28.9%) · VLM 回读确认。

## 3D 线框 + 点选删除 + 提示词重标 (2026-09-28 老倪: 「2D 是 2D 的, 但人能感觉出三维空间」)

需求原话: 「你要在手臂相机上画出 3D 的物体边界框；再增加一个用户交互功能：用户可以选择
每个叠加的 3D 边界框，可以删除错的边界框；然后视觉语言大模型再次标注，期间我可以通过
提示词跟你互动，指导你标注的方向。」

**一、画真三维线框(不是最小外接矩形)**
- 角点顺序定死：`bits=[(i,j,k) for i in(0,1) for j in(0,1) for k in(0,1)]` ⇒ 索引 = 4i+2j+k，
  于是 12 条棱写成常量表 `EDGES`（差一位即相连），永不再算。
- 投影前必须先取**相机系 z**（`base_to_cam`）: 任一角点 `z<=0.05m` 或整盒出画 ⇒ 如实跳过并报原因,
  不能拿 `1/z` 的垃圾值画线（否则出现“飞框”）。
- **进深靠画法**: 按棱的平均相机 z 排序，**远的先画且细(1px)/暗(×0.55)、近的粗(2px)/亮**，
  八角点再画点(近点半径 3/远点 2) ⇒ 人眼立刻读出立体感。这是“3D”与“2D 矩形”的差别所在，
  不是换个颜色就能替代。
- 只有 `box3d` 的框才画线框；det/vlm 只有像素框 ⇒ 仍画矩形并标注 kind=2d（不假装有 3D）。

**二、点选/删除：稳定 id + 删除清单落盘**
- id 规则 `origin|label`（重名追加 `#2`…）——**同一件东西重新生成后 id 不变**，
  所以删除能持久；否则“删了又冒出来”。
- 删除清单存 `spec["deleted"][cam]`（不是内存变量）⇒ 重生成 sim/det/vlm 都不会把它带回来。
- 端点分工（与点动同规矩）：`GET /boxes` 只**读**（这帧实际画出来的框 + 像素几何 + id + 已删清单，
  叠加线程没跑时现场重算一遍，不返回空）；`POST /boxes/delete` · `POST /boxes/restore` 才能**改**。
  不给 ids 的 restore = 清空删除清单。

**三、页面命中层：SVG 必须精确覆盖“图像渲染区”**
- `object-fit:contain` 会在容器里留黑边 ⇒ 直接 `inset:0` 铺满会**整体错位**。
  定式：按 `naturalWidth/Height` 与 `clientWidth/Height` 算 `sc=min(...)`，把 SVG 的
  left/top/width/height **设成图像的实际渲染矩形**，`viewBox='0 0 nw nh'` ⇒ 之后 SVG 坐标 == 图像像素。
- 命中区用**粗透明描边**（stroke-width 14~16）画同一形状（3D 用 8 角点的凸包，与 JPEG 里的线框同形），
  命中概率才够（细线几乎点不中）；点击后黄虚线高亮 + 列表同步选中。
- 每 1.5s 重新拉 `/boxes` 重绘 ⇒ **DOM 元素被重建，自动化工具握着的 ref 会失效**；
  取证要点名重查（`querySelectorAll('#svgOv [onclick]')[i]`）而不是用旧 ref。
- 模型给的 label 会进 HTML 属性 ⇒ 白名单过滤后再拼，别让怪字符把页面搞死。

**四、提示词互动（人删错框 + 给方向 → 大模型重标）**
- 把操作者指示拼成**最高优先级段**（明写“与上面默认口径冲突时以本节为准”）；
  并把**被删的 label 当负项**（不要再给）、保留的当正项（沿用口径）一起传下去 ——
  只删不改提示词，下一轮模型会照旧给出来。
- 规格里记 `hint/negatives/keep/at/model`（`merge_origin` 的 meta）⇒ 页面显示“上轮指示”，
  这一轮标注到底被什么指导的可以追溯。
- `/gen` 支持 `&hint=<url 编码>`，仍走后台线程 + 卡死自愈（VLM 单次 5~140s）。

**五、验收口径（实测）**: `/boxes` 框数/3D/2D · 真浏览器点框后 nSel=1 且删除按钮解禁 ·
点删除后 `n_3d` 减 1 且该框从画面与清单同时消失（两帧差异像素落在被删框区域内） ·
恢复后回来 · 带提示词重标后**被删的 label 不再出现**且规格记录了 hint/negatives。
回归脚本：`tools/verify_overlay_interactive.py`（`--no-vlm` 秒级）。

## 把 3D 视图(dreamview 仿真)的元素叠到臂上相机 (2026-09-28 老倪: 「这里可以看到所有元素的边界框, 你要把这些叠加到手臂相机上」)

**先立口径, 不要直接投仿真坐标**: 仿真世界(metaworld 几何)与真机 base 之间**没有可信的相似变换** ——

## 交互删除 / 重新生成 的两个“会把框搞丢”的真因
- **“重建/重新生成”按钮必须是按 origin 合并, 不是整体覆盖**: `save_spec(build_from_sim())` 会把
  别家(vlm/det)的框和用户的**已删清单**一起抹掉 —— 老倪点一下「重建仿真元素」就能撞上。
  修法 `merge_origin(load_spec(), cam, origin, boxes, meta)`, 并在返回语里报“保留其它来源 [...]”。
- **删除必须按稳定 id 落盘**(`spec.deleted[cam]`), 且跳过原因要写明"用户删除", 否则重生成后又冒出来。

## 画 3D 盒: 近乎正俯视时「只画线框 = 看不出三维」(实测倒逼的定式)
老倪要的是「人能感觉出三维空间」。同一件事我做了两轮, 第二轮的根据是**独立像素复核**:
- 只画 12 条棱的线框 → 复核结论「不明显」: 全图斜向像素占比 **0.0~0.1%、零透视收敛**,
  读起来像「歪了一点的双线矩形」。原因说透了: 相机近乎垂直向下看, 盒子的近/远棱投影**几乎平行**,
  “近粗远细”只能暗示厚度, 不足以建立体感。
- ⇒ **给“体”上色**(照仿真 3D 视图的做法): 整体轮廓淡填 ~16% + **顶面再加浓** ~18%。
  顶面 = 角点位序 k=1 那四个点(`index = 4i+2j+k` ⇒ 1,3,7,5), 俯视时一定看得见。
  填法 `cv2.fillConvexPoly(convexHull(8 角点投影))` ⇒ **不可能溢出**(其外接矩形就是框的 xyxy)。
- 取证口径: 叠加帧 vs **同刻**原帧, 逐框算区域平均色偏是否朝该来源色(实测 ΔG +16~+105 / ΔR 负);
  同时算「原帧 vs 原帧隔 1s」的噪声基线(实测 0.88%)扣掉 —— 否则会把相机噪声/臂动当成“染色溢出”冤枉自己。

## 交互键位: 选中后直接敲键就删 (老倪: 「不要再向下找屏幕上的按钮了, 太麻烦」)
- `Delete`/`Backspace` = 删选中 · `Esc` = 取消选择 · `Ctrl+Z` = 撤销。
- **键盘焦点分流**: `ev.target` 是 INPUT/TEXTAREA 时键盘归输入框(否则写提示词时按删除会把框删了)。
  取证时要**把 keydown 派发到真得到焦点的元素上**——派发到 `document` 时 target=document,
  合成事件根本走不到守卫分支, 会得出“守卫失效”的假阴性。
- **撤销必须按实际删除顺序**: 规格里的 `deleted` 清单是排序去重的, 拿“最后一个”当“最近一次”会撤错东西(实测发生);
  在页面里另记一条会话内的删除栈, 空栈才退而用清单末尾。
- 选中后应在**画面内浮出操作条**(已选 N/删除/恢复/取消) —— 用户不想为了点按钮滚屏。
- 点画面空白处: 有选中时先取消选择, 不要直接跳全屏(否则“选好了想点别处”就被搞成全屏)。

## 叠加上色/面染色的**取证铁律**: 同帧 A/B + 标签不许压住盒子
面染色这种"画在半透明层上"的改动, 跨帧比对**测不出来**: 拿"叠加帧 vs 原帧"做差会被机械臂运动/曝光漂移淹没,
外部复核对着一张运动中的帧得出「零像素半透明」的结论, 而我当时信了口径没自己验。正确做法:
- **同帧 A/B**: 同一输入帧、同一 TCP, 只翻染色开关渲染两遍再逐像素做差 ⇒ 差异**只可能**来自染色本身。
  留 `ZMAX_FILL=0/1` 这类开关就是为这个 (scene_overlay: `_FILL_ON` / `FILL_ALPHA` / `FILL_TOP_ALPHA`)。
  判据: 凸包内「Δ>6 的像素数」远大于 0; 若为 0~个位数 ⇒ 没落笔或被盖死。
- **小盒跑不出体积感, 先查标签底片**: 标签是**不透明**色块, 贴在盒子中心时会 100% 盖住凸包
  (实测 398px 凸包 - 397px 被自己的标签盖住) ⇒ 染色和棱线全白做。**标签一律放盒子轮廓外**(上方不够就放下方)
  + 一条 1px 引线指回盒子, 否则标签飘着不知道是谁的。
- **大盒按面积减淡**: 台面框 14 万 px 按小盒的 alpha 填上去, 整屏糊成一块绿, 反而看不清物体
  ⇒ `alpha *= min(1, 8000/area)` 封顶 0.45 倍。
- 近正俯视相机下, 厚度 10mm 的台面盒**天生只能读成"一层板"**: 体积感靠"顶面浓+侧面淡"的两调, 别期待斜边/透视收敛。

## 真 3D 盒的定式: 位置/尺寸/朝向必须**全实测**(标称+轴对齐必被老倪一眼看穿)
老倪原话:「边界框都不对…光模块是一个3维的长方体, 要8个顶点」。查下来两条硬伤:
- **尺寸写标称**(如 40×16×12mm)、**朝向轴对齐**(`R=None`): 料盘上的模块在画面里是斜的,
  轴对齐长方体投影出来必然与物体错开一截。实测该模块其实 ~120×68×20mm、斜 ~6° —— 标称 40mm 错了 3 倍。
- **位置只取框中心那一点深度**, 没量足印 ⇒ 长宽是编的。
量法定式(每步可复算) → 工具 `tools/measure_module_cuboid.py`:
1. 锚框(L5/YOLO 像素框)= 用户看到的物体轮廓, 只当"往哪儿看"
2. 中心 40% 区的有效深度中位(丢 0 值/超量程)
3. **角点深度用"框内物体层拟合的深度平面"**(±20mm 带内 lstsq → d=a·u+b·v+c → 代入四角)。
   取角点邻域中位会吃到框外的台面/槽壁(更远), 足印被拉长 **3 倍**。
4. RealSense 深度 = **沿光轴的 z** ⇒ 直接成相机系点云再变换到 base, 不用猜平面(px_to_base_ray 是有深度前的退路)
5. base XY 足印 minAreaRect ⇒ 实测长/宽/朝向
6. 高度 = 物面 base z - **周围最深面(槽底)的 base z**(P20), 别用中位: 模块坐在凹槽里, 中位量到的是比它还高的台面
自检判据: **8 顶点投回像素的 xyxy 与锚框的 IoU**(0.65~0.8 合格)。比"IoU vs 分割掩膜"靠谱 —— 不受分割质量影响。
两个已排除的路子(写进工具头注释): ①"窗内深度最近一层"分掩膜 ⇒ 平放料盘上退化成一条横带(量到的是料盘前缘凸筋);
②"亮金属∪绿光"外观掩膜 ⇒ 帧间漂移(同窗 250~996px), 且 D405 的 **0 深度会经形态学闭运算漏进掩膜**(足印拉到 375mm)。
来源配色: `meas`=紫(实测长方体), 真值带加"量测="一栏; 2D 像素框与 3D 长方体同时压在同一物体上会打架, 用 `--hide-2d` 把 2D 的标为已删。

## 相机被机械臂转过之后重画 3D 盒的定式(2026-09-28 实测踩坑)
老倪: 「我移动了机器人的位置…重新画出3D边界框」。相机位姿一变, 旧框全错。四条硬教训:
- **量测必须等臂停稳**: 机械臂在动时逐帧画面不同(TCP 两分钟内变 3 次), 量出来的框自己跳。
  先 `read_tcp` 连采 15s 看值是否恒定, 再动手; 量完把帧龄/TCP 写进报告。
- **判轴**: 腕部转过以后同一物体在画面里可能由竖变横。剖面法(逐行扫边缘)要**两个方向都扫**,
  取"有效行多 × 宽度稳"的那个(不判轴会把 90mm 的模块量成 20~50mm 且角度乱跳)。
- **minAreaRect 的 (w,h,angle) 里只有宽边方向才是 angle**: `rh>rw` 时长轴 = angle+90°。
  不判这点实测把模块朝向量偏 90°(手把 rect w=28 h=49 ang=-87.1 ⇒ 长轴其实是 +2.9°)。
- **锚点选择**: 近距视角里"绿手把"(高饱和绿)是最干净的锚, 掩膜无假阳性; 而亮金属/阈值分割
  不可用 —— 同帧里模块条 y=140 行灰度 130~255, y=100 行只有 117~120(比料盘还暗)。
- **深度分层对平放物体不可用**: 模块只比料盘抬几毫米, ±10mm 带连通域会把料盘一起吃进来
  (实测 410×95mm)。深度只在"物体明显凸起(≥20mm)"时能分层。
- 量不出就如实报负结果(本轮右侧竖放那件的绿手把细长比 1.08, 朝向定不出来 ⇒ 报"待重测",
  不硬给角度)。

## 把第二个页面通道挂到公网 (2026-09-28 实测: 工位总览 8793 → ECS)
老倪: 「http://10.163.146.78:8793/station 把这个通道, 推流到 ECS」。定式:
- **页面先做"子路径安全"再谈反代**: 页面里加 `const B=(location.pathname.replace(/\/[^/]*$/,''))`
  + `_u=(u)=>u.charAt(0)==='/'?(B+u):u`, 所有站内相对地址(data-src / 接口 / 轮询 / POST)统一过 `_u()`。
  否则 nginx 用 `location /st/ { proxy_pass ...:PORT/; }` 剥前缀后, 页面的 /snapshot/xx.jpg 会打到站点根 → 404。
  根路径访问行为不变(空 B)。
- **只读闸门要分模式, 不是一个白名单走天下**: 工位总览页面上有**手动控制区**(会真动机器人),
  所以外放的口径是"页面本体 + 6 路只读画面放行; /ctl/* /move* /gen(触发拍照烧钱) /tap /api/aoi/detect
  与一切 POST 一律 403"。追加一个 `--mode` 而不是把 /station 从 DENY 里删掉 —— 改完**跑一次真值表**
  (overlay 与 station 两模式逐路径断言 200/403), 否则容易在旧通道上开后门。
- **闸门/上游侧路径 ≠ 公网路径**: 体检脚本里的探针要存"闸门侧路径"(如 `/station?k=...`),
  公网 URL 由 `${PUB}${path}` 拼(前缀已被 nginx 剥)。存成带前缀的会得到**假 403**(以为闸门坏了)。
- **localhost.run 匿名只允许一条隧道**: 第二条 ssh -R 连上后只打到 `authn: authenticated as anonymous user`
  就**不派发域名**(日志里永远没有 https://xxx.lhr.life); 换带 key 的连接直接 `denied`。
  ⇒ 想要第二个公网口, 不要指望 lhr 开第二条, 走 ECS 反向隧道/其它宿主。
- **ECS relay 的 upload 口 ≠ 对外快照口**(§13 已记): 没 ECS 登录权限就没法给"页面级"外放 ——
  任何"推上去就等于外放了"的结论都是错的, 老老实实报"卡在 ECS 权限"。
- **免密不通 ≠ 干不了**: 项目既有口令通道(`ZMAX_ECS_PW`, 见 http-relay-service 的 zmax-relay-deploy.md)
  直接 `export ZMAX_ECS_PW="$(cat <600文件>)"` 跑 `--apply` 即可; 脚本会把口令落到 600 的
  EnvironmentFile 供 systemd 用 —— **不要卡在"等他贴公钥"上**, 先把能做的做完再说。
- 🔴 **nginx location 必须用 `^~` 前缀匹配**: 宝塔 vhost 里有 `location ~ .*\.(jpg|jpeg|png)$ { expires 30d;
  try_files $uri =404; }` 这类**正则 location**, 优先级高于普通前缀匹配 ⇒ `location /st/ {}`
  会把 `/st/snapshot/*.jpg` 全变成 404(146B nginx 404, 根本没到闸门), 而 .mjpg/页面却正常
  (容易误判成"通道尾好了一部分")。改 `location ^~ /st/ {}` 后全部 200。
- 外放后**用浏览器真跑一遍**而不是只看 curl: MJPEG 页面不会触发 load 事件(navigate 会 timeout),
  用 `document.images` 的 `naturalWidth>0` 逐格核 —— AOI 这类"有检测才有帧"的格天然是 0,
  要先看源侧 `/last_result` 是不是"尚无检测结果"再下结论。

## 按钮结果 = 浏览器大图页 (不只是画布小窗)
- 🔴 **2026-09-27 实测铁证: 窗口最大化 ≠ 图大**。老倪说"怎么还是打开一个小窗口"时, 浏览器**已经**是最大化窗口(3068x1862),
  但 4:3 单画面在 2.84:1 的宽屏上 `object-fit:contain` **只占窗口宽度 46.1%**(左右各 827px 纯黑),
  在他眼里就是"一个小窗口"。度量法: 截图后按窗口区域取舞台中间带, 逐列算平均亮度,
  `col < 2` 的列数就是信箱黑边(本次 53.9%)。
- 定式: 宽屏上要么**默认多格并排**(每格用满自己的列 ⇒ 宽度 100%), 要么给 **🖵 铺满窗口**
  (`body.m_full` 藏 header/按钮/页脚 + `#stage{position:fixed;inset:0}` ⇒ 舞台=整窗, 舞台高得
  多出来的那几百像素全给画面); 两者都实测过。**别把 contain 的黑边当成"窗口太小"**。
- 切模式的 JS 别用 `document.body.className=m` —— 会把 `m_full` 一起抹掉(实测); 用 `classList.remove/add`。
- 按钮开窗前先 `wmctrl -i -c` **关掉旧的**同名窗口: 否则每点一次堆一个, 堆出来的旧窗(旧版页面/小尺寸)
  正是用户口中的"小窗口"。
- 老倪口径: 「点场景叠加应该显示一个浏览器网页, 图像要大一些」。主交付是浏览器页;
  画布节点是附送; 不要把"画布上小窗有画面"当成交付完成。
- 开窗不能用 xdg-open: 它把地址塞进**已开着的小窗**(常在另一台显示器)且无法指定尺寸
  ⇒ 认到具体浏览器就用 `--new-window`。**但 `--start-maximized` 在本机 GNOME 下不生效**
  (实测新窗只到 2880x2012) ⇒ 必须 wmctrl 补一刀。
- `wmctrl -i -r` 要的是**窗口 id (第 1 列 0x…)**: 把标题当 id 传进去会**静默无效**,
  日志写"已最大化"而窗口不动。改完必须**读回 `wmctrl -lG` 几何写进日志**。
- 窗口可能起在**另一块显示器** ⇒ 按控制台窗口 (`wmctrl -lG` 里找 XSpace Studio) 的坐标
  先搬屏再最大化+激活; 页面标题随时会变(浏览器把地址开成旧窗的新标签也改标题),
  所以对所有标题匹配的窗都执行一遍。
- 页面本身要"大": 舞台吃满剩余高度 (`flex:1 + height:100% + object-fit:contain`),
  默认只显示叠加图铺满一屏, 另给 原始图/并排/全屏 三个布局按钮, **点画面=全屏**;
  底部真值带(帧龄/源fps/画框/手眼)必须留着。

## 多路同屏页 (6 格: 3相机 + 深度 + 工控机 2 路检测) —— 真天花板在**连接数**
- **HTTP/1.1 对同一 host:port 只有 6 条并发连接**。6 格全用 MJPEG(=6 条长连接) 会把名额占满 ⇒
  页面的 `fetch('/stats')` 永远排队, 实测右侧状态栏永远"读取中…"、按钮点击无回显(请求发不出去)。
  真根因确认法: `ss -tnp | grep :<port>` 数 chrome 连接 = 6 且全是长连接。
- 解法定式: **高速两路留 MJPEG + 其余各格走单帧快照**, 且快照**全局串行**(同一时刻只发一条,
  用预载 `new Image()` 成功再换 `img.src`, 失败保留上一帧不闪黑) ⇒ 常占用 ≤ 4 条。
- **状态接口合并成一条**: `/station/status` 一次返回 stats+ctl+aoi, 别让页面并发发 3 条。
  再加**卡顿自诊断**: 报字段超 7s 未更新就显示横幅提示"关掉其它本端口的页面"。

## 会被频繁打开的页面: 给它自己的端口(独立连接名额)
- 浏览器对**同一 host:port** 只有 6 条连接(HTTP/1.1)。实测过真事故: 用户那台 chromium 对 8791
  恰好 6 条 ⇒ 页面上部分图有了、其余格空着、右侧状态"读取中…"、按钮点了没反应。
- 诊断: `ss -tnp | grep :<port>` 按 **pid** 数连接 —— 到 6 基本就是它(注意: `ss -tn` 是
  **ESTAB**, TIME-WAIT 的连接**不算**名额)。
- 两道防线一起上: ①要频繁打开/带按钮的页面 **一格 MJPEG 都不用**, 全走串行单帧快照(常占 1 条)
  ②该页**单独监听一个端口**(如 `--station-port 8793`), 主端口同名路由 **302** 过去 ⇒
  与其它页面各占各的 6 条, 互不饿死。启动日志里要打印两个 URL。
- 前端也要能自救: POST/状态请求加 `AbortController` 超时(状态 6s / 动作 18s)、按钮禁用加 15s
  兜底放开, 失败时明写"请求没发出去/超时"; 并保留看门狗(状态 lag>7s 弹横幅)。
- 重启脚本杀旧进程: `pkill -f cam_live_stream.py` 会连**同一条命令行里出现的文件名**都匹配
  (例如同条命令里还跑了 `py_compile tools/cam_live_stream.py`) ⇒ 把自己的命令 SIGTERM。
  改成**按端口找 pid**(`ss -tlnp | grep ":8791 " | grep -o 'pid=[0-9]*'`)再 kill。

## 进手机 APP（页面必须与视频流同源，别放站点上）
- **站点是 HTTPS ⇒ 页面里取 `http://…` 的 MJPEG 属混合内容，内核直接拦死**（页面能开、画面永远黑）。
  所以叠加页由**视频源那台机器自己用 http 提供**（同端口同源），APP 用**顶层跳转**过去
  （跳转不受混合内容限制）。手机需与那台机器在同一局域网。
- 页面里 `const API = location.protocol.startsWith('http') ? location.origin : 'http://<兜底IP>:8791'`
  ⇒ 地址零硬编码，换 IP 不用改页面。
- Android 侧：manifest 必须 `android:usesCleartextTraffic="true"`（否则 9+ 拒 http），
  WebSettings 加 `setMixedContentMode(MIXED_CONTENT_ALWAYS_ALLOW)`。
- **不想依赖站点部署/密码 ⇒ 给 APK 加第二个 LAUNCHER 入口**（同包两个桌面图标）：
  manifest 里再加一个 `<activity>`，带自己的 `android:label` + `android:icon`（`@mipmap/ic_*`，
  各密度 png 都要齐）和同样的 MAIN/LAUNCHER intent-filter；构建脚本 javac 把**两个 .java 都编**。
  验：`aapt2 dump badging` 应列出**两条** `launchable-activity`，且 dex 里两个类都在。
- `--build`/`scp` 之外**没有别的部署通道**：relay 是数据槽（单槽覆盖），不能发页面文件。

## 用户说「这两格要实时推流」时: 先算连接名额, 再选 MJPEG/snap (2026-09-27)

- **HTTP/1.1 同一 host:port 只给 6 条并发连接**。一条 MJPEG 长连接**永久占 1 条**, 所以 6 格全推流 = 6 条
  占满 ⇒ `fetch`/点动 POST 排在队尾看起来像“按钮没用”(实测 chromium 到 8791 恰 6 条 ESTAB 即上限)。
  算法: **MJPEG 格数 + 状态轮询(1) + 串行快照(1) ≤ 5**; 真要更多格就换子域/多端口(每个端口各 6 条)。
- 用户只关心“看着实时”的格(本次是工控机 AOI 两路)走 MJPEG; 真实相机 4 格继续单帧快照 —— 快照刷新
  1~2s 在目视上足够实时, 还把名额留给按钮。
- 服务端本来就有 `/<name>.mjpg` 就用它, **不要重写**; 推“加工后的判据图/规范图”而不是 4.9MB 原图
  (实测 5s 抓流 767KB/6 分片), 原图另开一条**低频**流给「整板原图」按钮切。
- 面板标题要自己标出模式(`· 🔴 实时推流`), 否则用户分不清这格是流还是快照。
- **副作用**: `<img src=*.mjpg>` 挂上后浏览器**永不触发 load/onload**(流不结束) ⇒ 任何“等页面加载完成”的
  自动化(navigate/snapshot)会超时; 取证改用 console 查 DOM(`img.naturalWidth`/`currentSrc`)+ scrot 截图。
- 深度图那种真低帧率的源(实测 0.24Hz)别假装实时: 面板上标真帧龄, 并告知“每 N 秒才一帧”是硬件/驱动侧的事。

## 控制台按钮「点了什么都没打开」的真根因: DBUS=disabled (2026-09-27 实测复现)
- 症状链: 日志照打「收到点击 → 浏览器已启动(chromium)」, 然后 12s 认窗全空、**一个窗口都没有**, 进程随即消失。
  离屏脚本 / 终端手敲**逐字相同的命令却能开窗** ⇒ 别只在"认窗逻辑/窗口位置"里找原因。
- 真根因: 控制台进程环境里是 `DBUS_SESSION_BUS_ADDRESS=disabled:`(从终端/服务/systemd 启动时常见)。
  本机 chromium 是 **snap**: 它必须能连会话 D-Bus 让 snapd 建好 cgroup, 连不上就打印
  `"<...scope> is not a snap cgroup for tag snap.chromium.chromium"` 然后**静默退出(exit 1, 零窗口)**。
- 逐字对照(同机同 profile, 只换这一个变量): `disabled:` → 退出码 1 / 窗口 0 个;
  `unix:path=/run/user/<uid>/bus` → 进程存活、窗口正常。**`snap run` 不解决**(同样 exit 1) —— 关键变量是 D-Bus, 不是 cgroup 名。
- 定式: ①给子进程一份干净 env(`env=_zmax_sane_env()`: DBUS/XDG_RUNTIME_DIR/DISPLAY/XAUTHORITY 补齐)
  ②主程序**一启动**就补 DBUS ③启动脚本里也补 ④浏览器 stdout/stderr **落文件留证**(丢 DEVNULL ⇒ 出事两眼一抹黑)
  ⑤"命令 + cwd + cgroup + DBUS 修前/修后"写 `/tmp/zmax_browser_cmd.log`。
- 🔬 **给按钮加自测命令通道**(强烈建议): `studio.py` 本就轮询 `/tmp/zmax_nav_cmd`(一行一命令) ⇒ 加
  `ov_page` / `station_page` 直接调按钮本体, 就能从**控制台内部**反复复现, 不必盲点坐标。
  盲点坐标极易点到按钮间隙 ⇒ 误判"按钮没反应"(实测: 本机 v5.15.33 画布页 y232 处:
  状态空间≈2407-2567 · 3D视图≈2600-2760 · 场景叠加≈2787-2947 · 工位总览≈2973-3133)。
- 同类: 目标机器上**任何** snap 应用(不只是浏览器)从终端/服务拉起都可能撞这条 ⇒ 先补 DBUS 再拉。

## OPT(10082/10083)「实时推流」的真实上限 = 触发拍照耗时 (2026-09-27 实测)
- 先量再改: 不触发时**连读 3 次 `/picture?kind=origin`(隔 3s)指纹完全一样** ⇒ 工控机内存里的图是**静止的**,
  必须触发拍照才会有新图。只读不触发是 8~11ms(拿旧图), `?grab=1` 才是真拍。
- 单张耗时实测: 10082 `GET /picture?kind=origin&grab=1` **0.67~0.73s**; 10083 `GET /picture?kind=crop&grab=1` ≈0.6s
  ⇒ **硬件上限 ≈1.4~1.7 帧/秒**。任何"改成 25fps 实时"的要求都要先把这个数摊给用户(相机取图时间, 不是网络的锅)。
- 定式(**有人看才顶满, 没人看就退避** —— 产线相机不能长期被占):
  ① MJPEG 生成器每轮打心跳 `_AOI_VIEW_TS[name]=time.time()`(**用时刻不用引用计数** ⇒ 客户端被强杀不会泄漏计数,
     不会永久顶着重拍产线相机); ② 采集线程: 心跳在 8s 内 ⇒ 每轮带 `&grab=1` 且**不 sleep**(节奏=取图耗时);
     否则回到"只读不触发"的慢速; ③ 回执里加 `live` 字段, `/stats`/`/station/status` 可见 ⇒ 页面和我都能核对当前模式。
- 量法(交付证据, 别只报"改好了"): `curl -m 10 /<name>.mjpg` 落盘后数 JPEG SOI 数 ⇒ 帧/秒; 同时看 `/station/status` 的 `live`。
  老倪那次实测: 空闲 1.05/0.89 fps(不变) → 有人在看 1.4/1.4 fps。
- 页面侧**不用改**: 面板本来就是 `<img data-mode="mjpg" src="/<名>.mjpg">`, 采集快了流就快了(帧龄从几十秒降到 <1s)。
  但**服务重启后旧页面的 MJPEG 连接已断** ⇒ 必须刷新页面, 否则会出现"一路 live=True 另一路 False"的假象。

## 像素框 → 3D 框的反解定式 (重画 3D 框用)
目标: 把**已目检确认的 2D 像素框**变成 base 系 3D 盒(能跟手眼走)。
- 🔴 **别把物体轮廓反投到台面**: 物体有高度, 轮廓的足印会被**放大**(实测 143px 的模块反投出 140mm, 实际约 60mm)。
  反投平面取**物体中高面**; 高度未知时, 台面 z 用场景里 `台面·工作台面` 盒的上表面(实测 0.1198m), 别自己编。
- 定式: 初值=中高面四角反投求心 + 局部边长估尺寸, 然后 `scipy.optimize.least_squares` 解
  (cx, cy, yaw, L, W) 5 参(高度固定), 残差 = `box3d_to_xyxy` 的 4 个边界 vs 观测框。
- ⚠️ **5 参拟合 4 约束 ⇒ 残差 0.0px 是必然的, 不是精度证据**。要另外给**物理合理性**(尺寸/长宽比是否像该物体)
  和**多源交叉**(本地 Qwen / 云 VLM / 像素取证子代理), 别把“刚好重合”当准。
- 判坏不要混口径: 手眼质量看 `load_handeye()['closed_loop_std_mm']`(实测 TSAI/8 poses/**1.74mm** = 好),
  别拿另一个量纲的数字(如某处出现的 915°)断言标定坏了 —— 本轮我就是这么误记了一条错笔记。

## VLM 框的边界一定会过度延伸 ⇒ 端点用逐行扫核实 (2026-09-28 实测)
四路(我的分割/本地 Qwen/像素取证子代理/云 VLM)在**位置**上收敛, 但在**框的下端**分歧:
云 VLM 给竖模块 `y2=239`, 而逐行扫该竖条(x384-424)显示 **y120-160 绿拉环 42~46%、y160 以下绿像素 0**
⇒ 模块止于 y≈160, 云 VLM 多框了 80px(把槽/阴影算进去)。
- ⇒ 定式: **VLM 只用来定“是什么/在哪一带”, 框的每个端点用像素逐行(或逐列)扫绿拉环/金属段**; 两端都扫。
- 拉环(高饱和绿 G-R>25 且 G-B>20)是该类零件最干净的锚; 金属阈值在同帧不同行会失效(比底座还暗)。

## 推理型 VLM 空返回要按 `finish_reason` 分两类 (本轮自己踩了一次)
- `finish_reason=length` + content 空 = **调用方 `max_tokens` 给太小**(思考链吃光)。本轮我给了 **900** ⇒ 3 次全空;
  改 **4000** 后 19~126B 正常返回。视觉模型出 JSON 一律 ≥3000~4000, **别归因 API/额度**。
- `finish_reason=stop` + 空 = API 侧偶发 ⇒ 同一张图**立刻重试**(实测 2.7s/137s 都可能成功)。
- 登录判据: `usage.completion_tokens_details.reasoning_tokens` 是否≈max_tokens ⇒ 一眼分两类。

## 嵌入式物体的 3D 框: 朝向靠槽族、高低靠齐平 (2026-09-28 老倪两轮纠正)
- **朝向**别靠局部边缘拟合(会被槽沿/托盘边骗): 用 Hough 量出料盘**平行线族**提嵌在槽里的物体**长轴 ∥ 所在槽的边线族**; 把族向**反投到台面**得 base 系 yaw 再锁定。判据: 模块**两侧**邻接线的角度须一致(实测右邻接 76.1/73.6/74.2/77.0° = 槽族 ✓, 左邻接 86–93° = 另一结构 ✗)。
- **高低**是眼睛最先看出的错: 嵌入式物体**不要"立着"画**(底面=台面往上长 H ✗) ⇒ 顶面 ≈ 台面/槽上沿、箱体**往槽里沉**。实测: 立着版框顶沿比物体可见顶沿高 13~22px(= 老倪"高出来了"); 改成顶面=台面后顶沿 y 与可见顶沿重合(62/41)。
- **自动判据必须有回归闸门**: 只有新结果的两路指标都优于现版才写盘 —— 本批拦下两次(颜色分割掩膜失真 IoU 0.605→0.280; 边缘能量单目标被槽沿骗到)。落盘前先备份 overlay_spec.json。
- **目检结论是硬约束, 优先于任何自动判据**: 老倪说"顶面齐平/嵌在槽里"就直接把 ztop=台面、yaw=槽族**固定**, 只留中心/长宽可解(4 约束 4 未知量) ⇒ 此时**残差 0.00px 是必然、不是精度证据**(必须另找独立自检: 本批是解出宽 20.8/17.1mm ↔ 真实光模块宽 18.4mm)。
- **颜色分割在这个曝光下不可靠**: 模块是暗的(横区 V 中位 74), 亮金属阈值只圈到 22% ⇒ 别用颜色当掩膜。
- `data/scene/overlay_spec.json` **被 .gitignore 忽略**(.gitignore `data/`) ⇒ 它只能进**现场批次归档**(`~/zmax_data/release_archive/<v>_<date>/state/`), 不入库。

## 把 TCP 轨迹做成 3D「通道」叠在**固定相机**上 (VR 面板免标定 + AR 面板要外参, 2026-09-29 实测)
老倪: 「用 VR/AR 把机器人工具中心轨迹可视化出来, 要有明显的 3D 渲染让人感觉出走过的通道, 默认不显示, 人工开启」。

- 🔴 **先证明这台相机的画面里看得见末端, 再谈标定**: 端到端做完了才发现笔记本 640×480 那路
  **末端工具直接出画**(只有上段臂杆, 从右边缘进/左下没入托盘), 底座也在画外, 且被操作员躯干挡掉中段工作区 ——
  这种视角**外参标得再准, 管道也会画在看不见的臂上甚至压在托盘上**, 拿它调算法比不画更坏。
  判据(视觉子代理逐块放大): MAXHUB 1280×720 里整条臂+台面+夹具都在画面内 ⇒ **选它当 AR 底图**;
  同一件"夹具上方的小白块"在两张图里都出现 = 交叉验证末端确实在夹具正上方。
- **标定按相机各存一份**(`data/scene/cam_calib.json` 的 `{"<cam>": ...}`, 读取侧 `load_calib(cam)` 先多相机后单相机兼容),
  页面**可切相机**; 切相机必须同时换 `IMG_W/IMG_H` 并清掉已点的标定点 —— 标定点是**像素量纲**, 混用分辨率必然全错。
- **VR 面板(不标定, base 系)才是立刻能用的那个**: 但它必须**按数据包围盒自动对焦**, 别写死视点。
  实测踩坑: 写死 `tgt=(0.70,0.22,0.14)/dist=1.6` 而轨迹只占 ~5cm ⇒ 画布中间一小坨 ≈50px, 用户结论就是"没有轨迹";
  改成包围盒自适应后同一份数据 **2818px**(铺满), 再给「自动环绕」自转 ⇒ 立体感一眼可读。
- 🔴 **页面必须每轮轮询都同步「显示开关」, 不能只在 init 读一次**: 用户打开页面时后端若处于关/清除线在末尾,
  页面就永远画空的, 之后在别处开了它也不知道 —— 这就是老倪反复"看不到历史轨迹"的两个真因之一。
- **MJPEG `<img>` 每帧触发 `load`, 而给 `canvas.width` 赋同一个值也会清空画布** ⇒ 逐帧闪白/闪烁。
  定式: 布局用**尺寸签名**守卫(不变就 return) · `canvas.width/height` 只在真变尺寸时设 · 重绘只按**数据签名**触发(别 1.5s 无条件重画)。
  取证: 注入 30 次 `img.load` 事件, 断言重绘次数 = 0 且标记像素没被清。
- **演示/标定 UI**: 末端只有 10~25px 时肉眼点不准 ⇒ 光标旁挂 **4× 放大镜**(跟随 + 十字准星, 越界自动翻边)。
  最少点数 **6**(<6 无 DLT 线性初值, 解会"飞", 实测退化到 f=84.6/z=1.4e4m/RMS 2.4e8px; 带 DLT 初值后自检 f 520→521.9、RMS 0.46px)。
- **显示/清除语义要单一真源**(`tools/traj_display.py`, 推流侧 + 服务侧 + 两个页面共用):
  「清除」= 把**清除线 baseline_n 设到当前时刻**(只画新点, 数据不删), 用户会理解为"历史全没了" ⇒
  必须另给「全部历史」(baseline_n=0)。隐藏的折线移到 `_hidden_paths.json` 缓存, **永不真删**。
  默认关由**推流循环**强制执行(trace/plan 从规格里摘掉), 光改前端开关不算数。

## 「清除/删除轨迹」点了没反应 / 删不掉历史 —— 三个真根因 (2026-09-29 实测)
老倪: 「/overlay 删除轨迹，无法删除历史轨迹」。查到的是**三件事叠在一起**, 每一件都能单独让按钮变哑巴:

1. 🔴 **按钮打的是另一个端口上的服务, 而那个服务没人托管**。`/overlay` 页的四个轨迹按钮
   (`▶显示/⏸隐藏/🧹清除/📜全部历史`)并不打本页的 8791, 而是打 **AR 轨迹台 `:8797`**
   (`tools/web/scene-overlay.html` 里 `var AR_PORT = 8797`)。该服务当时**根本没在跑**
   (`ss -ltnp | grep 8797` 空), 因为它是人工起一次、没有任何 unit 的 —— 一旦机器重启就永久失效。
   定式: **凡"页面按钮 → 另一个服务"的, 那个服务必须有 systemd 单元**, 否则故障表现是"按钮没反应"而不是"服务挂了"。
2. 🔴 **「清除」只改了清除线, 真删折线靠下一轮发布**。`/api/traj/clear` 原来只做 `set_state(baseline_n=n)`,
   真正把折线从叠加规格里挪走的是发布器; 而发布器要读**录制器**(容器内)落的 `/tmp/live_trace.json`,
   录制器一停它就只打一行"还没有轨迹数据(录制器起了吗?)/tmp/live_trace.json"就退出 ⇒
   **规格里那条历史折线一个像素都不动**, 用户看到的就是"点了没用"。
   定式: **用户看得见的动作必须在服务侧直接落盘**, 不能把可见结果托给下游某轮发布 ——
   清除 = 直接 `traj_display.strip_origins(["trace"])`(先改规格, 画面下一帧就没了);
   反向「全部历史」= 规格里没折线时 `restore_origins(["trace"])` 兜底。发布器再把清除线之后**新走过**的点画上。
3. 🔴 **采集链会自己退, 且没人托管**: 录制器/发布器都带 `--seconds`(1h / 90min)到点自己 exit,
   停了 8 小时后页面还写着「已录 26479 点」——用户以为数据是新的。
   定式三件套: ①systemd 托管 + `Restart=always`; ②**心跳可视**: 页面读发布产物
   (`reports/moveit/live_trace.json`)的 mtime, >阈值就显示「⚠️ 轨迹链已停 N 分钟」;
   ③发布器加**停摆守卫**: 源龄超阈值就 `publish([], clear=True)` 把画上的轨迹撤掉,
   绝不许把**冻结的旧轨迹**当实时画。

⚠️ 附带的真坑: **录制器重启后它自己的计数 n 从 0 重来, 而"清除线"是按 n 记的** ⇒ 上一纪元的清除线(如 26479)
永远大于新 n(几十), 发布器走 `raw[base:]` 的兜底只留最后一个点 ⇒ 画面上的轨迹被**永久夹成 1 个点**。
定式: 录制器启动脚本里**同步把清除线归 0**(新纪元 = 新的计数空间)。

取证口径(都要实测留数): `curl -s 127.0.0.1:8797/api/traj/state` 看 `in_spec`/`trace_age_s` ·
清除前后比 `in_spec.trace.n_pts`(应归零/回落) · 真浏览器点按钮后读 DOM 角标与 `baseline_n` 变化 ·
叠加图里数**黄色轨迹像素**(实测 158 → 68, 余下的是清除线之后新走过的点, 属正常)。

## 在固定相机画面上画「辅助线」定空间位置 (2026-09-30 老倪: 「定位桌子上面、横梁内部的空间位置, 给我画几条辅助水平线叠加到笔记本摄像头的画面上」)

- 🔴 **先查页面引用的到底是原始帧还是叠加帧**: `/station` 的笔记本格子原来 `data-src="/snapshot/local.jpg"`(原始帧) ⇒
  叠加里画什么用户**一概看不见**(与上次"工位总览没有轨迹线"同源)。改 `overlay_local.jpg` 后**回读页面 HTML** 确认,
  页面是 **mtime 热读** ⇒ 不用重启服务。落地新 origin 颜色(改 `scene_overlay.py`)才需要重启。
- 线位置**只用像素台阶定**, 模型只给语义:
  · 水平边 = 各行 `|Sobel_y|` 均值取峰; 竖直边 = 各列 `|Sobel_x|` 均值取峰; 再用 Hough 线族角度看"竖直+水平"是否成 90°(可与用户口述的"横梁互相垂直"互相印证)。
  · 每条候选边再算**上下 20 行均值差**(台阶强度) ⇒ 梁的内沿/台面沿这种真边界 |Δ| 大(实测 −29.5 / +42.2), 梁心或平滑处只有 1~3 ⇒ 一眼分出"真边界 vs 模型瞎指"。
- 落地方式**零代码改动**: 2D 分支 `cv2.rectangle(..., 线宽 2)` ⇒ 用**细盒**当水平线
  (`{"origin":"guide","xyxy":[0,y-1,W,y+2],"no_label":true}`); ⚠ 2D 分支有退化判定 `y2-y1<2 跳过` ⇒ 盒高取 **3px**。
- ⚠ **画面底部状态带会把线整个盖住**: 实测 y=466 的线在叠加帧里**一个像素都没有**(状态带不透明、宽约 600px),
  而同批 y=108/264/350 各 +3840px ⇒ 核验时"某条线 0 像素"先看它是否落在状态带里, 别怀疑自己画错。
- 🔴 **子代理/模型列进 `uncertain` 的项, 绝不可以当已验证直接落地**。本轮实测: 视觉子代理在"不确定"里写了
  "y≈264 的台阶可能是台面后沿、也可能是白墙上的阴影边界", 我没跟进核实就画成了"台面后沿" ⇒ 老倪一眼看出
  "你画的是后面的窗台" ✗。**自己复量才钉死**: 左区 y=264 上下均为中性灰(BGR 107/113/113→133/138/138,
  无台面应有的透视/冷暖差) ⇒ 确是窗棂/白墙。定式: 凡"可能是A也可能是B"的特征, **先用物理量(色/台阶/材质)判完再画**,
  判不出来就不画那一层。
- ⚠ **弱拟合(=内点少)不能当锚点**。本轮托盘后沿的特征线只有 11~12/28 内点 ⇒ 拟出 335(偏 13px);
  改用**逐行剖面找最强"亮→暗"台阶**(托盘区实测 y=346~350, −5.0~−6.7; x=350 处 340:111→350:18 直接掉进托盘暗腔)
  ⇒ 锚点 348。定式: 有强实测台阶的层一律用固定锚点, 别让弱拟合把线拉偏。
- 交付口径: 亮色(`guide`=亮青 255,255,0) + `no_label`(不出现"白底黑字"标签) + 端到端核验(叠加帧 vs 原始帧在**该 y 的窄带**里数该色像素增量, 实测每条 +3840)。

## 世界水平线 = 过**消失点**的斜线, 不是图像横线 (2026-09-30 老倪: 「画的线不是以相机坐标系为轴, 要以世界坐标系为轴, 要平行于横梁」)

- 🔴 **图像水平 ≠ 世界水平**。3D 平行线在图像里交于消失点 ⇒ "世界水平且平行于横梁"的线是**过横梁消失点的斜线**。
  本轮实测：4 条层的倾角 −3.1° / +5.0° / +8.3° / +13.9° (**层越低越斜**, 正是水平面向消失点收敛的必然)。
  若只画像素 y 恒定的横线, 就是"以相机坐标系为轴" ✗ —— 用户会直接指出。
- **消失点只用横梁自身的两条平行棱求交**(上棱亮线 + 下棱亮暗台阶; 两者在 3D 里平行、在图像里收敛),
  这是本视角唯一可靠的平行证据。⚠ 本视角下两棱近乎平行(斜率差仅 0.066~0.09) ⇒ **VP 条件数差**,
  x 在 ±150px 量级浮动 ⇒ **倾角重复性 ±1~3°**: 作目视参考够用, **不是量具**; 要度量级精度必须给该相机
  做一次现场标定(3+ 已知 base 坐标点 ↔ 像素 ⇒ 平面单应; 仓库已有 `data/scene/cam_calib.json` 多相机机制)。
- 🔴 **不许用"随便两族线求交"的自动拟合**: 梁上下棱近乎平行时条件数极差, 实测三次给出 **144 / 248 / 286**
  三个不同答案 —— 这种解宁可报"解不出, 不画", 也不许拿去画线。(同场自动 Hough+PCA 拟合也被吊灯/线槽污染, 给出 −8.4°/−4.1° 等错值。)
- 渲染器必须有 **`pts2d` 折线元素**(轴对齐 `xyxy` 盒子画不出斜线) + 纳入"真值带之上补画"通道(否则底部状态带把线盖住)。
- 核验口径: **逐条**取"落在该线 ±3px 内"的像素拟合倾角(按 y/x 窗口取会把邻线混进来, 本轮自己踩过),
  与目标比 ±1.5° 内为过(实测差 ≤0.14°)。

## 交付前自检（必做）
1. `--verify` 投影链自检（手眼 det/正交性/闭环 std）
2. 正投影 vs 实检逐位姿表（报中位 + max，不报单个最好）
3. 双链收敛 IoU/中心差
4. 叠加帧与原帧**差异像素占比**（证明真画上了，不是只报了个数）
5. 把叠加后的图**再喂给 VLM 回读**，核对它读到的底部真值带内容 = 实际状态
6. 服务端点 HTTP 状态 + `/scene.json` 的 `_overlay_info`（画几框/跳过原因/tcp_ok）
7. 场景元素清单：每件带 `source` + 画面内/外 + base 坐标；链路往返 px 与凹陷 Δ 一并留档（`gen_scene_cell.py --report`）
